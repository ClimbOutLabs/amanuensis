- Workspace tasks MUST use `package.json` scripts; add a script when a missing workflow is repeatable like the existing commands, not ad hoc commands.
- CI package path filters, matrix package ids, and root scripts `test:*` in `.github/workflows/ci.yml` and root `package.json` MUST stay synchronized when a workspace package is added, renamed, or moved; the `store` filter sync rule lives in `packages/trueforge-core/src/agent-session/store/AGENTS.md`.
- Release wiring MUST keep dist-free host development, `pnpm smoke`, and packed CJS/ESM consumers of `@truefoundry/trueforge-core` and `@truefoundry/trueforge-sdk` working without changes. Workspace loaders opt into SDK/core `src/` via the `trueforge-dev` export condition (never `"development"`); the SDK's `trueforge-dev` branch MUST keep `types` on its generated `.d.ts` (emitted by root `sdk:types`) because generated source is not `exactOptionalPropertyTypes`-clean.
- Release versioning is handled by the maintainers; pull requests to this repository do not add changeset files.
- Shared Postgres/Redis settings in `docker-compose.yml` and `docker-compose.dev.yml` (image versions, health checks, `env_file`) MUST stay synchronized; intentional differences (app services, data paths, project `name`, host ports, in-network `POSTGRES_HOST` / `REDIS_URL`) MUST stay explicit. `packages/trueforge/.env` is the host-dev + secrets source; `docker-compose.yml` may read it but MUST override container connectivity so host-dev localhost values are not used inside the smoke-test stack.
- Changes to types or schemas MUST keep `packages/trueforge-core`, `packages/frontend`, `packages/trueforge`, and `patches` synchronized; they MUST NOT update only one affected layer.
- TypeScript code MUST NOT use assertion escapes such as `as T`, `as unknown as T`, non-null `!`, or `as never` to silence type errors; implementations MUST use sound contracts, guards, or corrected types.
- When catching an error and throwing another, the new error MUST set `{ cause: caught }` so the original failure is preserved for logs and debugging.
- Every type, schema, helper, and contract MUST have one canonical owner; code MUST NOT introduce duplicate definitions or forwarding shims that hide ownership.
- AgentUIServer / server-port types (`AgentChatServer`, `AgentBuilderServer`, catalog ports, session/turn DTOs, stream events) MUST be defined only in `@truefoundry/assistant-ui-runtime` (`src/server/types.ts` / `events.ts`). `@truefoundry/trueforge-ui` MUST re-export them from `src/server/types.ts` (pass-through aliases only) and MUST NOT add hand-written parallel definitions of those ports/DTOs.
- Runtime types backed by Zod schemas MUST be derived with named `z.infer<typeof Schema>` aliases; code MUST NOT duplicate those schemas as hand-written interfaces or indirect utility-type chains.
- Modules MUST use static `import` and `import type`; they MUST NOT use `require()`, `require.resolve()`, or lint suppressions to bypass import checks.
- A change that makes code unused MUST remove that dead code in the same change; it MUST NOT leave stale exports, files, documentation, duplicates, or “just in case” shims.
- Every nested `AGENTS.md` MUST have a sibling `CLAUDE.md` containing only `@AGENTS.md`, so Cursor and Claude Code load the same scoped rules.
- OpenAPI specs under `.github/fern/openapi/openapi.json` and `docs/openapi.json` are autogenerated in CI and MUST NOT be edited manually (both copies MUST stay identical)
- Code under `packages/trueforge-sdk` is autogenerated in CI and MUST NOT be edited manually
- Tests MUST live under a package-top-level `test` or `tests` directory that mirrors the `src` layout; they MUST NOT be inlined under `src`.
- Functions with more than one parameter of the same type MUST take a single options object (e.g. `f({ a, b }: { a: string; b: string })`); they MUST NOT use multiple positional parameters of that repeated type (e.g. `f(a: string, b: string)`).
- Zod unions MUST use `z.discriminatedUnion` whenever every member carries a shared literal discriminator field; `z.union` is only permitted when no such common discriminator exists.
- HTTP/OpenAPI wire shapes (path params, query params, request/response JSON fields) and database identifiers (table/column names, persisted jsonb document keys) MUST use `snake_case`.
- Server code MUST NOT read environment variables via `process.env` directly; all env reads MUST go through `packages/trueforge/src/config.ts`, unless there is a documented special requirement (for example bootstrap before config is loaded).
- UI styles MUST use `rem` for lengths (not `px`); assume **1rem = 16px**. Prefer Tailwind spacing/type scale utilities when they fit. Exceptions: `0px` in `calc()`/`env()` fallbacks, existing media-query breakpoints, and canvas/measurement APIs that require CSS pixels.

## Code comments

- Comments MUST explain intent, trade-offs, or constraints and remain brief; they MUST NOT restate the code, include issue-tracker IDs, or use `{@link …}` / deep cross-links.
- Do NOT add file-level banners that enumerate implementations, backends, or call graphs; put a one-line note on the symbol that needs it, or omit.
- Comments MUST NOT leak internal wiring into public or shared surfaces.
- OpenAPI / route `description` and `.describe(…)` strings MUST stay under 50 words and describe the caller-visible contract only — not backend routing or storage.
- TODOs stay to one short line when needed.

## Spec-driven development

- Non-trivial features MUST have a spec under `specs/NNN-slug/` before
  implementation: `spec.md` (user-visible behavior, numbered requirements,
  examples, out-of-scope, testable acceptance criteria), `plan.md`
  (technical approach, files and interfaces, decisions), `tasks.md`
  (small units with done criteria). Copy `specs/_template/` to start.
  The full workflow is documented in `specs/README.md`.
- Specs are behavior-focused: they describe what the user experiences, not
  the implementation. Implementation details belong in `plan.md`.
- One feature per spec. Split when it gets big and link the pieces.
- PRs MUST reference their spec directory. Reviewers check the diff against
  the spec's acceptance criteria and reject changes outside the spec's scope.
- When scope changes, update the spec first (before coding the change when
  possible), then resync the plan and tasks. A spec that no longer describes
  the code MUST be fixed or deleted, not left to rot.
- Implement from a fresh session with the spec as the context. Do not carry a
  long design conversation into implementation; the spec is the handoff.
- Trivial fixes and small refactors do not need a spec; a clear PR
  description is enough.

## Test honesty

- Tests MUST assert observable behavior. A mock-call assertion is legitimate
  only when the call itself is the observable behavior, for example when the
  call is the only side effect the unit produces. A test whose mock assertion
  could pass while the real behavior is broken is a false signal.
- Every test MUST contain at least one assertion that can fail for a real
  reason. Placeholder assertions (`expect(true).toBe(true)`) are forbidden.
- Type-level tests (`@ts-expect-error`) MUST be wired into a gate that
  actually type-checks them. An assertion no gate verifies is decoration.
- Tests MUST engage the production shape they claim to cover. A test that
  passes against mocks but whose code path never fires against the real
  service is a false signal; verify against real integrations where the
  suite supports it.
- Do not add tests to raise a count. One honest test beats ten decorative
  ones.

## Review bar

- Every PR gets a hard adversarial review: two to three staff-engineer lenses,
  each trying to kill the PR. Every finding is fixed (gates re-verified) or
  explicitly adjudicated with reasoning recorded. Any BLOCK verdict is a hard
  stop: the PR is fixed, re-verified, and re-reviewed until reviewers approve.
  No exceptions.
- One lens is always the SCOPE/USER lens: it starts from what the user asked
  for and walks backwards. It states the desired end-user experience first,
  then judges whether the change delivers it. It argues outcomes, never
  implementation details.
- The USER lens MUST actually run the user journey, not narrate it. A review
  that approves code without executing the integration it claims is a rubber
  stamp.
- Security, efficiency, code quality, and user outcome are all mandatory
  properties of the implementation, not competing priorities to trade off.
  A journey delivered by an insecure, wasteful, or sloppy implementation is
  not a delivered journey.
- Reviews run before gates: get the adversarial reviews first, then verify
  the final approved head once. A review BLOCK after green gates wastes a
  full gate cycle.
- Verify once at the exact head. Never re-run a green gate on an unchanged
  SHA.

## Verification

- `pnpm verify` runs the full local gate (format, typecheck, lint, build,
  tests, private-data scan). Run it before pushing, not after something fails.
  Local gates are the source of truth.
- GitHub Actions (`.github/workflows/ci.yml`) runs the same checks on every
  PR once the repo is public (free for public repos). PRs MUST be green
  before merge. Do not claim GitHub CI runs on the private repo; it does not.

## Release flow

- The public tree is produced by export machinery from the private source
  repo. Do not hand-edit the public tree; land changes in the private source
  and let the export carry them. Direct public-target updates happen only on
  explicit maintainer command.
- Public must stay deployable at all times. Never publish a partial state.

## Upstream and forks

- "Upstream" means TrueForge (truefoundry/trueforge), the harness this
  project builds on. Upstream changes land on a `sync/upstream-<date>` branch
  for review; never merge an upstream sync into `main` without an explicit
  maintainer request.

## Feature freezes

- During a declared feature freeze (announced by the maintainer), no new
  features land; only fixes and the explicitly allowed work proceed. Public
  stays deployable throughout the freeze.
