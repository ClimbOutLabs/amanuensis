The sandbox gives your agent a secure, isolated environment to run code, manipulate files, and execute shell commands — separate from the TrueForge server and your infrastructure.

Skills and [Code Mode](/key-features/code-mode) require a sandbox. Check that it is ready under **Settings → Sandbox**, then enable the sandbox on each agent that needs it.

## TrueForge's approach

There are two common patterns for combining agents with sandboxes:

| Pattern | Where the agent runs | Trade-off |
| --- | --- | --- |
| **Agent in sandbox** | Inside the sandbox image | Sandbox is provisioned even for the simplest request; secrets must live in the sandbox; updates mean rebuilding images |
| **Sandbox as tool** | Outside, on the server | Sandbox is provisioned on demand when needed; secrets stay in the harness; sandbox is only for exec/files |

TrueForge uses **sandbox as tool**: the agent loop and credentials stay in the harness; the sandbox only runs code, file, and shell operations.

That means:

- Model and MCP credentials never enter the sandbox.
- Conversation state survives a sandbox crash.
- A sandbox is created only when the agent actually needs one — simple Q&A and MCP calls incur no sandbox cost.

## The Docker sandbox

Code the assistant writes with `run_code` (Python and Node.js) runs in an isolated Docker container with no network access. **Settings → Sandbox** shows whether it can run right now: ready, or off with the reason (Docker not available to the server, image not downloaded, image signature not verified, and so on) and what to do about it. Use **Re-check** after you fix the cause. The image and the limits for each run (time, memory, disk) come from the server configuration and change only with a restart.
A script the assistant writes in the chat's workspace runs with `run_code` by name (`script_path`). The run reads a copy of that one file and never changes it. Package installs work only in a chat bound to a repository where downloads are allowed, and only on a sandbox that can reach the package gateway (sandbox slots). The Docker sandbox has no network for packages, so an install there is refused before any approval prompt.

Settings no longer offers a choice of sandbox provider. Docker is the only option offered there.

## Sandbox slots (preview)

A second backend runs `run_code` and the shell and file tools in four hardened slot containers instead of Docker containers started by the server. Each slot runs a small agent as PID 1, and every call starts in a fresh gVisor guest with no network. The server holds no Docker socket: it reaches a slot through a Unix socket in a small control volume that only the server mounts. The volume is mounted read-only so the server cannot change what is in it; that does not limit what the server can ask the slot to do, because connecting to the socket is all it takes. Keep the control volumes out of every other container.

- The installer sets the slots up for every instance and connects the instance's app to them: one `installer/install.sh` run builds the slot image, installs the AppArmor profile in `/etc/apparmor.d` (so it loads again at every boot) and creates the slot disks on Linux (asking before any `sudo`), and makes sure Docker starts at boot, starts the four slots and checks each one. `aman doctor sandbox` checks the slots and their attestation again at any time, and `aman doctor sandbox --fix` repairs them: it rebuilds the image, reinstalls and reloads the AppArmor profile, recreates missing disks and restarts the slots, asking before any `sudo`. Developers working from a checkout without the installer can start slots with `pnpm sandbox:slots`, which runs the same code. Either way it builds the image, starts the slots and checks each one; the agent refuses to run anything unless every safety check passes (user, capabilities, no-new-privileges, seccomp, read-only root, loopback only, no Docker socket, cgroup limits, AppArmor where the host has it, a workspace on its own disk, and a working gVisor guest).
- Each chat's workspace has a size limit (2 GB by default), enforced while a command runs. On Linux, setup (the installer, `aman doctor sandbox --fix`, or `pnpm sandbox:slots --fix`) also gives each slot a fixed-size disk of its own (16 GB by default, `--disk-gb` to change it): after asking, it creates the disk files under `/var/lib/aman-slots`, adds them to `/etc/fstab` and mounts them, so a runaway command can fill only its own slot's disk. On Docker Desktop and WSL2 there is no per-slot disk; the virtual machine's disk bounds the workspaces. `installer/install.sh instance remove <name> --purge-data` removes the instance's disk files along with its data (`pnpm sandbox:slots --down --purge` does it for a checkout-only setup).
- A command can use at most 128 processes. Allowed environment variables for a command are a short list (locale, terminal, language runtime and git settings); others are refused with their names.
- The installer's instance compose file sets `SANDBOX_BACKEND=slots` and `SANDBOX_SLOTS_DIR` for the app and mounts the control volumes, so there is nothing to add to any command. Each instance has its own slots (a Compose project named `<instance>-slots`). Installing with `--no-sandbox` leaves run code off. The default backend outside the installer stays `docker`.
- The guest image has Python 3 with pypdf, pdfplumber, reportlab, python-docx, openpyxl, pandas, matplotlib and Pillow, plus pytest, ruff and mypy for testing and checking code; Node.js with TypeScript, plus vitest, jest, eslint and prettier for testing and checking code; bash and coreutils; git; gcc, g++ and make; and poppler-utils with poppler-data, and Tesseract with language data, for reading PDFs and images. More packages can be downloaded only as described under Package downloads below.
- Files you attach in chat reach the sandbox the same way as on Docker, and the sandbox never fetches anything: the server sends the file into the chat's workspace (under `/workspace/.aman/uploads`) and offers it to `run_code` under `/ingress`. The text of a PDF or image is read inside the sandbox and placed in the message, so any model sees it without running code. Gmail attachments use the same path: Aman fetches the file from Gmail, sends it into the chat's workspace, and reads it there. Text taken from a file is passed to the model as data, not instructions, and goes through the tool-output screen when one is configured. DOCX and other files are read with `run_code` (python-docx and friends).
- Languages: PDF text works in any language (poppler-data covers Chinese, Japanese and Korean PDFs). Scanned pages and images are read with Tesseract: it detects each page's script and reads the page with that script's languages only (Latin: English, Portuguese, Spanish, French, German, Italian, Dutch; Devanagari: Hindi, Marathi; Arabic; Cyrillic: Russian; Chinese, simplified and traditional; Japanese; Korean). `DOCUMENT_OCR_LANGUAGES` (default: the Latin set) is used when a page's script cannot be detected, for example a page with very little text. Setting it to a language the image lacks is ignored for that language, so OCR keeps working.
- `pnpm test:slots-live` (from the checkout, `--instance <name>` for an instance other than `main`) proves it end to end on an installed instance: it reads generated PDFs and scanned images in each script family through that instance's sandbox, prints a line per case, and ends with a verdict. The test images are drawn in a throwaway container, so nothing is installed on the host.
- `aman doctor` reports `attachments`: ok when a test file sent into the sandbox comes back and the sandbox has the PDF and OCR tools and every language above; a failure with `aman doctor sandbox --fix` otherwise; a warning when the sandbox was too busy to check. A status list (`aman doctor --local`) and the upgrade check skip this live test. An install from before this release gets the tools and languages from `install.sh upgrade`, which rebuilds the sandbox image (about 140 MB larger); a plain `install.sh` re-run also starts running slots again when the image was rebuilt.
- Files in a chat's `/workspace` persist between commands. Processes do not: a background process ends when its command returns.
- Optional toolchains: `pnpm sandbox:slots --add go`, `--add rust` or `--add java` (a comma list works) adds Go 1.27, Rust 1.99 (rustc and cargo) or OpenJDK 21 to the guest image and rebuilds it; `--remove` takes one out again, and the choice stays until you remove it. The Go and Rust archives are downloaded on the host and checked against checksums pinned in the repository; Java comes from the Ubuntu archive. Guests have no network of their own, so Go and Cargo dependencies come only through the package mirrors described below, and Maven cannot download dependencies at all.
- Approvals judge a path in `/workspace` by its name: `..` is collapsed and anything that ends up outside `/workspace` asks, as with a local sandbox. The server cannot follow symlinks inside a slot, so for shell commands the thing that actually keeps a command inside its workspace is the guest, which mounts only that chat's workspace; a silent (Tier 1) command is contained by the guest's view, not by its tier. The slot agent opens every path of its own file reads and writes without following links.
- Skills are not available on slots yet.
- Git works through the server. `git clone`, `fetch`, `pull`, `ls-remote` and `push` of github.com repositories run as one plain command; the server does the network part with your GitHub connector's token and hands the result to the sandbox as files. The token is never placed in a slot and a slot never contacts GitHub. A push shows an approval card naming the repository, the branch and the commits first, and then sends only those commits as a fast-forward: forced pushes, deleting branches, pushing tags and changes to submodules or `.gitmodules` are refused. Repositories over 100 MB are refused; use `git clone --depth 1`.

## Package downloads

A project often needs packages before its code can build or its tests can run. On the slots backend, those downloads go through Aman's own mirrors, never straight from the sandbox to the internet:

- The sandbox itself still has no network. When a chat works on a repository and you have allowed downloads for that repository, the package tools inside the sandbox (pip, npm, Go and Cargo) are pointed at Aman's mirrors for that command, and the slot passes only those download requests through. Each chat gets its own short-lived token, tied to that repository, so one chat cannot use another chat's allowance.
- The mirrors run on the host, one per package type, and each speaks its registry's own standard mirror protocol: the simple index for Python packages, the npm registry read interface, the Go module proxy protocol, and the cargo sparse index. A mirror only ever downloads. It has no way to accept a publish or an upload, and it refuses anything that is not a download request, so `npm publish`, `cargo publish` and `twine upload` from the sandbox always fail.
- Each mirror fetches only from its own package site list (PyPI, the npm registry, the Go module proxy and checksum database, and the crates index and file host). If a package's own metadata names a file somewhere else, or an answer tries to redirect somewhere else, the mirror refuses. The public package sites can log these requests, including package names and this computer's address, exactly as they would for a normal install on this computer.
- A project that needs a package from a git address cannot be served yet, and the command stops with that message instead of trying.
- Downloads are kept in a cache on the host so repeat installs are quick. One file may be at most 1 GB and the whole cache at most 10 GB; the oldest files are removed first when the cache fills. Every download is written to the server log with the package, the version, the repository and the chat that asked, and when.
- Allowing downloads is per repository and stays off until you allow it (the repositories API carries the setting as `package_downloads_allowed`). Taking the allowance back stops new downloads on the next command and ends any live mirror token for that repository at once.

## Enabling the sandbox on an agent

The sandbox is **off by default** per agent. Turn it on in the agent builder when you need code execution, skills, or Code Mode. You can also set `config.sandbox.enabled` in the [agent spec](/create-agent/overview#config) when creating agents via the SDK.

Optional controls:

- **File downloads** — let users download files the agent produces (on by default in the chat UI).

### Downloads outlive the sandbox

A sandbox is stopped a few minutes after its turn finishes and deleted later, but a file the agent
declared in its `sandbox_artifacts` block is copied to host storage as soon as that turn
completes, so the download still works after the sandbox itself is gone. A file over
`SANDBOX_FILE_MAX_BYTES_FOR_DOWNLOAD` is not copied; downloading it later reports that it was not
kept, with the size involved. A turn still in progress has no persisted copy yet, so its download
route falls back to the live sandbox until the turn finishes.

## PDF and image text extraction

The Aman sandbox includes local PDF and OCR tools. As soon as the supported PDF and image
attachments in an upload are staged, their text is extracted in a single batched call and placed
directly in the message the model receives, using embedded PDF text when available and
OCR (in the languages listed above) for image-only PDF pages and for uploaded images, so any model, including a
text-only one, sees the content without deciding to call a tool for it. Batching the call keeps
the page, character, and byte caps shared across the whole upload and keeps only one OCR pipeline
running in the sandbox at a time. Extraction runs inside the sandbox (on slots, inside the slot's guest, which has no network) and does not send document
contents to an external OCR service. Very long documents are truncated in the message with a
note; the `extract_document_text` tool re-extracts a file on demand for page- and
line-addressable provenance, or for the remainder of a truncated document. Attachments of an
unsupported type get no extraction note; the upload announcement already lists them and the
model can read them with its own file tools.

## Repository-bound coding sessions

A session can be bound to one registered repository and an absolute checkout path. On every turn and thread rebuild, the harness verifies that checkout and gives the agent its repository ID, current branch, HEAD commit, working directory, and the IDs of confirmed build, test, and verification commands.

Confirmed commands are host-owned. The agent invokes a command by ID, while the harness supplies the exact command, working directory, purpose, and timeout. A missing command or invalid checkout fails clearly instead of falling back to a guessed command or directory.

To reduce first-run setup friction, the harness can propose commands from four bounded repository files after a checkout is bound:

- `package.json` scripts named `build`, `test`, or `verify`
- explicit `Build:`, `Test:`, or `Verify:` command declarations in `AGENTS.md`
- `pyproject.toml`: the pytest, Ruff and mypy tool tables, and explicit scripts in the Hatch default environment
- `Makefile` targets named `build`, `test`, `lint`, `check`, or `verify`

Proposals are never executable. Review and confirm a proposal before it enters the command registry. The registry remains the source of truth even if the source file later changes.

A successful `verify` command can authorize a separately approved commit in the next continuation turn. That authorization is single-use and is bound to the tenant, session owner, session, repository revision, provider sandbox, absolute checkout, and the exact Git state captured after verification. Any intervening workspace mutation invalidates it.

Verification authorization is process-local in this release. It survives normal turn reconstruction in one running server, but a server restart or replica hop loses it and the commit fails closed by asking for verification again. The runtime exposes an asynchronous receipt-store boundary so deployments can replace that owner with durable, cross-replica storage without changing sandbox admission.

The repository endpoints live under `/api/v1/repositories`; session binding lives under `/api/v1/sessions/{session_id}/repository`.

### Working on a repo from a chat

The chat has a "Work on a repo" button. The person picks one of their GitHub repos (read through the GitHub connector attached to the chat) or pastes a GitHub address, and picks a branch. Aman then asks, in the chat, to clone the repo into the sandbox workspace; the clone goes through the usual host git path, so it asks for approval like any other clone. When the clone finishes, the chat is bound to the checkout, the chat shows the repo and branch it is working on, and the command proposals found in the repo files appear in one card for the person to confirm or dismiss. A repo larger than 100 MB cannot be opened yet, and without a GitHub connector the picker says to connect GitHub first, under Connectors. Public repos can be opened by address without a connector.

## Structured file edits

`apply_patch`, `replace_text`, and `write_file` are the sandbox's structured file-edit tools.
`apply_patch` accepts a Git-format unified diff, or OpenAI's `apply_patch` envelope format
(`*** Begin Patch` / `*** Update File:` / `*** End Patch`), converted to a git diff before
validation; a body that omits the envelope but still opens with a file operation header is
accepted the same way.

Every multi-line text field these three tools take (`write_file`'s `content`, `apply_patch`'s
`patch`, `replace_text`'s `old_text` and `new_text`) also accepts a sibling `<field>_lines`
array: one array element per line, blank lines as empty strings, joined with `"\n"` before
anything downstream sees it. Exactly one of each pair is required. Some models reliably produce
one array element per line but unreliably produce embedded newlines inside a single JSON string
value, so the array form is the reliable way for those models to send multi-line content; the
plain string form keeps working unchanged for models that handle it correctly.

Every call to these three tools passes through one argument-normalisation layer before
validation: a leading byte-order mark or a surrounding markdown code fence is stripped, CRLF
line endings are normalized to LF, an absolute path inside the bound repository is rewritten as
cwd-relative, and Unicode hyphen or no-break-space characters inside a path are normalized to
their ASCII form. A rejection that survives normalisation states what was received and what was
expected, so a retrying model has something concrete to correct.

`write_file` creates a new file only; it never overwrites one. It creates any folders on the path
that do not exist yet, so a new project can be written file by file. It never follows a link: a path
through a file or a link is refused with a plain message naming it.

## Coding in the sandbox

The shell tool runs repository and workspace commands. It does not run inline code
(`python3 -c`, `node -e` and the like), a script by path, or any other Python module; those go
through `run_code`. Building and testing a Python project is the exception: `python3 -m pytest`,
`python3 -m pip`, `python3 -m venv` and `python3 -m unittest` run in the shell.

A reply can do as much work inside the sandbox workspace as the task needs: writing and editing
files, running code, builds and tests. Two limits still apply to every reply:

- At most five actions that can reach past the sandbox, such as sending something, changing
  something in a connected app, or a `git push`. On a sandbox with network access, every command
  that does more than look at files counts too, builds and test runs included, because any of them
  could reach the internet; on an offline sandbox (sandbox slots) they do not. An action counts once
  it was tried, even if it answered with an error; one that was refused or never sent does not, and
  reads never do.
- A step budget of 8 model steps, with one step handed back for each step that saved a file in the
  sandbox (or wrote to a space), up to 12 more. When it runs out, Aman says what it changed and what
  is left, and you can ask it to continue.

The same call made twice with nothing changed in between is skipped as a repeat, so running the
tests again after a file edit works, and running them twice in a row does not. An action that can
reach past the sandbox is never repeated in one reply, whatever changed in between, and is not
retried after an error: it may have gone through anyway, so Aman checks and tells you instead.

If a skill cannot be copied into the sandbox, Aman says so once per chat, on the first tool result
that follows, and keeps working without it.

## Lifecycle

- Provisioned on demand when the agent needs code, files, skills, or Code Mode.
- Reused across turns in the same session (files persist).
- Stopped after idle time, then archived and eventually deleted per the provider settings.

## Credential safety

- Model and MCP credentials stay in the harness.
- MCP calls from [Code Mode](/key-features/code-mode) scripts are bridged back to the harness — the sandbox never holds those tokens.
