The sandbox is where the code your assistant writes runs. It also runs file and shell work. It is kept apart from the Aman server and from the rest of your computer.

Code Aman writes runs in a sealed sandbox with no internet access, a fresh one for every run. If the sandbox isn't available, code doesn't run.

## What it is

The installer sets up the sealed sandbox for every Aman instance. Each time the assistant runs code, Aman starts a fresh, isolated sandbox for that one run. The sandbox has no network, so code in it cannot reach the internet or your own network.

- Before every run, the sandbox checks its own safety limits. If a check fails, it refuses to run the code.
- Files the assistant saves in a chat's `/workspace` folder are kept between runs of that chat. Nothing else carries over: a program left running ends when its run ends.
- Each run has limits on time, memory and disk space. **Settings → Sandbox** lists them.
- The sandbox has Python 3 (with PDF, Word, Excel, data and chart libraries), Node.js with TypeScript, a shell, git, and a C and C++ compiler. Packages cannot be downloaded.
- Git works through the Aman server. Cloning, fetching and pushing github.com repositories run as one plain command, and a push asks for your approval first. Your GitHub token never enters the sandbox.
- Skills are not available in the sealed sandbox yet.

If the sandbox is not available, code does not run and Aman says why. It never switches to a less safe way of running code.

## Check it

- Open **Settings → Sandbox**. It shows "Sealed sandbox: ready", or the plain reason it is not.
- Or run this on the computer where Aman is installed:

```bash
aman doctor sandbox
```

When the sandbox is not ready, it ends with: "Code won't run until the sandbox is ready. Run: aman doctor sandbox --fix".

## Fix it

Run this on the computer where Aman is installed:

```bash
aman doctor sandbox --fix
```

It rebuilds and restarts the sandbox and checks it again. It asks before anything that needs administrator rights. Then press **Re-check** in **Settings → Sandbox**.

Aman needs Docker as its engine (Docker Desktop on Mac and Windows). If Docker is not running, start it first. On Linux, the installer can also make Docker start at boot, so the sandbox comes back after a restart.

## How the sandbox fits with the agent

There are two common patterns for combining agents with sandboxes:

| Pattern | Where the agent runs | Trade-off |
| --- | --- | --- |
| **Agent in sandbox** | Inside the sandbox image | Sandbox is provisioned even for the simplest request; secrets must live in the sandbox; updates mean rebuilding images |
| **Sandbox as tool** | Outside, on the server | Sandbox is provisioned on demand when needed; secrets stay in the harness; sandbox is only for exec/files |

TrueForge uses **sandbox as tool**: the agent loop and credentials stay in the harness; the sandbox only runs code, file, and shell operations.

That means:

- Model and MCP credentials never enter the sandbox.
- Conversation state survives a sandbox crash.
- A sandbox is created only when the agent actually needs one — simple Q&A and MCP calls incur no sandbox cost.

## Enabling the sandbox on an agent

The sandbox is **off by default** per agent. Turn it on in the agent builder when you need code execution, skills, or Code Mode. You can also set `config.sandbox.enabled` in the [agent spec](/create-agent/overview#config) when creating agents via the SDK.

Optional controls:

- **File downloads** — let users download files the agent produces (on by default in the chat UI).

### Downloads outlive the sandbox

A sandbox is stopped a few minutes after its turn finishes and deleted later, but a file the agent
declared in its `sandbox_artifacts` block is copied to host storage as soon as that turn
completes, so the download still works after the sandbox itself is gone. A file over
`SANDBOX_FILE_MAX_BYTES_FOR_DOWNLOAD` is not copied; downloading it later reports that it was not
kept, with the size involved. A turn still in progress has no persisted copy yet, so its download
route falls back to the live sandbox until the turn finishes.

## PDF and image text extraction

The Aman sandbox runtime includes local PDF and OCR tools. As soon as the supported PDF and image
attachments in an upload are staged, their text is extracted in a single batched call and placed
directly in the message the model receives, using embedded PDF text when available and
English-language OCR for image-only PDF pages and for uploaded images, so any model, including a
text-only one, sees the content without deciding to call a tool for it. Batching the call keeps
the page, character, and byte caps shared across the whole upload and keeps only one OCR pipeline
running in the sandbox at a time. Extraction runs inside the sandbox and does not send document
contents to an external OCR service. Very long documents are truncated in the message with a
note; the `extract_document_text` tool re-extracts a file on demand for page- and
line-addressable provenance, or for the remainder of a truncated document. Attachments of an
unsupported type get no extraction note; the upload announcement already lists them and the
model can read them with its own file tools.

## Repository-bound coding sessions

A session can be bound to one registered repository and an absolute checkout path. On every turn and thread rebuild, the harness verifies that checkout and gives the agent its repository ID, current branch, HEAD commit, working directory, and the IDs of confirmed build, test, and verification commands.

Confirmed commands are host-owned. The agent invokes a command by ID, while the harness supplies the exact command, working directory, purpose, and timeout. A missing command or invalid checkout fails clearly instead of falling back to a guessed command or directory.

To reduce first-run setup friction, the harness can propose commands from two bounded repository files after a checkout is bound:

- `package.json` scripts named `build`, `test`, or `verify`
- explicit `Build:`, `Test:`, or `Verify:` command declarations in `AGENTS.md`

Proposals are never executable. Review and confirm a proposal before it enters the command registry. The registry remains the source of truth even if the source file later changes.

A successful `verify` command can authorize a separately approved commit in the next continuation turn. That authorization is single-use and is bound to the tenant, session owner, session, repository revision, provider sandbox, absolute checkout, and the exact Git state captured after verification. Any intervening workspace mutation invalidates it.

Verification authorization is process-local in this release. It survives normal turn reconstruction in one running server, but a server restart or replica hop loses it and the commit fails closed by asking for verification again. The runtime exposes an asynchronous receipt-store boundary so deployments can replace that owner with durable, cross-replica storage without changing sandbox admission.

The repository endpoints live under `/api/v1/repositories`; session binding lives under `/api/v1/sessions/{session_id}/repository`.

## Structured file edits

`apply_patch`, `replace_text`, and `write_file` are the sandbox's structured file-edit tools.
`apply_patch` accepts a Git-format unified diff, or OpenAI's `apply_patch` envelope format
(`*** Begin Patch` / `*** Update File:` / `*** End Patch`), converted to a git diff before
validation; a body that omits the envelope but still opens with a file operation header is
accepted the same way.

Every multi-line text field these three tools take (`write_file`'s `content`, `apply_patch`'s
`patch`, `replace_text`'s `old_text` and `new_text`) also accepts a sibling `<field>_lines`
array: one array element per line, blank lines as empty strings, joined with `"\n"` before
anything downstream sees it. Exactly one of each pair is required. Some models reliably produce
one array element per line but unreliably produce embedded newlines inside a single JSON string
value, so the array form is the reliable way for those models to send multi-line content; the
plain string form keeps working unchanged for models that handle it correctly.

Every call to these three tools passes through one argument-normalisation layer before
validation: a leading byte-order mark or a surrounding markdown code fence is stripped, CRLF
line endings are normalized to LF, an absolute path inside the bound repository is rewritten as
cwd-relative, and Unicode hyphen or no-break-space characters inside a path are normalized to
their ASCII form. A rejection that survives normalisation states what was received and what was
expected, so a retrying model has something concrete to correct.

## Lifecycle

- Provisioned on demand when the agent needs code, files, skills, or Code Mode.
- Reused across turns in the same session (files persist).
- Stopped after idle time, then archived and eventually deleted per the provider settings.

## Credential safety

- Model and MCP credentials stay in the harness.
- MCP calls from [Code Mode](/key-features/code-mode) scripts are bridged back to the harness — the sandbox never holds those tokens.

## For developers

- The sandbox is made of four hardened slot containers. Each runs a small agent as PID 1, and every call starts in a fresh gVisor guest started with `--network=none`. The agent re-checks its own isolation (user, capabilities, no-new-privileges, seccomp, read-only root, loopback only, no Docker socket, cgroup limits, AppArmor where the host has it, a workspace on its own disk, and a working gVisor guest) before each call and refuses the call if any check fails. The server checks the same report independently.
- The server holds no Docker socket. It reaches a slot through a Unix socket in a small control volume that only the server mounts. Keep the control volumes out of every other container.
- `SANDBOX_BACKEND` defaults to `slots`; `SANDBOX_SLOTS` (1 to 4, default 4) and `SANDBOX_SLOTS_DIR` (the control directory) go with it. The installer's instance compose file sets them and mounts the control volumes. Installing with `--no-sandbox` leaves code off. A server started from a checkout (`pnpm dev`) has no slots to reach, so code does not run there until you set up slots with `pnpm sandbox:slots`, which runs the same code as the installer.
- `SANDBOX_BACKEND=docker` is the legacy backend. It stays as an explicit developer opt-in until it is removed, and it is the only setting that uses the Daytona provider and the local adapter described elsewhere in these docs. It is never a fallback for the default.
- Each chat's workspace has a size limit (2 GB by default, `SANDBOX_SESSION_DISK_MB`), enforced while a command runs. On Linux, setup also gives each slot a fixed-size disk of its own (16 GB by default, `--disk-gb` to change it), so a runaway command can fill only its own slot's disk. Setup asks before it creates the disk files under `/var/lib/aman-slots` and adds them to `/etc/fstab`. On Docker Desktop and WSL2 there is no per-slot disk; the virtual machine's disk bounds the workspaces. `installer/install.sh instance remove <name> --purge-data` removes the instance's disk files with its data (`pnpm sandbox:slots --down --purge` does it for a checkout-only setup).
- A command can use at most 128 processes. Allowed environment variables for a command are a short list (locale, terminal, language runtime and git settings); others are refused with their names.
- Optional toolchains: `pnpm sandbox:slots --add go`, `--add rust` or `--add java` (a comma list works) adds Go 1.27, Rust 1.99 (rustc and cargo) or OpenJDK 21 to the guest image and rebuilds it; `--remove` takes one out again. Guests stay offline, so `go get`, `cargo add` and Maven cannot download dependencies.
- Approvals judge a path in `/workspace` by its name: `..` is collapsed and anything that ends up outside `/workspace` asks. The server cannot follow symlinks inside a slot, so for shell commands the guest, which mounts only that chat's workspace, is what keeps a command inside its workspace. The slot agent opens every path of its own file reads and writes without following links.
- Git runs through the server: it does the network part with your GitHub connector's token and hands the result to the sandbox as files. A push shows an approval card naming the repository, the branch and the commits first, and then sends only those commits as a fast-forward. Forced pushes, deleting branches, pushing tags and changes to submodules or `.gitmodules` are refused. Repositories over 100 MB are refused; use `git clone --depth 1`.
