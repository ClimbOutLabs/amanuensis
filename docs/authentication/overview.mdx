---
title: 'Setup Login'
description: 'Aman signs people in with its own sign-in service; standalone always requires it.'
---

Aman uses its own sign-in. Outside sign-in services are not supported. Login is **mandatory in standalone mode** (the server refuses to start without it) and optional in hosted mode. For local development run `pnpm dev:login`, which starts Aman's sign-in service in Docker and prints the `OIDC_*` lines for `packages/trueforge/.env`. The installer sets the same service up for you.

## Choose your mode

| Mode | When to use | What users see |
| --- | --- | --- |
| **No login** (hosted default) | Hosted evaluation on a network you fully trust; not available in standalone | No login screen; everyone is a single shared local admin |
| **Login** | Standalone, or any shared deployment | Sign-in with Aman's sign-in service |

<Note>
  Standalone / local mode requires login and refuses to start without it. Hosted deployments (Docker Compose
  or Helm) can run without login, as a shared admin identity. An http sign-in address is accepted only on a loopback host.
  Local mode is intended for personal use on your own machine — it is not a production or internet-facing setup.
  We cannot take responsibility for data loss or unauthorized access if it is used beyond that.
</Note>

## Option A — leave login off

The hosted default (`STANDALONE=false`; standalone always needs login). Do **not** set any `OIDC_*` variables, run TrueForge as usual ([Quickstart](/quickstart)), and open the UI — there is no login screen, and Settings and chat are available immediately.

<Warning>
  Use this only on `localhost` or behind network controls you trust. On a public host, anyone who can reach the server gets full admin access under one shared identity.
  The Helm chart defaults to this mode (`configs.oidc.enabled: false`) plus a well-known bundled Postgres password and Redis without auth — see the [chart README](https://github.com/truefoundry/trueforge/blob/main/charts/trueforge/README.md#dev-defaults-read-before-exposing) before exposing a release.
</Warning>

## Option B — turn login on

The installer and the Compose `login` profile ([Turn on login](/quickstart#turn-on-login)) set Aman's sign-in service up and fill in the values below. To set it up by hand, set these variables together; partial config fails startup.

| Variable | Required | Purpose |
| --- | --- | --- |
| `PUBLIC_BASE_URL` | Yes | Public origin users see (no trailing path) |
| `OIDC_ISSUER_URL` | Yes | Address of Aman's sign-in service; its path is `/dex`. Any other address is refused at startup. |
| `OIDC_CLIENT_ID` | Yes | Client ID |
| `OIDC_CLIENT_SECRET` | Yes | Client secret |
| `OIDC_ALLOWED_EMAILS` | Standalone: yes | Comma-separated allowlist of exact emails and/or `*` globs, matched case-insensitively. Standalone requires exactly one address with no `*`: the owner's. |
| `OIDC_USER_REFERENCE_CLAIM` | No (default `sub`) | Claim used as the user id for session ownership |
| `OIDC_USER_DISPLAY_NAME_CLAIM` | No (default `name`) | Claim used as the user's display name |
| `OIDC_USER_ROLE_CLAIM` | No (default `groups`) | Claim inspected for admin membership |
| `OIDC_ADMIN_ROLE_VALUE` | No (default `admin`) | Exact string that grants `admin` (case-sensitive) |
| `OIDC_SCOPES` | No (default `openid,profile,email`) | Scopes for the authorize request |

Standalone accepts only ID tokens with `email_verified: true`; Aman's own sign-in always provides it. Keep `OIDC_CLIENT_SECRET` in a secret store and never commit it.

With Docker Compose these go in `packages/trueforge/.env`. With Helm they go under `configs.oidc` (`issuerUrl`, `clientId`, `clientSecret`, `allowedEmails`, and so on); see the [chart README](https://github.com/truefoundry/trueforge/blob/main/charts/trueforge/README.md#oidc) for the values shape.

Open the UI and you are sent to the sign-in page. After sign-in, admins see **Settings** and non-admins do not. Sign out and back in after any role change.

## Roles: admin vs user

Each signed-in person maps to exactly one role, decided by the role claim in their ID token.

| Role | Who | Can chat & use agents | Can change Settings |
| --- | --- | --- | --- |
| **admin** | Role claim contains `OIDC_ADMIN_ROLE_VALUE` | Yes | Yes — models, connectors, skills, sandbox |
| **user** | Everyone else who can sign in | Yes | No — Settings hidden |

<Note>
  Two current limitations:
  - **Session history is owner-only** — admins are not global session superusers today.
  - **The [Agent Library](/agent-library) is shared** — agents created by anyone are visible to everyone on the instance.
</Note>

To call the HTTP API or SDK against a server with login enabled, pass an ID token — see [Get a token and connect](/api/quickstart#get-a-token-and-connect).

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| Refused at startup with "Aman uses its own sign-in" | `OIDC_ISSUER_URL` does not point at Aman's sign-in service (path `/dex`) |
| Login works but everyone is `role: "user"` | Role claim missing from the ID token, wrong claim name, or admin value mismatch (case-sensitive) |
| SDK returns `401` | Login is on and the request has no [ID token](/api/quickstart#get-a-token-and-connect) or session cookie |
| "Only the owner can sign in to this instance." | The person is not the one address in `OIDC_ALLOWED_EMAILS` |
| Sign-in fails with `login_failed` / APIs return `401` | The `email` claim is outside `OIDC_ALLOWED_EMAILS`, is missing, or `email_verified` is not `true` |

## Security checklist

- Store `OIDC_CLIENT_SECRET` in a secret manager; never commit it.
- Do not expose a no-login deployment on the public internet.
- Register the exact callback URL your users hit (scheme + host).
