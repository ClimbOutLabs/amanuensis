## What this is

The installer sets up Amanuensis on your own machine with one command and a few prompts. Docker is the only prerequisite. The installer builds the app and its helpers locally, starts one stack per person, and gives each person a private login. Nothing is uploaded anywhere, and nothing is pushed to any registry.

One instance serves one person. If two people in the same household need it, they run two instances.

## What you need

- A computer with Docker: Docker Engine with Compose v2 or newer on Linux, or Docker Desktop on macOS. On Windows, run inside WSL2; native Windows is not supported. Rootless Docker and Podman are not supported.
- 10 GB of free disk space, and on Linux 20 GB more under `/var/lib` for the sandbox's slot disks (they are sparse and use real space only as code runs).
- Nothing else: no Node.js is needed. For the sandbox setup the installer downloads a pinned Node.js from nodejs.org (about 35 MB, checked against a SHA-256 pinned in the repository) into `~/.amanuensis/runtime/node`, and uses it only to run that setup. `--use-host-node` uses your own Node.js 22.14 or newer instead; `--no-sandbox` skips all of it.
- Docker needs at least 6 GB of memory for the first build. The installer blocks below 6 GB and warns between 6 and 8 GB; 8 GB or more is recommended.
- Your own model: the address of a model server you already run, for example `http://host.docker.internal:11434/v1`. API keys are entered in the app afterwards, not in the installer. The installer never scans your machine for models; you type the endpoint yourself.
- A git checkout of this repository. The installer runs from the checkout and builds the images from source.

## The one command

From the repository root:

```bash
installer/install.sh
```

The installer works in phases and shows you a printed plan before changing anything:

1. **Preflight (read-only).** Checks the OS, architecture, Docker, Compose v2 or newer, and free disk. On supported Linux without a working Engine, it offers to install Docker for you.
2. **Plan and confirmation.** Prints each step as done, will do, or needs root, then asks to continue. `--yes` skips the prompt; `--dry-run` prints the plan and stops without changing anything.
3. **Downloads.** Fetches third-party base images by pinned digest and the model weight files listed in the printed plan.
4. **Images.** Downloads the pinned Node.js runtime for the sandbox setup, builds the app and helper images locally from the checked-out source, then the sandbox slot image (its build log goes to `~/.amanuensis/state/sandbox.log`; the terminal shows one progress line).
5. **Machine services.** Starts the shared speech-to-text service.
6. **First instance.** Prompts for the instance details, starts the four sandbox slots (asking before the `sudo` steps on Linux: installing the AppArmor profile in `/etc/apparmor.d` and loading it, creating the slot disks, and enabling Docker at boot if it is not), then starts your stack connected to them.
7. **Doctor and summary.** Runs the health checks, then proves the sandbox: every slot's safety checks and a real call from the app to the slots. Prints your URLs, versions, backup location, and next steps.

### What it asks

For the first instance it prompts, with defaults in brackets:

- Instance name `[main]`
- Owner email
- Address you will use from other devices (press Enter to use this computer only)
- If you give a public address: address for the sign-in service (its own https address, never a path of the first one)
- Token Factory key (optional; typed hidden, never echoed). Giving one makes Nebius Token Factory the default model and skips the next question
- Model server address (optional; skipped when you gave a Token Factory key)
- Password (typed twice, never echoed; at least 8 characters, at most 72 bytes)

Everything else is generated: ports, secrets, and the login setup.

### What it downloads, and how big

The printed plan lists every first-run download with its approximate size, including the speech model weights and the embedding model. Expect a few gigabytes in total on a first install, mostly model weights and container image layers. The installer downloads over HTTPS and never pipes anything to a shell.

### Flags you may not have seen

- `--confirm-name NAME`: with `--purge-data`, the instance name typed in advance so it does not prompt.
- `--password-stdin`: read the owner password from the first line of stdin, before any prompt.
- `--token-factory-key-stdin`: read the Token Factory key from stdin (the line after the password when `--password-stdin` is also given). The key is never accepted as a command-line value, and it is written only to the instance `.env` (mode 600). See [Feeding the Token Factory key safely](#feeding-the-token-factory-key-safely). On an instance that already exists it replaces the key and restarts the app.
- `--token-factory-model ID`: the Token Factory model to use (default `nvidia/nemotron-3-super-120b-a12b`).
- `--token-factory-daily-cap N`: stop answering after N Token Factory tokens per day (default: no cap).
- `--tls local|off`: https on your network with a certificate from an authority made on this computer (the default), or plain http. See [First login](#first-login).
- `--tls caddy`: serve `--public-url` and `--login-url` over https with Caddy on this computer. See [Https with Caddy](#https-with-caddy).
- `--tls-root`: let the installer run the printed root steps for `--tls caddy` (and for the Caddy removal of `instance remove`) without asking. `--yes` alone never uses sudo.
- `--public-ip ADDRESS`: this computer's public IPv4 address for the DNS check of `--tls caddy`, instead of asking a lookup service.
- `--install-docker`: let the installer run the printed root steps to install Docker Engine (Debian, Ubuntu).
- `--add-docker-group`: let the installer add your user to the docker group (needs sudo).
- `--sandbox-root`: let the installer run the printed root steps for the sandbox (AppArmor profile, slot disks) without asking. `--yes` alone never uses sudo.
- `--no-sandbox`: install without the gVisor sandbox. Run code stays off.
- `--use-host-node`: run the sandbox setup on this computer's Node.js 22.14 or newer instead of downloading a pinned copy.
- `--print-root-steps`: print the root steps for installing Docker and stop.
- `--print-network`: print every host the installer may contact and stop.
- `--print-proxy-requirements`: print what a reverse proxy in front of an instance must do and stop.

### Feeding the Token Factory key safely

Type the key at the hidden prompt, or read it hidden into a shell variable and hand it over on stdin. A command-line value or `echo KEY |` would put the key in your shell history and in the process list, so the installer refuses the first and these docs never use the second.

```bash
read -rs KEY                                   # type or paste the key; nothing is shown
printf '%s\n' "$KEY" | installer/install.sh --yes --token-factory-key-stdin
unset KEY
```

`printf` is a shell builtin, so the key never appears as an argument of any process. With `--password-stdin` as well, the password is the first line and the key the second.

To rotate the key, run the same command again on the machine. For an instance that already exists, the installer replaces `NEBIUS_API_KEY` in the managed block of its `.env` (mode 600, written atomically), prints `Token Factory key updated; restarting the app`, and recreates the app container. Add `--name <instance>` when there is more than one instance and none is called `main`.

### Fresh Docker installs on Linux

If the installer just installed Docker for you, it finishes the same run without making you sign out first (it runs the Docker commands through a group wrapper for that run only) and prints a sign-out note. Sign out and back in afterwards so your shell picks up the `docker` group.

## First login

When the installer finishes, it prints a short table with the addresses to open. By default Aman answers at every address this computer has on a private network (`127.0.0.1`, `localhost`, its LAN address, its Tailscale address, its host name, `<name>.local` and its MagicDNS name), and signing in works from each of them: open any one in a browser, from this computer or another device, and sign in with the owner email and the password you set. The sign-in service itself stays on this computer; the app passes its pages through under its own address.

On a home network the app is served over https at port 8443 (the next free port), with a certificate from an authority the installer makes on this computer: nothing needs administrator rights or a package on the host, and a pinned web front end in the instance's own project serves it. The plain port (8791) only sends devices to https and serves one short page, `/trust`, with the certificate for each kind of device (an iPhone profile and a certificate file for Android, Mac and Windows). Each device trusts the authority once, with the steps on that page; the ending of the install prints the link and a code a phone can scan. The authority lasts ten years, the certificate renews with the daily backup (`aman doctor tls` checks it, `aman doctor tls --fix` renews it), and the authority's key is part of every backup so a restored computer keeps the one your devices trust. `--tls off` keeps plain http, where the password is not encrypted on the way and only Tailscale protects it. A public address is never used over plain HTTP: for access from the internet use `--public-url`, `--login-url` and `--tls caddy`. `--address <name or private address>` (repeatable) adds a name this computer cannot work out itself, and `--local-only` keeps the app on `127.0.0.1` alone. If this computer gets a new address later, `aman doctor network` says so and `aman doctor network --fix` adds it.

Your password is never stored anywhere. The installer hashes it once and keeps only the hash.

## Adding people

Each person gets their own instance with their own ports, secrets, data, and login.

```bash
installer/install.sh instance add <name>    # create and start another instance
installer/install.sh instance list          # show name, ports, URL, owner, and state
installer/install.sh instance remove <name> # stop and remove it; data volumes are kept
```

`instance add` prompts for the new owner's details, picks free loopback ports by testing binds (override with `--port` and `--login-port`), generates fresh secrets, and waits for the instance to answer its health check.

`instance remove` stops the stack and its sandbox slots and deletes their containers and config, but keeps the data volumes. To delete the data too:

```bash
installer/install.sh instance remove <name> --purge-data
```

This asks you to type the instance name to confirm (or pass it in advance with `--confirm-name`). The installer never deletes a volume otherwise.

An instance served with `--tls caddy` also has a site file in `/etc/caddy/aman.d`. `instance remove` prints the root steps that delete it and reload Caddy (`sudo rm -f /etc/caddy/aman.d/<name>.caddyfile`, then `systemctl reload-or-restart caddy`) and runs them after you answer yes or pass `--tls-root`. Without consent the instance is still removed, a warning says that Caddy keeps serving its names, and the steps stay yours to run.

## Using it from other devices

The first run is local only. To reach an instance from another device on your network, you put your own reverse proxy in front of it. The installer configures nothing outside the machine; it only prints what your proxy must satisfy:

- One HTTPS origin per instance, plus one HTTPS origin per login server. Never a path prefix.
- The `Host` header forwarded to the instance.
- Streaming responses passed through unbuffered.
- Every name resolvable from inside the containers, not just from your browser.

When you set a public URL, that instance's URL and its login issuer switch to HTTPS behind your proxy. An HTTP login issuer is only allowed for loopback addresses.

### Https with Caddy

On an Ubuntu or Debian machine with a public address you can let the installer be that proxy:

```bash
installer/install.sh --public-url https://<app-name> --login-url https://<login-name> --tls caddy
```

Create two DNS A records first, one for each name, both pointing at this machine's public address. The installer then:

1. Checks that both names resolve to this machine's public address. If not, it says which one does not and stops before anything is requested from Let's Encrypt.
2. Prints the root steps and runs them only after you answer yes (or pass `--tls-root`): install Caddy from the Ubuntu package archive, replace the package's default `:80` site with a main Caddyfile that only imports `/etc/caddy/aman.d` (the original is kept once as `/etc/caddy/Caddyfile.aman-orig`, and the admin API stays on localhost), check the new site file together with the other instances' files before it replaces the previous one, and reload Caddy. A file Caddy rejects never replaces a working one. No container image is pulled for Caddy.
3. Lets the app reach the login name through this machine (an `extra_hosts` entry), so sign-in does not depend on the machine reaching its own public address.

Both names are served with `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy` and `X-Frame-Options: DENY`, each added only when the app or the login service did not send it. The installer changes no firewall. Open only TCP 443 to the internet, plus SSH from your own address; port 80 can stay closed. The names are only ever given on the command line or at the prompts; nothing in the installer or its files contains a domain.

`aman doctor` then also tries the public health address and the login discovery document over https, and (with a Token Factory key) the model.

## Doctor

The doctor binary is not on your PATH. It lives at `~/.amanuensis/bin/aman`. Either run it with the full path, or add the folder to your PATH:

```bash
export PATH="$HOME/.amanuensis/bin:$PATH"   # add to your shell profile to keep it
```

Doctor checks the whole setup and tells you exactly what to do about anything it finds:

```bash
aman doctor                 # everything: machine plus every instance
aman doctor --instance main # one instance only
aman doctor --deep          # raises the probe timeout to 30 seconds
aman doctor --json          # machine-readable output
aman doctor sandbox         # sandbox: every slot's safety checks, then a real call through the app
aman doctor sandbox --fix   # repair the sandbox: rebuild the image, reload AppArmor, recreate disks, restart the slots
aman doctor network         # are all this computer's addresses listed for sign-in?
aman doctor network --fix   # add the new ones and restart the instance
```

Each check reports one of four states:

- **ok**: healthy, nothing to do.
- **warn**: works today, needs attention soon.
- **fail**: broken; the check prints the exact command that fixes it.
- **off**: intentionally disabled; silent.

The command exits 0 when nothing fails, 1 when anything fails, and 2 on a usage error. `aman doctor` is read-only; to repair, rerun the installer. The one repair it does itself is `aman doctor sandbox --fix`, which asks before any `sudo` and runs on the same pinned Node.js (or your own, if you installed with `--use-host-node`).

Common checks and what they mean:

| Check         | Fails when                                      | Fix                                                             |
| ------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| docker        | Engine not answering, Compose v2 or newer missing     | Start the daemon; on Linux, accept the installer's Docker offer |
| docker_memory | Docker has less than 6 GB of memory             | Raise it in Docker Desktop under Settings, Resources, Memory. On Linux, free up memory or add swap |
| images        | A pinned image is missing locally               | Rerun the installer                                             |
| service       | An instance's containers are unhealthy          | The check prints the start command                              |
| login         | The login server is unreachable                 | Wait a few seconds on first start, then check the proxy hints   |
| database      | SQLite is not writable or migrations are behind | The check prints the start command                              |
| disk          | Under 2 GB free is a fail                       | Free space or prune unused images                               |
| clock         | Machine clock disagrees with the containers     | Enable automatic time sync                                      |
| run_code      | The app cannot reach the sandbox slots, or a slot fails a safety check | Run `aman doctor sandbox --fix`                   |
| model         | Token Factory refuses the key, does not list the model, or the model answers a tool call without `tool_calls` | The check says which; fix `NEBIUS_API_KEY` or `TOKEN_FACTORY_MODEL` in the instance `.env` and restart |
| public_url    | The public https address does not answer the health check (https instances only) | Check DNS, Caddy (`sudo systemctl status caddy`) and port 443 |
| public_login  | The login discovery document is not served over https with the configured issuer | Same as above; the issuer in the instance `.env` must be the address Caddy serves for sign-in |

A fresh install never warns about backups until the first backup exists.

## Backup and upgrade

Backups stay on your machine, unencrypted, and are never uploaded:

```bash
installer/install.sh backup          # back up every instance
installer/install.sh backup main     # back up one instance
```

Backups land in `~/.amanuensis/backups/<timestamp>/` with restricted permissions. The installer keeps the five most recent.

```bash
installer/install.sh upgrade --check   # compare the installed version with the checkout (no network call)
installer/install.sh upgrade           # back up, rebuild, restart, health-check
```

Upgrade refuses to start unless doctor shows no failures, unless you pass `--force`. It backs up every instance first, rebuilds the images, restarts each stack, and checks health. If the upgrade fails after the restart begins, it restores the backup and the previous images, then tells you what it did.

## Forgot your password

```bash
aman password                  # with several instances: aman password --instance NAME
```

It asks for a new password twice, signs everyone out of that instance, and restarts only its sign-in service and app. Run it on the computer where Aman is installed; that is how Aman knows you are the owner.

## What is off in this version

Running code (`run_code`, Python and shell in a gVisor sandbox with no network) is on after a normal install. Settings → Sandbox shows it as ready, and new chats have the sandbox enabled. Email attachment extraction and skills show as **off** in this version, with the plain reason shown in the app. An instance installed with `--no-sandbox` has run code off too.

## Troubleshooting

**The `docker` group needs a sign-out.** After a fresh Linux Docker install, your shell does not know about the new `docker` group until you sign out and back in (or reboot). The installer works around this for its own run and prints a reminder; if later commands say permission denied on the Docker socket, sign out and back in.

**Ports in use.** `instance add` tests each port with a real bind before using it. If it reports a port conflict, either free the port or pass `--port` and `--login-port` explicitly.

**Docker Desktop credential store.** If image pulls fail with credential errors, open Docker Desktop, sign the credential helper back in, and rerun the installer.

**Clock skew.** If logins or certificate checks fail right after a sleep or a VM resume, check the machine clock. Turn on automatic time synchronization and run doctor again.

**Login unavailable while the login server starts.** The login server takes a few seconds to come up on a first install. Wait, reload the page, and if it still fails, run `aman doctor` and follow the login check's fix.

## Privacy notes

The installer reads no chats, memories, mail, or audio. What it handles: generated secrets, the owner email, the password hash, the model endpoint you typed, and install state and logs. Secrets never appear in command arguments, logs, or reports. There is no telemetry and no network scanning; the installer only contacts the addresses you typed or the ones its printed plan lists.
