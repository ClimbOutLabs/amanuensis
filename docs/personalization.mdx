## What is stored

Personalization is a single profile owned by the authenticated user. It contains only:

- Your name and how the assistant should address you
- Assistant name and concise identity guidance
- Voice guidance
- A concise user profile
- Up to 12 pinned preferences
- The areas you picked for the Tour's "What would help you most?" question, in the order picked. They shape the Tour's cards and are never sent to the model
- An optional learned profile document, maintained by the server when profile learning is on
- A profile learning switch, off by default

The profile is stored locally in the configured database. Standalone mode uses SQLite; distributed mode uses Postgres. It is never copied from chat history automatically and it is not shared with other users.

The profile records its owner, last updater, timestamps, a monotonic revision number, and a SHA-256 digest of the model-facing content. Updating a profile with identical content leaves its revision unchanged. The learning switch and the help areas are not model-facing and so are deliberately outside the digest; the server compares them separately, so changing either alone still writes and still advances the revision.

## What the model sees

On every root-agent turn, the server builds one bounded `<personalization-context>` section from the current profile. Dynamic subagents never receive it. Default-assistant turns receive the assistant name, identity, voice, your name and form of address, user profile, pinned preferences, and learned profile. When a configured persona is active, that persona is the sole assistant identity: the server omits the default assistant's name, identity, and voice while retaining your name and form of address, the user profile, pinned preferences, and learned profile.

The default-assistant profile projection is available through:

```text
GET /api/v1/personalization/context
```

The active persona and its instructions remain visible in Personas and on the chat's active-speaker indicator. The server derives the turn's speaker-specific projection from those visible sources; `profile_digest` identifies the source profile, not the projected prompt bytes.

## API

```text
GET    /api/v1/personalization/profile
PUT    /api/v1/personalization/profile
DELETE /api/v1/personalization/profile
GET    /api/v1/personalization/context
```

`PUT` replaces the complete profile. Send `expected_revision` beside `profile` with the revision you read: if the profile has changed since, for example because the assistant learned something, the save is refused with `409` and nothing is written. Settings does this for you and saves your edits on top of the newest profile, so text learned while the page was open is kept. Use `DELETE` to remove it. The authenticated identity determines profile ownership; callers cannot select another user's profile.

A `PUT` whose body carries nothing at all is rejected, because removing a profile is what `DELETE` is for. `learning_enabled` counts as content in either position, so a profile holding only the switch is legitimate whether it is on or off; that is the state a user lands in by trying profile learning and then turning it back off. Omitting the field entirely is what reads as no content, and it also reads as learning off.

## Learned profile

Profile learning is off until you turn it on, in Settings under Personalization, with the switch beside the learned profile. The switch is the `learning_enabled` field on the profile and it persists through the same profile `PUT` as everything else; a user with no profile has never opted in, so nothing runs for them. Nothing else gates the pass: there is no operator-side switch and no restart to change it.

With it on, learning has no model call of its own. After each successfully completed turn, one helper call already decides what the turn holds that is worth remembering. That same call is shown the learned profile's lines and also says which of the facts it kept belong in the profile: who you are, a lasting preference, or how you want the assistant to work with you. It sees only what you wrote in the turn. It never sees a tool result, a file, or recalled memory, and of the assistant's reply it sees at most the last question, to understand a short answer. When no such call runs for a turn (no memory, or turn summaries off), the server makes that one call itself. Nothing is learned from an Incognito chat.

The document is then edited by the server's own code, not rewritten by a model. A new line is added under one of two headings: `## How to work with me` for how you want the assistant to work with you, and `## About me` for everything else. A line that corrects an older one takes its place. Nothing already in the document is reworded, shortened or merged.

The document is limited to 4,000 characters. When a new line does not fit, the oldest line under `## About me` (or under any other heading you wrote yourself) is moved into memory exactly as written, as a note marked as your own words, and the new line goes in. Lines under `## How to work with me` stay, and one of them moves only when no other line is left to move. A line is moved only after memory has accepted it. If memory is off or does not accept it, the document is left as it is and the new fact stays in memory only. So the profile holds your standing wishes and the most recent things you said about yourself, and memory holds the rest in full. There is nothing to clean up by hand.

Learning never delays or fails the turn it learned from, and every failure inside it is logged and changes nothing. The switch is read again after the turn, so turning it off while a turn is running takes effect for that turn too. If you edit the profile while a turn is being learned from, the new lines are added to your edit. The helper call uses the summarization model from **Roles and Personas**, else the main chat model, and its usage shows on the turn's usage line with the other helper calls.

Every host write leaves an `aman.profile.learned` event on the completed turn's event log carrying the previous document, the new document, and the profile revision the write produced, so the change trail is auditable through the events API. The learned profile lives in Settings and in the prompt. Memory holds only the lines that were moved out of a full profile, one note each. Earlier versions also saved a copy of the whole document as a memory note. Each turn that is learned from, and each save or delete of the profile in Settings, now removes any such copy, and recall never shows one. Clearing the learned profile in Settings therefore stops it being used anywhere. As with any deleted memory, the copy's old text stays in the dated file in the memory folder, hidden, until the line is removed from that file by hand.

The document is part of the personalization profile: it renders in the model-facing `<personalization-context>` block after pinned preferences, with a preamble stating that it was learned from past conversations. You can read, edit, or clear it at any time in Settings under Personalization, and it round-trips through the same profile `PUT`.

## Deliberately not included yet

This phase does not extract episodic memories, create embeddings, use a vector database, or store hidden reasoning. The learned profile is the only automated write, it is off by default, and it stays fully visible: the exact document the model sees is the document shown in Settings.
