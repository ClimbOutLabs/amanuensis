# Spec: Email Integration (v1, Gmail only)

## Problem

A personal AI assistant without email is a toy. The morning digest, finding a thread, drafting a reply, and collecting emails into a project space are the highest-value daily journeys, and none of them work without email access.

## Solution

First-class Gmail support through the user's own gmail-mcp adapter container (`@george43g/gmail-mcp`, pinned version), hardened per this spec. The user brings their own OAuth client; Amanuensis never owns an OAuth client, never goes through provider verification. This spec fixes the large-result handling against the real Gmail server shape, locks down credential storage and the send path, and defines the exact tool contract the agent sees, rewritten parameter by parameter against the real adapter source. Outlook and iCloud are explicitly deferred to v2.

## Design Decisions

**User-owned credentials.** Each user registers their own Google OAuth client. Amanuensis provides the setup guide and the credential fields; it never provisions a shared client and never goes through provider verification. The user's own client id and secret are stored encrypted in the vault (needed for the OAuth exchange, token refresh, and provisioning the adapter credentials file). One maintainer cannot carry the compliance, quota, rotation, and incident-response burden of app-owned credentials, and a shared client is a shared blast radius. This is the same decision as calendar.

**One OAuth client, one refresh token, logical grants.** Gmail and Google Calendar share one OAuth client and one refresh token carrying the union of granted scopes. "Separate read and send grants" are logical grant records in the connector layer, not separate OAuth tokens: the read grant maps to the `gmail.modify` scope set, the send grant maps to the `gmail.compose` scope set. The user can connect email read-only (consent for `gmail.modify` only) and add send later (a second consent adding `gmail.compose`). The swap order is load-bearing: the connector obtains the new union-scoped refresh token, persists it in the vault first, and only then revokes the old token at Google. Revoking first could strand both products if anything fails in between. The connector enforces the grant split: without the send grant record, the four draft tools are hidden in the UI and rejected server-side, regardless of what the adapter's own scope-aware listing exposes.

**Read grant is `gmail.modify`, not `gmail.readonly`.** The digest promises unread-first triage with a working mark-read loop, and removing the UNREAD label requires `gmail.modify`. `gmail.modify` covers read, search, download, and label changes, and explicitly does not authorize permanent deletion (that needs `gmail.full`, which v1 never requests).

**Send grant is `gmail.compose`, not `gmail.send`.** The v1 send path is draft-only (`send_draft`), and creating drafts requires `gmail.compose`; `gmail.send` alone ("send only") cannot create drafts. With `gmail.compose` the raw `send_email` tool is authorized at the Google level, which is exactly why the connector blocks it at invocation: the raw send path never reaches the agent.

**Revoking Gmail disconnects Calendar.** Google revocation is per-token, not per-scope, and both products share one refresh token. Disabling Gmail therefore silently kills Calendar access too. The revocation UX must warn about this explicitly and require confirmation (see Revocation).

**The user's OAuth client must use Production publishing status.** A client left in Testing gets refresh tokens that expire after 7 days, which turns the "one setup" claim into weekly reconnection prompts. The setup guide includes the publishing-status step, and the connector treats the 7-day-expiry failure pattern as a reconnection trigger.

**Send never happens without explicit confirmation.** Drafting is free; sending requires the user to confirm the actual recipients, subject, and body in the chat. The agent must not send on implied consent, standing instructions, or a previous turn's vague approval. The raw send tool is blocked at the connector invocation layer, so every send passes through the gate. Confirmation binds draft id, canonical hashes, and a 15-minute TTL; at send time the gate re-reads the draft live from Gmail and compares, so edits made anywhere (agent call, Gmail UI, another client) between confirmation and send invalidate the send. There is no draft version to go stale: provider state is the source of truth.

**One account in v1.** Settings names the connected Gmail account. Search results and the digest state which account was searched, so partial coverage is labeled, never silent. The adapter's `switch_account` / `list_accounts` tools are blocked in v1.

## Assumed connector framework interface (pinned: `gmail-connector-if/1`)

This spec does not define the connector framework; it depends on it. This spec pins the assumed interface as version `gmail-connector-if/1`. Implementation of this spec is blocked until the framework documents exactly that version. If the framework ships a different version, this spec must be re-reviewed against it. The framework is a separate component with its own spec, and it must provide exactly these hooks for the `gmail` connector:

- Registration: a named connector with configuration (adapter URL, adapter bearer token, tool allowlist, vault key id, health probe cadence).
- Transport: Streamable HTTP to the adapter `/mcp` endpoint, authenticated with the adapter bearer token.
- `tools/list` filtering: the framework drops every tool not on the allowlist before the agent sees the listing.
- Grant-aware listing hook: the framework calls the connector's listing filter on every `tools/list`; the connector reads the grant records from its own namespaced grant store and removes tools the active grants do not cover (the four draft tools without the send grant record) before the agent sees the listing. The static allowlist filter alone cannot do this because grants change per user and per session.
- `tools/call` interception: the framework rejects any call whose tool name is not on the allowlist before touching the MCP transport, and routes allowlisted calls through per-tool hooks (grant checks, the send gate). Agent-facing interception applies only to agent-initiated calls.
- Internal tool-call path: a connector-internal path (e.g. `connector.internalToolCall`) that reaches the adapter without passing the agent-facing allowlist interception. The health probe and the send gate's live draft read use this path; it is not reachable from the agent. This is how `health_check` (blocked for the agent) is callable by the backend probe without tripping the interception. Required: the internal path is unreachable by construction from agent context (not a callable tool name, not a flippable flag), with a test asserting rejection of any agent-context attempt to reach it.
- Server-side namespaced state: a confirmation store, a grant store, and the miss log, all namespaced to the gmail connector and never exposed to the agent. Both the confirmation store and the grant store survive backend restarts (the listing hook and the send gate read the grant records on every call path; if the records were memory-only, a restart would silently drop both grants while the vault still held a valid token, leaving the user to re-run setup to recover). The connector writes the read grant record after the OAuth code exchange persists the refresh token, writes the send grant record after the second consent persists the union-scoped token, and deletes both records during revocation. Required test: restart the backend after read-only consent and assert the draft tools stay hidden and read tools work; restart after the second (send) consent and assert the draft tools remain listed and `send_draft` remains gated-but-available; restart after revocation and assert the draft tools are hidden.
- UI-facing confirmation APIs, part of this pinned interface: `POST /api/v1/connectors/gmail/confirmations` (writes the confirmation record; requires a human UI session, see Send gate and confirmation binding) and `GET /api/v1/connectors/gmail/drafts/{draftId}` (live draft read for the confirmation dialog; requires a human UI session).
- Health: the connector exposes `connectors.gmail.health` (`healthy`, `not_configured`, or `down`, plus last probe time) to the agent runtime.

Where this spec says "the connector" does something, it means backend code running against this interface.

## User Journeys

### Morning digest

This journey is the email digest: the user's request is email-scoped ("Catch me up on my email"). Aman returns a grouped digest: unread important mail first, then newsletters and notifications collapsed, each item one line with sender, subject, and a one-sentence gist. The digest names the Gmail account it searched. "Important" means Gmail's importance markers: mail carrying the `IMPORTANT` label assigned by Gmail's own classifiers, exposed in the adapter's `labelIds`. Within the important group and within the rest, newest first. The digest does not invent its own importance score. Action items found in mail are listed separately.

Query strategy: the digest first lists `in:inbox is:unread` newest-first (by internal date descending) for the triage pass; if budget remains it continues with `in:inbox` newest-first, skipping threads already reviewed. Pagination follows the provider's `nextPageToken`. The order is newest-first throughout, so the coverage statement ("N threads reviewed, roughly M remain unreviewed") describes the oldest unreviewed mail, not a random sample.

If Gmail is unreachable, the digest says so in one line and continues with the other sources; it never fails the whole briefing. If Gmail was never connected, the digest does not return an empty digest with email silently absent: it states in one line that Gmail is not connected and points to Settings → Connect Gmail, then stops. (When the user asks for the full morning briefing across sources rather than the email digest, each source's section carries its own health label per the digest health signal below.)

Mail in other languages: the one-sentence gist is written in the language the user is conversing in; the item line notes the mail's language; full translation happens only on user request.

Email fetching for one digest run is bounded per call by the enforced 8,000-token bound (see Context-bloat bounds); the 32,000-token aggregate across calls is agent guidance, not an enforced limit. When fetching stops (bound reached, guidance exhausted, or no more pages worth fetching), the digest states coverage: how many threads and messages were reviewed and roughly how many remain unreviewed. A bare "stopped fetching" is not acceptable.

### Search

The user types "Find the email about the lease." Aman searches the connected Gmail account with Gmail query syntax, shows the top matches with sender, date, and snippet, and offers to open one. Results are labeled with the account. The default search scope is the inbox (`in:inbox` is the adapter default); sent mail is excluded unless the query overrides it, and the journey states the scope it used. When the user asks about mail they sent ("find the email I sent to the landlord"), the agent searches with `in:sent` rather than returning zero matches under the inbox default. Every search answer states coverage: how many matches the provider reported, how many results were reviewed, and whether the result list was truncated by the `maxResults` cap or the token bound.

### Read

The user types "Show me that thread" (or picks a result). Aman renders the full thread in reading order with headers collapsed to sender and date. Attachment metadata (filename, size, MIME type) is shown inline. Long threads are truncated oldest-first within the token bound and marked as truncated; the truncated envelope retains the omitted messages' ids (not bodies) so the agent can fetch individual omitted messages on request rather than dumping everything. Mark-read is conditioned on complete rendering: the agent removes the UNREAD label only when the thread was rendered without truncation. A partially rendered thread keeps surfacing in the digest until the user has seen the omitted messages.

When the user asks what an attachment says (the read journey: "what does the attached lease say"), the agent downloads it via `download_attachment` and reads the content subject to the attachment content path (below). Text formats (text/plain, text/html rendered as text, text/csv and similar) are read directly; PDFs are read through text extraction when available. Extraction runs in the connector, bounded by the 10 MB input cap and a 60-second timeout; if extraction exceeds the timeout or fails, the agent gets the honest decline below rather than a partial read presented as complete. Files larger than 10 MB are not downloaded; content is truncated to the token bound with the truncation stated.

Continuation: the downloaded file is retained in the connector's sandbox for the sandbox lifetime (up to one hour from download, keyed to the messageId plus attachmentId read session). To read the next part, the agent calls `download_attachment` again with the same `messageId` and `attachmentId`; the connector serves the next token-bound window from the cached file instead of re-downloading, and the response states which window was served and the approximate total ("part 2 of about 5"). The window unit is the token bound (the same bound used for truncation), measured on the extracted text: for PDFs the connector caches the extracted text alongside the file for the sandbox lifetime so continuation windows serve from the cache rather than re-running extraction. If the sandbox expired, the call re-downloads from the start and says so. A read session serves at most 20 windows; beyond that the connector refuses and suggests opening the message in Gmail, so a single attachment cannot become an unbounded read loop. There is no offset parameter on the real tool; the windowing is connector-side read-position tracking, not an invented adapter parameter.

When content cannot be read (images, scanned PDFs without extractable text, archives, binaries, or anything over the size bound), the agent says so plainly: it names the format and size, offers the metadata it has, offers to open the message in Gmail (a link to the Gmail web UI for the message), and does not guess at the content. The agent never invents attachment content.

### Draft

The user types "Draft a reply to a colleague saying Thursday works." Aman creates a provider-side draft threaded as a reply (via `threadId` / `inReplyTo`) and shows it in the chat: recipients, subject, body, editable. The draft is never sent at this step. The user can edit in the chat; each edit calls `update_draft` on the same draft id (no orphan copies), and abandoned drafts can be removed with `delete_draft`. CC and BCC are supported. Attaching files to drafts is deferred to v2. Across sessions, the agent uses `list_drafts` to resume an edit loop (the user returns the next day and says "send that draft to the landlord"), which is why `list_drafts` is in the contract even though in-session the agent already holds the draft id.

### Forward

The user types "Forward that thread to Sam." Forwarding without attachments is a first-class journey: Aman creates a new draft quoting the thread content (sender, date, body excerpt) addressed to the new recipient, and it goes through the same confirmation and send gate as any other send. Forwarding with attachments is not possible in v1 because draft attachments are deferred: the agent says so explicitly and offers to forward the text without the files, or to share the original thread another way. The agent never promises attachment forwarding it cannot perform.

### Send

After reviewing the draft, the user says "Send it." Aman shows a final confirmation dialog. The dialog handler re-reads the draft live from Gmail at click time (through the connector's internal draft-read path, not from cached state and not from agent prose) and renders recipients, subject, body, the send-as identity (`from` alias), the `mimeType`, the `inlineImages` when set, the rendered `htmlBody` when one is set, an attachments-present indicator when the live read shows attachments (the dialog refuses to confirm an attachment-carrying draft in v1), and the reply context (which thread the reply lands in). The dialog renders the full body or marks truncation explicitly. Only on explicit confirmation does it call `send_draft`. The confirmation is bound to the draft id plus canonical SHA-256 hashes of `to`/`cc`/`bcc`/`subject`/`body`/`htmlBody`/`from`/`mimeType`/`inlineImages`/`threadId`/`inReplyTo` plus a 15-minute TTL on the backend clock. There is no version number: at send time the gate re-reads the draft live from Gmail, hashes that, and compares. Any change anywhere (agent `update_draft`, Gmail UI edit, another client) invalidates the confirmation and the user re-confirms. Confirmation records are single-use: a successful `send_draft` invalidates the record. The 15-minute TTL closes the confusion window between confirmation and send: in the normal flow send is seconds after confirmation, and the TTL bounds how long a stale confirmation (from a changed context or an unattended session) can authorize a send. It is a ceiling, not a grace period. The sent message is confirmed back with a message id. If the provider rejects the send (auth, quota), the draft is preserved and the error is shown with a retry action.

### Emails into a space

The user types "Put together a space for the apartment hunt." Aman searches mail for relevant threads, proposes a set with coverage stated (how many threads were reviewed, how many are proposed, how many were included, and whether results were truncated), and on approval collects them into a new space. The space body contains the thread summaries and records the source Gmail account alongside them. Linking back to messages is explicitly deferred: the spaces model defines no pinning or source-reference mechanism, so the space body holds summaries plus the Gmail thread ids as plain-text identifiers for manual lookup. Structured source links are not claimed and not built; they wait on the spaces spec. The space body records the account so coverage stays labeled if a second account ever arrives.

## Tool Contract

The contract is rewritten against the real `@george43g/gmail-mcp` tool source (37 tools in the vendored source; the documented catalog lists 33; the pinned version governs). The contract is default-deny: the 10-tool allowlist below is the entire agent-visible contract. Any tool name not on the list is rejected at `tools/list` (the agent never sees it) and at `tools/call` (rejected before the MCP transport), which also defeats tool names smuggled in via prompt injection in email content. The allowlist lives in the connector definition, versioned with this spec.

### Kept tools (10)

The downloaded file is retained for the sandbox lifetime (up to one hour from download) to serve the continuation windows described in the Read journey; the connector deletes it when the read session is closed or the hour expires, whichever comes first.

### Blocked tools (27), with reasons

- `send_email`: the raw send path (takes `to`/`subject`/`body` directly). Blocked at invocation; this is the safety-critical block. The confirmation binding would be meaningless with it live.
- `reply_all`: builds recipients and threading headers automatically, then sends directly outside the confirmation binding. Blocked; replies go through `draft_email` (`threadId`/`inReplyTo`) plus the gated `send_draft`. This is the documented disposition of the real adapter's `reply_all`, not a silent drop.
- `search_emails`: redundant with `list_inbox_threads` (see above).
- `get_inbox_with_threads`: redundant and a context-bloat vector (one call can return full inbox bodies).
- `download_email`: writes email files to container disk; no v1 journey needs it.
- `modify_email`, `batch_modify_emails`: label mutation beyond the v1 mark-read/archive path; `modify_thread` covers triage.
- `delete_email`, `batch_delete_emails`: permanent deletion, requires `gmail.full`, never requested in v1.
- `report_phishing`, `batch_report_phishing`: apply the SPAM label; no v1 journey needs them.
- `list_email_labels`, `create_label`, `update_label`, `delete_label`, `get_or_create_label`: no label management in v1.
- `list_filters`, `get_filter`, `create_filter`, `delete_filter`, `create_filter_from_template`, `list_send_identities`: filter and send-identity management; require `gmail.settings.basic`, which v1 never requests.
- `list_accounts`, `switch_account`: one account in v1; `switch_account` is a state change the agent must not perform (and the adapter does not refresh its tool catalog on switch, so it would also lie about the surface).
- `unread_summary`: aggregates unread counts across ALL configured accounts, which contradicts the one-account disclosure rule.
- `health_check`: blocked for the agent; reserved for the backend probe over the connector's internal tool-call path (it needs no Gmail scope and makes no Gmail call).

### Why the connector must enforce the grant split itself

The adapter hides tools outside the token's granted scopes from `tools/list` and rejects them at call time, but that is not sufficient for the read/send split: with a read-only token (`gmail.modify`), the adapter still exposes `draft_email`, `update_draft`, `delete_draft`, and `send_draft`, because `gmail.modify` appears in each tool's scope list. The connector therefore enforces the grant split independently: without the send grant record, all four draft tools are rejected server-side even when the adapter would allow them, and hidden from the listing through the grant-aware listing hook.

**Context-bloat bounds.** Defaults, configurable. Enforcement and guidance are deliberately separated:

- Enforced in the fetch-semantics layer: no single tool call may inject more than 8,000 tokens of email content into the agent's context. The bound applies to every tool result, including list/search results: snippets are capped at 200 characters per result, `maxResults` is capped at 100, and `get_thread` / `read_email` results are truncated oldest-first with the truncation stated. The token bound is enforced in the fetch-semantics layer (character-count approximation in the hot path is acceptable).
- Agent guidance only: one digest run should inject no more than 32,000 tokens in aggregate across calls. The assumed framework interface provides no run id or meter hook to attribute calls to a digest run, so the aggregate cannot be enforced; the spec claims enforcement only for the per-call bound.
- The agent is instructed to prefer `metadata`/`minimal` formats and fetch full bodies only for messages the user opens. The format preference is agent guidance; the spec claims enforcement only for the bound.

Sizing arithmetic (provisional, pending real-world measurement): 100 results times 200-character snippets is 20,000 characters, roughly 5,000 tokens at 4 characters per token, plus envelope overhead, landing under the 8,000 per-call target. Character-count approximation systematically undercounts tokens for non-Latin scripts (CJK and similar scripts run closer to 1-2 characters per token), so a multilingual result set can exceed the token target while passing the character bound; the error direction is undercount, meaning possible over-injection, which the tests must exercise.

## Send gate and confirmation binding

The gate sits in the backend connector invocation path, between the agent and the adapter. The adapter's send-capable tools are never exposed to the agent directly; only the connector's gated wrapper is. Enforcement layers, in order:

1. Invocation allowlist: only the 10 contract tools are callable. `send_email` (raw) and `reply_all` (direct send) are rejected before the MCP transport, as are all other blocked tools and any tool name arriving via prompt injection.
2. Grant check: `draft_email`, `update_draft`, `delete_draft`, and `send_draft` require the send grant record in the connector's namespaced grant store (the same store the listing hook reads; the gate and the listing hook never consult different sources).
3. Confirmation check on `send_draft`: the gate looks up the confirmation record and rejects the send unless the record exists (a missing record, including after a backend restart with no record, rejects: fail closed), names the same draft id, is unexpired (15 minutes by the backend wall clock at invocation), and has not been consumed. Check-and-consume is atomic (compare-and-set in the store transaction): two racing `send_draft` calls cannot both consume the same single-use record. The gate then re-reads the draft live from Gmail through the connector's internal draft-read path (not the agent allowlist, not cached connector state) and compares canonical hashes of the live `to`/`cc`/`bcc`/`subject`/`body`/`htmlBody`/`from`/`mimeType`/`inlineImages`/`threadId`/`inReplyTo` against the record. Any mismatch rejects the send. This covers edits made anywhere between confirmation and send, including the Gmail web UI, which no connector-side version counter could see. Residual, stated: the live re-read and the `send_draft` invocation are two separate provider calls with a millisecond race between them; accepted as residual.
4. Attachment check: the gate's live re-read also inspects the draft for attachments. Any attachment on the draft rejects the send in v1, because attachments are outside the confirmation binding's hashed surface: the connector's `draft_email`/`update_draft` path can never create them, but the Gmail web UI or another client can add them out-of-band between confirmation and send, and the hash comparison would pass while files the user never saw in the dialog go out. The rejection names the cause ("this draft has attachments, which are not supported in v1; remove them in Gmail and re-confirm"). The confirmation dialog renders an attachments-present indicator when its live read shows attachments, and the dialog handler refuses to write a confirmation record for an attachment-carrying draft. This closes the out-of-band path: the UI-created attachment case is rejected at both write time and send time.
5. Residual risk, stated explicitly: the adapter container holds the refresh token and has network egress to Google APIs, so a compromised or malicious adapter could call the Gmail API directly and bypass the backend gate entirely. The gate is a policy control on the honest path, not a security boundary against a compromised adapter. Mitigations are the pinned version with hash verification, egress restriction, and the adapter's scope-aware tool hiding. The trust statement in the deployment docs names the adapter as privileged code and states this residual risk.

**Confirmation record.** The writer is the chat UI's send-confirmation dialog handler, which writes through `POST /api/v1/connectors/gmail/confirmations` at the moment the user confirms. That endpoint requires a human UI session: it authenticates the session cookie and validates a CSRF token bound to that session, and it is unreachable from the agent execution context (the agent holds no session cookie and no CSRF token; requests without both are rejected). The same human-session requirement applies to the dialog's draft read, `GET /api/v1/connectors/gmail/drafts/{draftId}`. The agent cannot mint confirmation records: it knows the draftId and the canonicalization, but without a human session the write endpoint rejects the request. The record lands in the backend confirmation store namespaced to the gmail connector (server-side, never in the chat transcript; the store survives backend restarts). Before writing, the handler re-reads the draft live from Gmail at click time (via the UI-facing read API, a live provider read through the connector's internal path), and renders recipients, subject, body, the send-as `from` identity, the `mimeType`, the `inlineImages` when set, the rendered `htmlBody` when set, an attachments-present indicator when the live read shows attachments (the dialog refuses to confirm an attachment-carrying draft in v1), and the reply context (which thread the reply lands in), all fetched from the provider, not from agent prose, so the user confirms exactly what is hashed. The record's hashes are computed from the same live-read response that was rendered: there is no second fetch between render and write that could diverge from what the user saw. The dialog renders the full body or marks truncation explicitly; a silently truncated body would mean the user did not review what the hash covers. The record contains: `draftId`, canonical SHA-256 hashes of `to`/`cc`/`bcc`/`subject`/`body`/`htmlBody`/`from`/`mimeType`/`inlineImages`/`threadId`/`inReplyTo`, `confirmedAt`, a 15-minute TTL, and a consumed flag. Canonicalization: addresses are lowercased, trimmed, sorted, and comma-joined; subject and body are hashed as exact bytes (whitespace is significant). The TTL is enforced by the gate at send time using the backend clock. Note on the store's sensitivity: hashes of low-entropy fields (addresses, short subjects) are dictionary-reversible, so the confirmation store gets the same at-rest consideration as adjacent credential material. No draft version field exists: the live re-read at send time makes version tracking redundant (any content change changes the hash), and it eliminates the stale-version failure mode entirely, including across connector restarts, because there is no version map to lose.

## Auth Flow

Guided setup in Settings. The guide shows every step with screenshots, requires the user's OAuth client to use Production publishing status, and is acceptance-tested end to end on a fresh Google account by someone following only the in-product guide.

1. The user creates a Google Cloud project (or reuses the calendar one), enables the Gmail API, creates an OAuth client (Desktop app type), and sets the client to Production publishing status.
2. In Amanuensis Settings, they start "Connect Gmail." The app opens the provider consent URL carrying the user's own client id, with a `state` parameter of 128+ bits from a CSPRNG and PKCE (`S256` code challenge). The `state` value and the PKCE verifier (43-128 char base64url from a CSPRNG) are stored server-side in a pending-OAuth record bound to the user's session, single-use, with 10-minute expiry; neither value is logged or sent to the client. The callback validates `state` against the stored value before exchanging the code, and rejects the flow on mismatch or expiry.
3. Supported topology: when Settings runs on the same machine as the backend, Google redirects to the backend's loopback-only callback listener and the authorization code is handed to the token-exchange routine in process. When the browser is remote (for example a phone on the home network), the flow falls back to manual code paste into the Settings form over the existing authenticated session; the guide states the fallback's risks (shoulder-surfing, clipboard exposure), and the code remains single-use with 10-minute expiry while the PKCE verifier never leaves the server.
4. Amanuensis exchanges the code and stores the refresh token plus the user's client id and secret encrypted in the vault (see Security).
5. Requested scopes: `gmail.modify` for the read grant, always; `gmail.compose` for the send grant, only if the user enables sending, as a separate consent step. The UI shows which grant is active. Adding send later runs a second consent for `gmail.compose`; the connector obtains the new union-scoped refresh token, persists it in the vault first, and only then revokes the old token at Google (see Security 5 ordering).
6. If the user already connected Google Calendar, the flow reuses their existing client and adds the Gmail scopes to the same consent; one client, one refresh token, both products.

### Credential plane

There is exactly one credential plane. Amanuensis performs the OAuth flow and holds the refresh token plus the user's client id and secret in the encrypted vault. The adapter's Streamable HTTP bearer token also lives in the vault under the same AES-256-GCM protections (it is a long-lived credential with its own rotation story: rotated when the connector is re-provisioned, and on demand from Settings). The gmail-mcp adapter container receives credentials at startup through a file on a tmpfs mount, never an environment variable. The file uses the adapter's native credentials shape (the same shape the adapter's own `account auth` writes; exact JSON keys are verified against the pinned adapter, see the verification appendix), generated by the connector from the vault contents. The adapter's own loopback OAuth flow is disabled in this deployment (`OAUTH_DISABLED=true`).

The "adapter must not persist the token to disk" requirement is enforced structurally, not by trust: the only credentials path the adapter is ever given is the tmpfs file, so any adapter write-back (the adapter natively persists rotated access tokens to the credentials file it loaded) lands on tmpfs, which is ephemeral.

**Provisioning and restart recovery.** The connector owns the adapter container lifecycle. Before every adapter start, the connector re-generates the tmpfs credentials file from the vault, then starts the adapter; the adapter reads it at startup natively. On any container restart (crash, host reboot, redeploy), the connector re-provisions the file first, so there is never a restart that finds an empty tmpfs. The connector also re-syncs the tmpfs file back into the vault every 60 seconds, so a refresh token rotated by the adapter mid-life is not lost if the container dies before the next provision. Failure mode, stated: if the adapter rotates the token and the container dies inside the 60-second window, the vault holds the stale token; the next provision writes the stale token, adapter auth fails, and the connector surfaces "Email needs reconnection" rather than retrying with a dead credential. The tmpfs mount is `0o600`, owned by a dedicated uid shared by the connector writer and the adapter reader; the uid/gid mapping is part of the deployment configuration. Residual risk, stated: any process running as the same uid on the host can read the file; the mitigation is the dedicated uid plus `0o600`, not a claim that tmpfs is a vault.

### Reconnection

When Gmail reports invalid or expired credentials, the integration surfaces "Email needs reconnection" with a one-tap restart of the setup flow. Previously stored credentials are discarded when the new ones land. The rest of the product keeps working; only email features degrade.

### Digest health signal

The backend probes the adapter with the `health_check` tool over the connector's internal tool-call path (bypassing the agent-facing allowlist interception; needs no Gmail scope, makes no Gmail call) every 5 minutes and on demand. On-demand triggers: the Settings "Test connection" button, and the start of a digest run that includes email. The connector exposes three states to the agent runtime via `connectors.gmail.health`: `healthy` (the normal operating state; the digest includes email), `not_configured` (no Gmail connector, or configured but never successfully connected), and `down` (connector configured but the last probe failed; the digest says so in one line and continues). There is no fourth "degraded" state until a consumer needs behavior that differs from `down`. When the calendar integration is specified, its connector must implement the same `connectors.<name>.health` contract (same three states, same digest semantics) so the multi-source briefing's per-source health labels rest on a uniform contract; this spec's health signal is the reference implementation, not a Gmail-only special case.

Behavior on `not_configured` depends on the request. When the request is email-scoped ("Catch me up on my email"), the digest states in one line that Gmail is not connected and points to Settings → Connect Gmail, then stops; it never returns an empty digest with email silently absent. When email is one source among several in a briefing, the digest labels the gap ("Email: not connected") and continues with the other sources. The rule is the spec's own: partial coverage is labeled, never silent.

## Architecture

```
gmail-mcp            # @george43g/gmail-mcp, pinned version + hash, user's own OAuth
                     # Streamable HTTP /mcp, bearer token; egress restricted to Google APIs
aman-prod-*          # agent backend:
                     #   gmail connector (allowlist at list+call, grant-aware listing,
                     #     grant checks, send gate with live draft re-read,
                     #     confirmation store, fetch semantics,
                     #     health probe, miss log, tmpfs provisioning + vault re-sync)
                     #   encrypted vault (refresh token, client id/secret, adapter bearer token)
```

**The adapter is a pinned dependency.** The deployment pins the exact gmail-mcp version with SHA-256 hash verification at deploy time and on every reconnect. The expected hash is stored in the connector definition, versioned with this spec and committed in the repo. The hashed artifacts are the npm tarball of the pinned `@george43g/gmail-mcp` version and the built container image digest; transitive dependencies are pinned via the lockfile at build. The check is performed by the deploy script and by the connector on reconnect; a mismatch refuses to start the adapter and surfaces "Email needs attention." The spec requires a trust statement in the deployment docs naming the adapter as privileged code (it holds the refresh token and sees every email), stating the residual send-gate bypass risk, and documenting the egress restriction.

**Send gate location.** The send confirmation gate lives in the agent backend, in the connector invocation path: `send_draft` calls are intercepted before reaching the MCP transport, the confirmation record (draft id, canonical hashes, timestamp, TTL, consumed flag) is looked up, the draft is re-read live from Gmail and hashed, and the call is rejected if no valid matching confirmation exists. This is backend code, stated explicitly. It is not provider-specific; it operates on the tool contract.

**Fetch semantics: the backend adapts to the real server shapes.** The backend fetch-semantics layer normalizes real adapter results to the envelope conventions (item arrays under `results` / `threads` / `messages`, ids under `id` / `threadId` / `messageId`, next-page tokens under `nextPageToken`). The table is a static constant derived from the tool contract, verified once by hand against the live deployed adapter at the pinned version (see the verification appendix). The adapter is third-party code the project does not control, so the spec places no normalization requirement on it. The miss log (tool name plus structural fingerprint, never content) is drift detection: a scheduled weekly drift-review job consumes it, and 3 or more misses for one tool in 7 days raises a Settings alert and a re-pin task. TO VERIFY: the framework's scheduler mechanism that runs the drift-review job, and the exact Settings-alert channel it raises through.

## LargeToolResponse: the proper fix

**The defect.** The fetch-semantics table's envelope and id expectations were written from hand-built mock responses. Against the real gmail-mcp server the shape check fails, so the email specialization never engages in production.

**The fix.** Rewrite the table against the real server, once, by hand, verified against the live deployed gmail-mcp at the pinned version. The reviewer for this fix replays the oversized-result path against the real server and confirms the email specialization engages (pagination guidance names the real token fields). No fixture pipeline, no redaction workflow, no versioned captures. The backend-adapts framing (above) is what keeps the table valid going forward; the miss log plus the weekly drift-review consumer is what catches drift.

## Security

**Encrypted credential storage.** The refresh token, the user's OAuth client id/secret, and the adapter's Streamable HTTP bearer token are stored encrypted at rest in the vault. Algorithm: AES-256-GCM. Key derivation: Argon2id with memory 64 MiB, iterations 3, parallelism 4, from a machine-local secret. Salt: 16 bytes from a CSPRNG per encryption, stored alongside the ciphertext. Nonce: 12 random bytes per encryption. AAD: the string `amanuensis:gmail:vault:v1` plus the key version, binding each ciphertext to this vault and key generation. `vault.key` is 32 bytes from a CSPRNG generated at first setup, stored at `~/.amanuensis/vault.key` (`0o600`). Key rotation: keys are versioned; rotation re-encrypts all vault entries under the new key and is a Settings action. Backup semantics: the encrypted blob may be backed up; the key file is excluded from backups by the backup job's explicit exclusion list (not just documentation), and a startup self-check warns if the key path sits under a configured backup source.

**Migration of plaintext token files.** The existing Gmail plaintext token files at `~/.gmail-mcp/accounts/<account-id>/credentials.json` are migrated on upgrade: the migration reads the client id, client secret, and refresh token, exchanges the refresh token for an access token at Google's token endpoint, calls `gmail.users.getProfile` with the access token to verify, then encrypts and stores the credentials and deletes the plaintext files. (Google's tokeninfo endpoint validates access tokens, not refresh tokens, so verification goes through a real refresh exchange, which is also why the client secret must be available to the migration.) Deletion attempts secure overwrite and then unlinks; the spec notes overwrite is ineffective on SSDs and copy-on-write filesystems, so the guide additionally tells the user to purge old backups of the plaintext files, which cannot be enforced technically. Failure policy: 3 attempts with backoff; on permanent failure the file is renamed to `credentials.json.quarantined` (`0o600`), retries stop, the migration is logged without credential content, and Settings surfaces "Email needs reconnection." The migration re-runs on startup only while an unquarantined plaintext file remains.

**MCP trust boundary.** The gmail-mcp adapter is third-party code holding the refresh token. Requirements: exact pinned version with SHA-256 verification of the npm tarball and the built image digest at deploy and on reconnect (expected hashes in the connector definition); network egress restricted to Google API endpoints, enforced by the container runtime's egress policy (allowlist `*.googleapis.com`, DNS to the platform resolver only); deploy-time registry access for the image pull is a separate phase before the restriction applies. DNS as an exfiltration channel is acknowledged as residual risk, mitigated by resolver-only DNS. The deployment docs carry the trust statement naming the adapter as privileged code, including the send-gate bypass residual risk.

**No credential or content logging.** Tokens, secrets, authorization codes, and PKCE verifiers never appear in logs, error messages, tool results, or crash reports. Email content (bodies, subjects, sender and recipient addresses) never appears in debug logs, tool-result traces, or crash reports either. Operational logs may carry message/thread/draft ids, label ids, timestamps, and byte counts. Credential-shaped strings are defined as: Google refresh tokens (`1//` prefix, 100+ chars), short-lived access tokens (`ya29.` prefix), OAuth client secrets (24-35 chars with entropy above 4.5 bits/char), OAuth authorization codes (provider callback `code` parameter), PKCE verifiers (43-128 char base64url), and any string over 64 chars with entropy above 4.5 bits/char. Error paths that echo provider responses are redacted before logging. Tests feed these shapes through every error and log path and assert redaction.

**Revocation semantics.** Disabling Gmail runs in this order, and the order is load-bearing: (1) revoke the REFRESH token at Google's revocation endpoint (the grant lives on the refresh token; revoking an access token would kill only that token while the grant survives, leaving access live after "disconnection"). Verify success; on transient failure, abort and retry, never proceeding to local deletion while the grant may still be live at Google; the UI shows "revocation failed, retrying" rather than "disconnected." An already-invalid token is treated as success (nothing to revoke). Outstanding access tokens: Google's revocation invalidates the grant; any outstanding access token is additionally neutralized in practice because step (3) tears down the adapter container that holds it. This assumption is stated explicitly rather than left implicit. (2) Delete the stored credentials from the vault and delete the read and send grant records from the connector's grant store, so the listing hook immediately hides the draft tools. The connector stops the 60-second tmpfs re-sync loop before this step and does not restart it until the next successful connect; otherwise the loop could copy the tmpfs credentials file back into the vault between deletion and teardown, resurrecting a dead credential and breaking the "local credentials are gone" invariant. (3) Tear down the adapter container (closing its sessions) and purge the tmpfs credentials file. (4) Show the reconnect state in Settings. Google revocation is per-token, not per-scope: revoking removes both the read and send grants. Flipping an "enabled" flag while credentials remain valid is not revocation. Because Gmail and Calendar share one refresh token, the revocation dialog warns explicitly: "Revoking Gmail also disconnects Calendar. Both will need reconnection." On confirm, both connectors enter the needs-reconnection state. The shared vault entry is keyed by Google account plus OAuth client id and is owned by this spec's revocation section; the calendar integration, when specified, must reference this section rather than define a competing revocation path.

**OAuth flow hardening.** Every authorization request carries a `state` parameter of 128+ bits from a CSPRNG and PKCE (`S256`). Both the state value and the PKCE verifier are stored server-side in the pending-OAuth record bound to the user's session, single-use, with 10-minute expiry. The callback validates `state` against the stored value before exchanging the code, and rejects the flow on mismatch or expiry. Authorization codes are single-use and never logged.

**Send authorization.** Covered in the Send journey and the send-gate section: the raw send path is blocked at invocation, draft tools require the send grant, `send_draft` requires a live confirmation record bound to draft id plus canonical hashes of the full send-affecting surface, re-verified against a live provider read at send time, 15-minute TTL on the backend clock, single-use records, and the gate rejects any draft carrying attachments in v1 (attachments are outside the hashed surface and can be added out-of-band).

**TLS everywhere.** OAuth flows use Google's HTTPS endpoints only. The adapter's HTTP transport is bound to loopback, or to the container network with TLS plus the bearer token. Plaintext bearer transport over the container network is not permitted: the bearer is the single credential that voids every send control if intercepted, so the "TLS terminates at the trusted reverse proxy where one exists" escape hatch is deleted. The adapter bearer token is 32 bytes from a CSPRNG, generated at connector provisioning. Localhost callbacks bind to loopback.
