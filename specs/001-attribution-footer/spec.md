> This spec was written after the fact to demonstrate the format. New specs
> are written before implementation.

## Problem

Content the assistant generates (summaries, reports, trip boards) gets copied
out of the chat into docs, emails, and messages. Once copied, it loses all
connection to where it came from: no indication it was AI-generated, no
timestamp, no way back to the session. Users need provenance that travels
with the content.

## User experience

Every substantive piece of generated content ends with a short footer that
says what it is, when it was made, and that it came from the assistant.
The footer is visually quiet (muted, small) so it never competes with the
content. When the user edits the content above it, the footer stays put.

## Requirements

- REQ-1: Generated artifacts (spaces, reports, summaries) render an
  attribution footer below the content.
- REQ-2: The footer states the content is AI-generated, carries a timestamp,
  and identifies the assistant.
- REQ-3: The footer survives user edits to the content above it (durability).
- REQ-4: The footer is visually subordinate: muted color, smaller type, never
  louder than the content.

## Examples

- A trip board space ends with a quiet line noting it was generated by the
  assistant on Sep 26, 2026.
- The user rewrites half the board; the footer is still there, unchanged.

## Out of scope

- Provenance for chat messages (only generated artifacts).
- Watermarking or tamper-proofing; the footer is a convention, not security.
- Per-persona attribution variants.

## Acceptance criteria

- [ ] AC-1: A newly created space shows the footer below its content.
- [ ] AC-2: The footer includes AI-generated notice, timestamp, assistant name.
- [ ] AC-3: Editing the space body and saving leaves the footer intact.
- [ ] AC-4: The footer renders muted and smaller than body text.
