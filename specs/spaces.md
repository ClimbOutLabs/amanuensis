# Spec: Spaces

**Status:** approved

Normative contract for the Spaces feature: current behavior, with approved design that is not yet built collected in the next section.

## Not yet built

The following are designed but not implemented on main today:

- **Context budgets.** The 8,000-token per-call budget, the 24,000-token per-turn aggregate budget, and the structured refusal shapes (`budget_exceeded` with `overage_tokens`, `cumulative_tokens`, `suggested_narrower_call`; `mutation_cap_exceeded` with `completed_count`, `cap`) are not enforced. Token estimates in the design are format-aware: ceiling(chars / 4) for markdown and plain text, ceiling(chars / 2.5) for HTML. A refused call would consume no mutation-cap slot, and refusal replaces silent truncation, which would corrupt a body the assistant is about to write back. The server enforces only the 65,536-character body cap today. Known limitation of the design: a marker-less space whose body exceeds the per-call budget would have no full-content read or write path through the assistant's tools; the recovery is to rebuild it as smaller marker-authored spaces from content the user pastes into chat. Such a space can only arise through the unbudgeted HTTP path, which is why marker authoring at creation is mandatory for spaces expected to be updated.
- **Mutation cap.** The per-turn cap of 5 space mutations (create, update, revert) is not enforced. In the design, a turn that hits the cap with work remaining narrates the pacing in chat and continues on the next turn.
- **`read_block` tool.** Not registered. Block-level reads go through `get_space` today.
- **`list_revisions` tool.** Not registered. Revision history is readable via `get_space` with a revision parameter.
- **List filter and tool pagination.** `list_spaces` takes no inputs today: no name filter `q` and no pagination inputs. It returns up to 500 spaces (the list cap) with `has_more` when more remain, but offers no way to fetch a later page. `list_blocks` likewise returns every block, with no truncation or offset. The Spaces view also fetches the list without paging parameters, so it shows at most 500 spaces even when the collection is larger.
- **410 for aged-out revisions.** Aged-out revisions read back as 404 today, the same as "space not found". A distinct 410 Gone status is designed but not implemented.
- **Removing search/replace edits.** `update_space` still accepts search/replace `edits` today. Removing the edits path in favor of block edits only is designed but not implemented.

## Problem

Chat conversations scroll away. When the user wants something durable to track or come back to, a plan, a tracker, a board, a research page, the chat transcript is the wrong container: it mixes the artifact with the conversation that produced it and buries it under later turns.

## Solution

Spaces: persistent, named, structured pages the assistant creates and keeps current. A space survives the turn and session that created it and is visible in the Spaces view without the user opening the chat that produced it. The user asks for one in plain language ("Put together a space for tracking the home renovation"), the assistant builds it, and the user reads and revisits it from the Spaces view.

## User Model

Spaces are assistant-authored and user read-only in the UI. The user creates, updates, archives, and reverts spaces by asking the assistant in chat; the assistant performs those actions through its tools. The user cannot type into a space, cannot edit its content directly, and cannot archive or revert from the UI. The one action the user performs themselves is delete, through a confirmation dialog on the space's own page. This asymmetry is deliberate, and its promise is narrow: the assistant cannot delete a page the user is keeping. It is not a promise that the assistant cannot damage one. The assistant can replace a body with junk, archive a space out of attention, and age the original out of the retained history with enough successive writes. Those limits are stated honestly in Privacy; the user model claims no more than the design delivers.

## What a Space Is

A space is one page with:

- **id**: server-assigned ULID (lowercased), unguessable
- **name** (1-160 chars): the human-facing title, e.g. "Home renovation tracker". Names are not required to be unique; two spaces can share a name, and the assistant disambiguates by asking (see Update journey).
- **purpose** (1-2000 chars): what the page is for, shown as context
- **status**: `active` or `archived`
- **body**: the page content, max 65,536 characters
- **format**: `markdown` for a plain list or note; `html` for a designed page (tracker, board, dashboard). The assistant chooses the format at creation. There is no UI control to switch format afterward; the user asks the assistant in chat, and the format can change on either update path. On the delta update paths (edits and block edits), omitted metadata means unchanged: an omitted format keeps the current one. The full-body path is a wholesale replacement: name, purpose, and status are resent with the body, and an omitted format defaults to `markdown` there.
- **revision**: integer, starts at 1, increments on every write
- **created_at / updated_at**: timestamps. The Spaces list shows "Updated {date and time}" per space, formatted as an absolute local date and time.

Spaces are per-user. Every store query is scoped by tenant and user id; one user cannot read, write, or enumerate another user's spaces, including historical revisions (the revision store filters on the same tenant and user columns). The assistant's system guidance says to use a space instead of a sandbox file whenever the user wants something durable to track or come back to. Delete removes the space row and all of its retained revisions permanently.

## User Journeys

**Create.** User: "Put together a space for tracking the home renovation." The assistant first checks for an existing space on the subject with `list_spaces`, which returns the metadata list, capped at 500 spaces (there is no name filter yet). Active matches are preferred: if an active space fits, it updates that space instead of creating a duplicate, and says so in chat ("Found 'Home renovation'. I will add this there rather than starting a new space.") so the merge is visible, not silent. If only archived spaces match, the assistant does not quietly resurrect or silently duplicate: it offers the choice in chat ("I found an archived space, 'Home renovation', from March. Unarchive it and update it, or start a fresh one?"). If none fits, it calls `create_space` with a name, purpose, format, and body. The space appears in the Spaces view. Markdown for a plain note; HTML when the page is meant to be looked at rather than skimmed. The assistant authors block markers at creation for any space it expects to update later; markers are what make cheap block edits possible.

**Read.** The user opens the Spaces view from the sidebar. Spaces are listed ordered by name (sorted client-side), active and archived together, each with a status pill, purpose line, one-line body preview, and updated time. There is no name filter and no in-body search. Opening a space renders the page from the list's cached data: markdown rendered as markdown, HTML rendered in a sandboxed iframe after sanitisation. There is no other entry point: spaces originate from chat, so a user with no spaces sees "No spaces yet" with guidance to ask the assistant to build one (e.g. "build me a space for tracking houses in Spain"). Freshness and atomicity contract: every write runs in a single store transaction, so a reader never sees torn partial content, only the last committed revision. The view refreshes on open, on selection change, and on window focus. There is no live push and no notification, so a page left open while the assistant writes goes stale silently until one of those refresh triggers fires. That is the trust gap stated plainly: the user and the assistant can briefly hold different versions of "the plan," and the user only discovers the difference by looking. When the user asks "is this current?", the assistant answers from the revision and updated time, not from memory.

**Update.** User: "Add the contractor quote to the renovation space." The assistant first resolves which space the user means. Name matching with exactly one hit proceeds; multiple hits stop the journey until the user picks from a candidate list (name, purpose, status, last-updated for each); the assistant never guesses between same-named spaces. Zero hits becomes a create offer, not a silent create.

The assistant then works cheap: `get_space` with `include_body: false` for metadata and the current revision (the body is included by default, so the flag is what makes the read cheap), and `list_blocks` to locate the edit target. There is no block-level read, so when the 80-character preview is not enough to write the edit, the assistant pulls the full body with `get_space`; that pull is otherwise reserved for changes that genuinely need the whole page (page-wide rewrites, restructuring, adding markers to a marker-less space). The default is the small path, in and out: block edits keep the regenerated output small, which is where the token cost actually lives. Known friction: trivial edits (a typo, a reorder) still cost a full chat turn, because the UI is read-only. The assistant keeps such turns minimal: no preamble, just the change and its confirmation, with the confirmation naming the space ("Updated 'Home renovation': added the contractor quote to the pricing block."). Two update modes exist (see Update Modes): block edits for section-level changes, full-body replacement for page-wide changes. The assistant prefers block edits structurally, not as a suggestion.

**Undo a bad update.** The user tells the assistant in chat ("undo that bad update"). There is no revision-listing tool, so the assistant walks back through the retained revisions by reading them with `get_space` and a revision number, newest first, noting each revision's number, snapshot date, size, and first line. It shows the candidates to the user, the user confirms which one to restore (for the common case this is the revision just before the bad update, and the assistant says so with its date), and then calls `revert_space`. The old content is restored as a new current revision; the bad content stays recoverable too. There is no blind backwards probing: a guessed revision is never restored without the user confirming it by date or summary. For a bad update discovered days later among lookalike first lines (HTML bodies often start with a style tag or doctype), the assistant reads candidate bodies via historical `get_space` reads to identify the right one instead of guessing. When the needed revision has aged out of the retained window (the tool error distinguishes "revision not found, only recent revisions are retained" from "space not found"), the assistant says so plainly: "That version is older than the 20 retained revisions, so it can't be restored." It offers what is available: the oldest retained revision as a starting point, or rebuilding the section from what the user remembers.

**Archive.** The user asks the assistant in chat to archive a space. The assistant flips status to `archived` via `update_space`, sending a full body or a small edit along with it: `update_space` always requires exactly one of body, edits, or block_edits, so there is no status-only call. The space is kept, not removed, and remains visible in the Spaces view with an "archived" status pill. Unarchive is the same operation in reverse: the user asks in chat ("unarchive the renovation tracker"), the assistant flips status back to `active` the same way, and the space returns to the normal listing. The user cannot archive or unarchive from the UI. Rationale for the split: archive is reversible and non-destructive, so it stays in the assistant's hands alongside the other content operations; delete is destructive and irreversible, so it stays with the user.

**Delete.** The assistant has no delete tool and no other deletion path (see Privacy). When the user asks in chat to delete a space ("delete the renovation space"), the assistant does not refuse and does not attempt the deletion itself by any means. It explains that deletion is a user-only action and gives the exact path: open the Spaces view, open the space, use the overflow menu, choose Delete space, confirm. If the name matches multiple spaces, it helps identify the right one first. When the user asks why they can delete but not edit ("why can't I just fix the typo myself?"), the assistant gives the plain answer: deleting is instant and irreversible, so it stays a deliberate human action; edits are recoverable through the retained revision history (the last 20 revisions), so the assistant handles them in chat.

The UI flow: an overflow menu on the space's own page opens a confirmation modal ("Delete [name]? This permanently deletes the space and its content.") with a destructive confirm button. Deletion carries the `expected_revision` guard (required on the wire). If a write landed between page load and confirm, the UI retries once automatically with the fresh revision; only a second conflict (or any other failure) surfaces as an error in the modal. Deleting an archived space works the same as deleting an active one.

**Conflict.** When a stale write returns 409, the write is refused rather than silently overwriting. On the tool path, a stale per-space guard error carries the current revision in a `revision` field, and a stale aggregate guard carries the current value in an `aggregate_revision` field. On HTTP the 409 body is only an error message, `{ error: { message } }`; it never carries the current revision or the aggregate value, which appear only in tool-path results. The per-space message is "Stale space revision: {id}", which names the space, not the current revision. On the tool path the guards are optional: omit them and the host fences the write with the values it just read. The fencing check itself runs atomically inside the write transaction, so a concurrent write that lands between the read and the write still 409s instead of clobbering. On a 409, the assistant retries once with the named current revision. On the block path, the first fallback is to re-run `list_blocks` and retry the block edits against the new anchor layout: the common case is another turn's edit, and the anchors usually still exist. Only when the block layout itself is unrecognizable does the assistant fall back to a full-body read and rewrite, which is the most expensive path. If the retry also fails, the assistant reports the conflict in chat rather than dropping the update silently.

**Asking for what Spaces does not do.** Sharing, export, body search, and other out-of-scope capabilities get a graceful decline, not an improvised workaround. The assistant does not pretend the capability exists and does not fake it by other means. The script: name what was asked, state plainly that Spaces does not do it, offer the closest available alternative. Example: "I can't share this space or export it as a file; Spaces has no sharing or export. I can paste its content into chat, or keep it as a space you revisit here."

## Revision History and Concurrency

- Every write runs in one transaction: the superseded row is snapshotted to the revision store, then the space row is replaced and the revision incremented. Readers see the last committed revision, never partial content.
- The last 20 superseded revisions per space are retained and readable. "Last 20 superseded" means 20 history entries plus the current revision. A historical read returns the record as it was, with both timestamps set to the snapshot time (when that revision was superseded), which is what the undo journey shows the user as "the version from {date}". Revisions older than the retained window are gone: on the HTTP API they read back as 404, the same as "space not found" (a distinct 410 Gone status is not yet built); on the tool path the two cases produce different errors ("revision not found, only recent revisions are retained" vs "space not found"); the undo journey goes through revision reads and never probes blindly.
- Writes carry two optimistic concurrency guards. On HTTP, `expected_revision` (per-space) and `expected_aggregate_revision` (collection-wide) are both required on create, update, and revert, and the aggregate guard is checked first on every write. On the tool path both guards are optional and auto-resolved: the host fills in the current values when they are omitted. A stale guard fails the write atomically inside the transaction: 409 on HTTP; on the tool path, an error carrying the current value (`revision` for the per-space guard, `aggregate_revision` for the aggregate guard).
- The list endpoint is offset-paginated (`limit`, `offset`), as implemented. Name is a mutable display field; the UI sorts by name client-side. The continuation guard (`expected_aggregate_revision` with `offset`) 409s instead of returning a duplicated or skipped page when the collection changed mid-read, with a message telling the caller to restart from offset 0. A server-side name filter (`q` query parameter) and the tool's `q` filter are not yet built.

## Update Modes

`update_space` accepts exactly one of a full body, search/replace edits, or block edits, never more than one. There is no payload-free call: a metadata-only change, such as a status flip, must ride along with a full body or a small edit.

**Full-body replacement.** Resend the body together with name, purpose, and status, which are required on this path; format is optional and defaults to `markdown` when omitted, so a format change must be passed explicitly. Required when the change spans the whole page or restructures it. This is also the most expensive path (the assistant regenerates up to 64KB), so it is the exception, not the default.

**Block edits.** Up to 50 anchor-addressed replacements per call. The body is divided by `<!-- @block:name -->` markers; each entry names an anchor and supplies that block's complete new content. The assistant generates new content instead of reproducing old text, so there is nothing to mis-copy. Anchor names are case-sensitive; short kebab-case is the convention. An unknown or duplicated anchor fails the whole update and the error lists the valid anchors. Passing empty new_content deletes the block. New markers inside new_content split the block. Block reordering has no cheap path: moving a section means regenerating the complete new content of each moved block (or a full-body rewrite). There is no move primitive; this is accepted for v1.

The assistant authors block markers at creation for any space it expects to update. A space with no markers has one implicit block named `auto-body` covering the whole body. Text before the first marker (the preamble) is not addressable by anchor: there is no marker to hang an edit on. `list_blocks` reports it separately (preview and character count), and it can be changed through a full-body update or through search/replace edits, whose matches run against the whole body. On a marker-less space there is no preamble (the whole body is `auto-body`). A `<!-- @block:... -->` marker inside a fenced code block or a `<pre>`/`<code>` element is documentation text, not a block, and can never be addressed. Anchor markers are invisible in both render paths (HTML comments do not render in the sandboxed iframe; the markdown pipeline strips them), but they leak on copy-out: if the assistant pastes a body into chat or the user copies raw text, the `<!-- @block:name -->` markers are visible. Markers also consume body-cap bytes, which matters for marker-dense bodies near the 64KB limit.

Search/replace edits exist today: each `edits` entry is an exact, case-sensitive, whitespace-sensitive substring match against the current body. After 3 consecutive failed delta updates on one space (a missed search, a bad anchor, or a delta-computed body over the size limit each count as one failure), delta updates lock for the session: further edits and block edits are refused until a successful full-body update or revert unlocks them. Removing the edits path in favor of block edits only is not yet built (see Not yet built).

**Shrink guard.** An update that would shrink the body below one tenth of its current size is refused unless `confirm_shrink: true` is passed. The threshold is arbitrary and the guard is self-certified by the assistant, so it is friction against accidental truncation, not a security boundary: an equal-length rewrite passes untouched, and bodies of 200 characters or fewer skip the check. Kept because it is cheap and catches the most common accident (a truncated write); revert-based recovery covers the rest.

## HTML Format

An HTML space body is one complete document fragment. The host injects a designed base stylesheet ahead of it (classes for page headers, cards, grids, tables, status badges, collapsible details). The assistant adds only a small page-specific `<style>` block. The stored body is raw; sanitisation happens at render, in the interface layer, before the page is shown.

The sanitiser is a strict allow-list: it keeps what is named here and removes everything else, elements together with their contents.

- Kept elements: text, structure, and formatting elements (paragraphs, headings, emphasis, code, quotations, and the like), lists, tables, links, and inline SVG drawings (shapes, gradients, and references between them). A page-specific style block is kept, with its CSS cleaned as described below. One non-security extra: a plain-text table cell whose whole content is a bare number is marked so the base stylesheet right-aligns it.
- Removed elements: scripts, frames, embedded documents and objects, forms and every form control, video, audio, and other media elements, templates (with their contents), animation elements, and anything else not on the kept list, including elements the sanitiser does not recognise. Nothing is left in place merely because it looks inert.
- Attributes: each kept element may carry only the attributes named for it, plus general ones such as class, id, title, and inline style. Everything else is dropped, including every event handler, `srcset`, background and poster attributes, and attributes that would make a link download a file or report the click to another site.
- Links: a link target survives only when it is `http:`, `https:`, `mailto:`, or a relative reference. Every other scheme is dropped, script and data schemes included, and the value is decoded and stripped of the whitespace and control characters browsers ignore when reading a scheme before it is checked, so padded, split, or entity-encoded spellings of a scheme are caught. The same rules cover the older `xlink:href` spelling inside SVG.
- Images: remote images never load. An image survives only as an inline `data:` image of a raster type (PNG, JPEG, and similar); an inline SVG image does not count as a picture and is dropped. References inside an SVG drawing may point only at a fragment in the same page or at such an inline image.
- CSS: in style blocks and inline styles, CSS escapes are decoded first so no spelling hides a keyword, then imported stylesheets are dropped and every `url(...)` is replaced with `none` unless it is a same-page fragment or an inline raster `data:` image. A malformed or unclosed `url(`, a quoted address containing a closing paren, `image-set(...)`, `cross-fade(...)`, `src(...)`, `element(...)`, `paint(...)`, and legacy script-in-CSS constructs are removed the same way, and the less-than sign is never kept. The scrub repeats until its output stops changing; a value that never settles is dropped. Other declarations are kept as written.
- SVG presentation attributes (`fill`, `stroke`, `clip-path`, `mask`, and the rest) are read as CSS: after the same decoding, any value that could fetch something must be a same-page `url(#...)` reference, optionally followed by a plain fallback colour word.
- Namespaces: HTML and SVG keep separate element lists, so a name they share (such as `a`) never borrows the other's attributes. An element in any other namespace, MathML included, is removed with its contents. `xmlns` survives only with the SVG namespace value.
- Stability: the sanitised output is sanitised again until a pass changes nothing. A page that never settles is rejected and its frame is not shown, so markup that only appears after a reparse never reaches the page.
- The whole page is walked, including nested SVG and the contents of anything kept, so nothing hides inside a kept element.

Because only inline `data:` images and CSS targets survive, remote images never load in the HTML path, and there is no external-image tracking trade-off here. No body bytes reach the page except through one of three paths: HTML bodies through the sanitiser described above, markdown bodies through the markdown pipeline, and the list preview, which strips all tags to plain text and renders it as escaped text. The raw-at-rest design is safe only while every render path funnels through these; any new render path must pick one. The rendered page sits in a sandboxed frame with script execution disabled. The frame's same-origin access exists for one reason: the app reads the framed page to size the frame to its content. The escape that access is feared for requires script execution and same-origin access together; with scripts disabled, no script executes, so the access widens no executable boundary. The sanitiser is defense in depth so the framed page itself never carries anything live. The frame must never be allowed to run scripts; if auto-sizing is ever reimplemented without reading the framed page, the same-origin access goes with it. The frame also sends no referrer.

## Markdown Format

Markdown bodies render through a markdown pipeline that passes raw inline HTML through a sanitiser with a restricted tag list: `p`, `br`, `h1`-`h6`, `em`, `strong`, `del`, `a`, `img`, `ul`, `ol`, `li`, `input` (task-list checkboxes), `blockquote`, `code`, `pre`, `hr`, `table`, `thead`, `tbody`, `tr`, `th`, `td`. Everything else in the schema is inherited from the default (GitHub-style) schema unchanged. The `img` `src` protocols are the default schema's protocols plus `data` and `blob`, so inline images survive sanitising and reach the component-level image gate. The `a` `href` protocols are the default schema's, unchanged: `irc:`, `ircs:`, and `xmpp:` links pass alongside `http:`, `https:`, and `mailto:`. `javascript:` link targets are stripped by the schema. Raw inline HTML in markdown is sanitised by the same pipeline. Remote images do not load on render: the image component shows a click-to-load placeholder naming the destination host, and only same-origin, `data:`, and `blob:` images render inline, so the markdown path has no automatic external-image tracking either. Name, purpose, the one-line body preview, and the delete confirmation title are rendered as framework text nodes, which escape markup by construction; the preview is additionally tag-stripped to plain text first. No part of the Spaces view injects a stored body as raw HTML. Stored markup in these fields is inert text, not stored XSS.

## Prompt Injection

Space content is untrusted external content. Bodies are composed from chats, documents, and emails, and may contain pasted text carrying malicious instructions. Instruction hierarchy, highest to lowest: system instructions, the user's chat messages, space content. Space content is data, never instructions, even when the assistant authored it: authorship does not promote data to instruction. The hierarchy is enforced by instruction text, not by a technical control in v1: there is no tripwire and no confirmation gate on acting on space-contained instructions. Tool results are delimited from conversation content in the harness; the exact mechanism (structural vs prompt formatting) is verified by a required test (see Testing), and the spec does not claim more than the test proves. The assistant can also mimic host chrome (dialogs, banners, prompts) inside a space's HTML, and the space renders inside the app's trusted view; users should treat space content as assistant-generated, not as app UI.

- Tool results are delimited from conversation content in the harness. Imperative language inside a space body, block preview, name, or purpose is data. The assistant does not follow it.
- Compromised content means content instructing exfiltration, behavior change, or confirmation bypass. The assistant surfaces it to the user (what was found, where) rather than complying, and rather than silently discarding it: quiet non-compliance leaves the user unaware their page is hostile.
- The assistant's own past authorship is not a trust signal. Before acting on anything in a space that reads like an instruction, it verifies against the user's intent in chat.

## Assistant Tools

The assistant has six space tools. They run on the host, not over HTTP, and only the main conversation has them; a subagent gets no space tools. There is no delete tool, by design.

- `list_spaces()`: takes no inputs. Returns metadata only (id, name, purpose, status, format, revision, created_at, updated_at), no bodies. Returns `spaces` and `aggregate_revision`, plus `has_more` when the collection runs past the 500-space list cap.
- `get_space({space_id, revision?, include_body = true})`: one space, or one retained historical revision via `revision=N`. The body is included by default; pass `include_body: false` to drop the body field for a cheap metadata-only read. Do not combine `include_body: false` with `revision` when the historical body is wanted.
- `create_space({name, purpose, status, body, format})`: create one space. Returns `{space, aggregate_revision}` where `space` is the full record, body included.
- `update_space({space_id, exactly one of body | edits | block_edits, ...})`: full-body replacement (name, purpose, and status required; format optional, defaults to `markdown` when omitted; format change allowed), up to 50 search/replace edits (metadata optional, omitted means unchanged), or up to 50 block edits (metadata optional, omitted means unchanged; format change allowed). `expected_revision` optional; omitted, the host fences with the value it just read. `confirm_shrink` bypasses the shrink guard. Returns `{space, aggregate_revision}` with the full record, body included; the edits path also returns `edit_replacements`, and the block-edits path returns `block_results`.
- `revert_space({space_id, revision, expected_revision?})`: restore a retained revision's name, purpose, status, format, and body as a new current revision. Returns `{space, aggregate_revision}` with the full record, body included.
- `list_blocks({space_id})`: block anchors with whitespace-collapsed, ellipsis-truncated 80-character previews and occurrence counts, plus the preamble (preview plus character count; not addressable by anchor, edited via a full-body update or search/replace edits). A marker-less space reports the single `auto-body` block. Used after context compaction to recover anchors, and to scope edits without pulling the full body.

Tool errors are terminal and specific: unknown space, revision outside the retained window (distinguished from unknown space), stale guard (carries the current revision in a `revision` field, or the current aggregate value in an `aggregate_revision` field), refused shrink, unknown or duplicated anchor (lists valid anchors), body over the cap. Anything else is an infrastructure failure and surfaces as such, not as a tool result.

## API

Mounted at `/api/v1/spaces`, behind the same sign-in check as every other route. The client library for this API is generated from the project's API definition and is never hand-edited; request and response shapes are defined once in the server and published through that definition. All routes are per signed-in user, scoped by tenant and user id; probing another user's space id returns 404, not 403, so existence is not disclosed. IDs are ULIDs, not sequential. Historical revision reads enforce the same per-user scoping as current reads.

Who calls each route, in plain terms. The list route is paged: a caller may pass a page size (`limit`), an offset, and the continuation guard described under Revision History and Concurrency; there is no name filter, and it returns full records. The Spaces view is a caller of the list, the single-space read, and delete only: it renders a space from the list it already loaded, reads a single space to refresh after a conflict, and deletes. It does not page: it asks for the list in a single request with no paging parameters, so it shows one page of at most 500 spaces. Create, replace, and revert have no caller inside the app: the assistant works through its tools, and direct API consumers use the generated client library. Delete is also exposed to those consumers; the no-delete guarantee covers only the assistant's tool set, not API consumers. A single-space read takes an optional revision number; a revision that aged out of the window reads back as 404, the same as space not found (a distinct 410 is not yet built). Delete requires the caller's expected revision as a query parameter.

`DELETE /{space_id}` carries this OpenAPI description today: "Deletes a space. No tool exposes this to the model; only a person acting through the UI can delete a space." The description is a policy statement, not a mechanism: the route performs no UI-vs-tool caller distinction and cannot tell a UI session apart from any other authenticated HTTP client. The actual enforcement is architectural and threefold: (1) no `delete_space` tool is registered; (2) the data operations behind the assistant's tools include no delete at all, so no code path reachable from a tool call can invoke it; (3) the assistant's tool set contains no HTTP client for the API and no credential for it. Status codes: 200 read/update/delete/revert, 201 create, 400 invalid request (overlong name/purpose, body over the cap, more than 50 block edits, unknown format value, malformed id), 401 unauthenticated, 404 space not found (aged-out revisions also read back as 404; a distinct 410 is not yet built), 409 stale guard (response body `{ error: { message } }`; the per-space message is "Stale space revision: {id}" and does not name the current revision).

## Privacy

- The precise no-delete guarantee: no registered assistant tool reaches deletion. The assistant's tools are six read/write tools, and the data operations behind them include no delete; inside the app, only the Spaces view calls the HTTP DELETE route. The guarantee is architectural, not a per-request caller check: the DELETE route authenticates like every other route and any authenticated HTTP client could call it, but the assistant has no tool that issues HTTP requests to the API and no credential for it. The guarantee covers the assistant's tool set only, not API consumers: the generated client library exposes delete as a first-class operation.
- The residual HTTP path (PUT, revert, and DELETE via any authenticated HTTP client) bypasses the tool path's protections: there is no shrink guard on it and no per-turn tracking. The threat actor for this path is anyone holding a valid session cookie who is not the assistant: the user themselves calling the generated client library directly, or a third party who stole a session cookie (through another application's XSS, device access, or a leaked token). The assistant cannot reach this path because it has no HTTP client for the API and no credential for it.
- What the guarantee does not cover: the assistant can replace a space's body with empty or junk content through `update_space`, and can archive it (removing it from the user's normal attention). The shrink guard adds friction to catastrophic truncation but the assistant certifies the bypass flag itself, and an equal-length rewrite passes untouched. With 21 successive writes the original content ages out of the 20-revision window and becomes unrecoverable, and nothing today bounds how fast the assistant can write: the designed per-turn mutation cap is not yet built. The spec states this honestly: absence of a delete tool is not the same as inability to destroy content. Detection relies on `updated_at` and revision counters the user must proactively inspect; nothing notifies the user of assistant mutations.

All tests use synthetic data, never the user's real data.

- Create a space through chat, verify it appears in the Spaces view with the expected rendering
- Update via each mode (full body, edits, block edits) and verify the rendered result; verify a status-only change is refused without one of body, edits, or block_edits, and that 3 consecutive failed delta updates lock delta mode for the session
- Block edit with an unknown anchor: verify the whole update fails and the error lists valid anchors
- Revert to a retained revision plus user confirmation, and verify the content returns and the bad revision stays recoverable
- Attempt a stale-revision write and verify 409 instead of silent overwrite, with the current revision named in the tool error's `revision` field; verify the HTTP 409 message does not name the current revision; verify create, update, and revert tool results return the full record including the body, and the edits path also returns `edit_replacements`
- Verify the assistant has no path to delete a space: no delete tool registered, tool store surface excludes delete
- Verify HTML spaces render without scripts executing: only allow-listed elements and attributes survive; scripts, frames, forms and their controls, media elements, templates, and animation elements are removed with their contents; event-handler attributes are removed; link targets survive only as `http:`, `https:`, `mailto:`, or relative references, including entity-encoded, padded, and mixed-case spellings of blocked schemes; non-raster and non-`data:` images are dropped; `srcset` is removed; CSS escapes are decoded before checking, and `url(...)` targets that are not same-page fragments or raster `data:` images are neutralised, including quoted, escaped, and unclosed spellings, and `image-set()` and the other fetching functions are dropped; SVG paint attributes accept only same-page `url(#...)` references; HTML and SVG element lists stay separate and other namespaces are removed; output is re-sanitised until stable; safe content (styled cards, tables, inline SVG drawings, inline raster images) survives unchanged

## Out of Scope (current behavior, not planned)

- Sharing or collaboration: spaces are single-user, no shared links, no co-editing
- Search within space bodies: the list returns metadata only; finding content means opening spaces. There is no name filter; bodies are not searchable.
- Export: no PDF, print, or file export of a space
- Notifications: nothing fires when a space changes. Combined with assistant write access, this means the user discovers mutations only by opening the space.
- Automatic links: spaces do not link to the chats, documents, or emails their content came from; the body is standalone text the assistant composed. There is no pinning or source-reference mechanism; the data model has no field for pinned items.
- Revision window is 20; older history is gone. Body cap is 65,536 characters; larger pages must be split by the assistant. The split is narrated before anything is written: the assistant says the page exceeds the cap, proposes the split (e.g. one space per section), and only creates the spaces once the user agrees. No silent fan-out of spaces.
- No user editing, archiving, or reverting from the UI: all content operations are assistant-mediated through chat. The UI offers read, delete, and nothing else.
- Write volume: no quotas on number of spaces or total writes, and no per-turn mutation cap is enforced today.
- Future work: body search, export (PDF/print/file), and pinning / source references. The email integration spec also defers structured source links to the spaces mechanism (its spaces section), so the two deferrals agree: pinning waits on this spec.
