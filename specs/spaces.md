# Spec: Spaces

**Status:** partly implemented

Normative contract for the Spaces feature as shipped.

## Not yet built

The following are designed but not implemented on main today:

- **Context budgets.** The 8,000-token per-call budget, the 24,000-token per-turn aggregate budget, and the `budget_exceeded` refusal shape are not enforced. The server enforces only the 65,536-character body cap.
- **Mutation cap.** The per-turn cap of 5 space mutations is not enforced.
- **`read_block` tool.** Not registered. Block-level reads go through `get_space` today.
- **`list_revisions` tool.** Not registered. Revision history is readable via `get_space` with a revision parameter.
- **List filter and pagination.** `list_spaces` takes no inputs today: no name filter `q`, no `offset`/`limit` pagination, no `has_more`/`next_offset`. The name filter and pagination are designed but not implemented.
- **410 for aged-out revisions.** Aged-out revisions read back as 404 today, the same as "space not found". A distinct 410 Gone status is designed but not implemented.
- **Removing search/replace edits.** `update_space` still accepts search/replace `edits` today. Removing the edits path in favor of block edits only is designed but not implemented.

The Context Budgets section below describes the intended design, not current behavior.

## Problem

Chat conversations scroll away. When the user wants something durable to track or come back to, a plan, a tracker, a board, a research page, the chat transcript is the wrong container: it mixes the artifact with the conversation that produced it and buries it under later turns.

## Solution

Spaces: persistent, named, structured pages the assistant creates and keeps current. A space survives the turn and session that created it and is visible in the Spaces view without the user opening the chat that produced it. The user asks for one in plain language ("Put together a space for tracking the home renovation"), the assistant builds it, and the user reads and revisits it from the Spaces view.

## User Model

Spaces are assistant-authored and user read-only in the UI. The user creates, updates, archives, and reverts spaces by asking the assistant in chat; the assistant performs those actions through its tools. The user cannot type into a space, cannot edit its content directly, and cannot archive or revert from the UI. The one action the user performs themselves is delete, through a confirmation dialog on the space's own page.

This asymmetry is deliberate, and its promise is narrow: the assistant cannot delete a page the user is keeping. It is not a promise that the assistant cannot damage one. The assistant can replace a body with junk, archive a space out of attention, and age the original out of the retained history with enough successive writes. Those limits are stated honestly in Privacy; the user model claims no more than the design delivers.

## What a Space Is

A space is one page with:

- **id**: server-assigned ULID (lowercased), unguessable
- **name** (1-160 chars): the human-facing title, e.g. "Home renovation tracker". Names are not required to be unique; two spaces can share a name, and the assistant disambiguates by asking (see Update journey).
- **purpose** (1-2000 chars): what the page is for, shown as context
- **status**: `active` or `archived`
- **body**: the page content, max 65,536 characters
- **format**: `markdown` for a plain list or note; `html` for a designed page (tracker, board, dashboard). The assistant chooses the format at creation. There is no UI control to switch format afterward; the user asks the assistant in chat, and the format can change on either update path. On the delta update paths (edits and block edits), omitted metadata means unchanged: an omitted format keeps the current one. The full-body path is a wholesale replacement: name, purpose, and status are resent with the body, and an omitted format defaults to `markdown` there.
- **revision**: integer, starts at 1, increments on every write
- **created_at / updated_at**: timestamps. The Spaces list shows "Updated {relative time}" per space.

Spaces are per-user. Every store query is scoped by tenant and user id; one user cannot read, write, or enumerate another user's spaces, including historical revisions (the revision store filters on the same tenant and user columns). The assistant's system guidance says to use a space instead of a sandbox file whenever the user wants something durable to track or come back to.

Delete removes the space row and all of its retained revisions permanently.

## User Journeys

Note: journeys that mention `read_block` or `list_revisions` describe the intended design. Those tools are not yet built (see Not yet built above); the journeys are kept to document the target behavior.

**Create.** User: "Put together a space for tracking the home renovation." The assistant first checks for an existing space on the subject with `list_spaces`, which returns the full metadata list (there is no name filter yet). Active matches are preferred: if an active space fits, it updates that space instead of creating a duplicate, and says so in chat ("Found 'Home renovation'. I will add this there rather than starting a new space.") so the merge is visible, not silent. If only archived spaces match, the assistant does not quietly resurrect or silently duplicate: it offers the choice in chat ("I found an archived space, 'Home renovation', from March. Unarchive it and update it, or start a fresh one?"). If none fits, it calls `create_space` with a name, purpose, format, and body. The space appears in the Spaces view. Markdown for a plain note; HTML when the page is meant to be looked at rather than skimmed. The assistant authors block markers at creation for any space it expects to update later; markers are what make cheap block edits possible.

**Read.** The user opens the Spaces view from the sidebar. Spaces are listed ordered by name (sorted client-side), active and archived together, each with a status pill, purpose line, one-line body preview, and updated time. There is no name filter and no in-body search. Opening a space renders the page from the list's cached data: markdown rendered as markdown, HTML rendered in a sandboxed iframe after sanitisation. There is no other entry point: spaces originate from chat, so a user with no spaces sees "No spaces yet" with guidance to ask the assistant to build one (e.g. "build me a space for tracking project milestones").

Freshness and atomicity contract: every write runs in a single store transaction, so a reader never sees torn partial content, only the last committed revision. The view refreshes on open, on selection change, and on window focus. The implementers are `SpaceProvider.load` in `server/SpaceContext.tsx` (provider mount plus window `focus` and document `visibilitychange` listeners) and the `SpacesView` effect that calls the provider's `refresh` on every open and every selection change, covering the normal loop where chat creates a space and this view opens without the tab ever losing focus. There is no live push and no notification, so a page left open while the assistant writes goes stale silently until one of those refresh triggers fires. That is the trust gap stated plainly: the user and the assistant can briefly hold different versions of "the plan," and the user only discovers the difference by looking. When the user asks "is this current?", the assistant answers from the revision and updated time, not from memory.

**Update.** User: "Add the contractor quote to the renovation space." The assistant first resolves which space the user means. Name matching with exactly one hit proceeds; multiple hits stop the journey until the user picks from a candidate list (name, purpose, status, last-updated for each); the assistant never guesses between same-named spaces. Zero hits becomes a create offer, not a silent create.

The assistant then works cheap: `get_space` with `include_body: false` for metadata and the current revision (the body is included by default, so the flag is what makes the read cheap), `list_blocks` to locate the edit target, and `read_block` to read one block's full content when the 80-character preview is not enough to write the edit. A full-body `get_space` pull is reserved for changes that genuinely need the whole page (page-wide rewrites, restructuring, adding markers to a marker-less space). The default is the small path, in and out: block reads and block edits keep both the read and the regenerated output small, which is where the token cost actually lives.

Known friction: trivial edits (a typo, a reorder) still cost a full chat turn, because the UI is read-only. The assistant keeps such turns minimal: no preamble, just the change and its confirmation, with the confirmation naming the space ("Updated 'Home renovation': added the contractor quote to the pricing block.").

Two update modes exist (see Update Modes): block edits for section-level changes, full-body replacement for page-wide changes. The assistant prefers block edits structurally, not as a suggestion.

A single block over the per-call budget has no tool read or write path (`read_block` refuses it, and a block edit would carry the block's full content as payload). The assistant script is the same honest recovery as the marker-less over-budget case: say so plainly, read alongside the user in the Spaces view, and rebuild from pasted chunks with markers added so the new blocks stay under the budget.

**Undo a bad update.** The user tells the assistant in chat ("undo that bad update"). The assistant calls `list_revisions`, which returns the retained revisions newest-first with each revision's number, snapshot date, size, and first line. It shows the candidates to the user, the user confirms which one to restore (for the common case this is the revision just before the bad update, and the assistant says so with its date), and then calls `revert_space`. The old content is restored as a new current revision; the bad content stays recoverable too. There is no blind backwards probing: a guessed revision is never restored without the user confirming it by date or summary. For a bad update discovered days later among lookalike first lines (HTML bodies often start with a style tag or doctype), the assistant reads candidate bodies via `read_block` with the candidate `revision`, or historical `get_space` reads, to identify the right one instead of guessing. `read_block` takes an optional `revision` parameter (revision omitted means the current revision) precisely so the undo journey can read a historical block without pulling the historical full body. When the needed revision has aged out of the retained window (the tool error distinguishes "revision not found, only recent revisions are retained" from "space not found"), the assistant says so plainly: "That version is older than the 20 retained revisions, so it can't be restored." It offers what is available: the oldest retained revision as a starting point, or rebuilding the section from what the user remembers.

**Archive.** The user asks the assistant in chat to archive a space. The assistant flips status to `archived` via `update_space`. The space is kept, not removed, and remains visible in the Spaces view with an "archived" status pill. Unarchive is the same operation in reverse: the user asks in chat ("unarchive the renovation tracker"), the assistant flips status back to `active` via `update_space` with `expected_revision`, and the space returns to the normal listing. The user cannot archive or unarchive from the UI. Rationale for the split: archive is reversible and non-destructive, so it stays in the assistant's hands alongside the other content operations; delete is destructive and irreversible, so it stays with the user.

**Delete.** The assistant has no delete tool and no other deletion path (see Privacy). When the user asks in chat to delete a space ("delete the renovation space"), the assistant does not refuse and does not attempt the deletion itself by any means. It explains that deletion is a user-only action and gives the exact path: open the Spaces view, open the space, use the overflow menu, choose Delete space, confirm. If the name matches multiple spaces, it helps identify the right one first.

When the user asks why they can delete but not edit ("why can't I just fix the typo myself?"), the assistant gives the plain answer: deleting is instant and irreversible, so it stays a deliberate human action; edits are recoverable through the retained revision history (the last 20 revisions), so the assistant handles them in chat.

The UI flow: an overflow menu on the space's own page opens a confirmation modal ("Delete [name]? This permanently deletes the space and its content.") with a destructive confirm button. Deletion carries the `expected_revision` guard (required on the wire). If a write landed between page load and confirm, the UI retries once automatically with the fresh revision; only a second conflict (or any other failure) surfaces as an error in the modal. Deleting an archived space works the same as deleting an active one.

**Conflict.** When a stale write returns 409, the write is refused rather than silently overwriting. The 409 names the current revision: on the tool path the error carries a `revision` field with the current revision; on HTTP the response body is `{ error: { message } }` and the stale-guard message names the current revision (the message naming is a required change). On the tool path the guards are optional: omit them and the host fences the write with the values it just read. The fencing check itself runs atomically inside the write transaction, so a concurrent write that lands between the read and the write still 409s instead of clobbering.

On a 409, the assistant retries once with the named current revision. On the block path, the first fallback is to re-run `list_blocks` and retry the block edits against the new anchor layout: the common case is another turn's edit, and the anchors usually still exist. Only when the block layout itself is unrecognizable does the assistant fall back to a full-body read and rewrite, which is the most expensive path and may itself hit the per-call budget. If the retry also fails, the assistant reports the conflict in chat rather than dropping the update silently.

**Asking for what Spaces does not do.** Sharing, export, body search, and other out-of-scope capabilities get a graceful decline, not an improvised workaround. The assistant does not pretend the capability exists and does not fake it by other means. The script: name what was asked, state plainly that Spaces does not do it, offer the closest available alternative. Example: "I can't share this space or export it as a file; Spaces has no sharing or export. I can paste its content into chat, or keep it as a space you revisit here."

## Revision History and Concurrency

- Every write runs in one transaction: the superseded row is snapshotted to the revision store, then the space row is replaced and the revision incremented. Readers see the last committed revision, never partial content.
- The last 20 superseded revisions per space are retained and readable. "Last 20 superseded" means 20 history entries plus the current revision. A historical read returns the record as it was, with both timestamps set to the snapshot time (when that revision was superseded), which is what the undo journey shows the user as "the version from {date}".
- Revisions older than the retained window are gone. On the HTTP API they read back as 404, the same as "space not found" (a distinct 410 Gone status is not yet built). On the tool path the two cases produce different errors ("revision not found, only recent revisions are retained" vs "space not found"); the undo journey goes through `list_revisions` and never probes blindly.
- Writes carry one optimistic concurrency guard: `expected_revision` (per-space, checked atomically in the write's WHERE clause). The collection-wide `expected_aggregate_revision` survives only as the list-continuation guard, not on writes (required change). On the tool path the guard is optional and auto-resolved; the remaining race between resolve and write is closed by the atomic check, which 409s and names the current revision.
- The list endpoint is offset-paginated (`limit`, `offset`), as implemented. Name is a mutable display field; the UI sorts by name client-side. The continuation guard (`expected_aggregate_revision` with `offset`) 409s instead of returning a duplicated or skipped page when the collection changed mid-read, with a message telling the caller to restart from offset 0. A server-side name filter (`q` query parameter) and the tool's `q` filter are not yet built.

## Update Modes

`update_space` accepts exactly one of a full body, search/replace edits, or block edits, never more than one.

**Full-body replacement.** Resend the body together with name, purpose, and status, which are required on this path; format is optional and defaults to `markdown` when omitted, so a format change must be passed explicitly. Required when the change spans the whole page or restructures it. This is also the most expensive path (the assistant regenerates up to 64KB), so it is the exception, not the default.

**Block edits.** Up to 50 anchor-addressed replacements per call. The body is divided by `<!-- @block:name -->` markers; each entry names an anchor and supplies that block's complete new content. The assistant generates new content instead of reproducing old text, so there is nothing to mis-copy. Anchor names are case-sensitive; short kebab-case is the convention. An unknown or duplicated anchor fails the whole update and the error lists the valid anchors. Passing empty new_content deletes the block. New markers inside new_content split the block.

The assistant authors block markers at creation for any space it expects to update. A space with no markers has one implicit block named `auto-body` covering the whole body. Text before the first marker (the preamble) is not addressable by anchor: there is no marker to hang an edit on. `list_blocks` reports it separately (preview and character count), and it is edited only through a full-body update. On a marker-less space there is no preamble (the whole body is `auto-body`). A `<!-- @block:... -->` marker inside a fenced code block or a `<pre>`/`<code>` element is documentation text, not a block, and can never be addressed.

Block reordering has no cheap path: moving a section means regenerating the complete new content of each moved block (or a full-body rewrite). There is no move primitive; this is accepted for v1.

Anchor markers are invisible in both render paths (HTML comments do not render in the sandboxed iframe; the markdown pipeline strips them), but they leak on copy-out: if the assistant pastes a body into chat or the user copies raw text, the `<!-- @block:name -->` markers are visible. Markers also consume body-cap bytes, which matters for marker-dense bodies near the 64KB limit.

Search/replace edits exist today: each `edits` entry is an exact, case-sensitive, whitespace-sensitive substring match, with a size-change breaker and a consecutive-failure lock for the session. Removing the edits path in favor of block edits only is not yet built (see Not yet built).

**Shrink guard.** An update that would shrink the body below one tenth of its current size is refused unless `confirm_shrink: true` is passed. The threshold is arbitrary and the guard is self-certified by the assistant, so it is friction against accidental truncation, not a security boundary: an equal-length rewrite passes untouched, and bodies of 200 characters or fewer skip the check. Kept because it is cheap and catches the most common accident (a truncated write); revert-based recovery covers the rest.

## HTML Format

An HTML space body is one complete document fragment. The host injects a designed base stylesheet ahead of it (classes for page headers, cards, grids, tables, status badges, collapsible details). The assistant adds only a small page-specific `<style>` block. The stored body is raw; sanitisation happens at render.

The sanitiser (`sanitizeSpaceHtml`, UI layer) is denylist-based, not an allow-list: it removes what it knows is dangerous and keeps the rest. The required rules:

- Removes these elements entirely: `script`, `link`, `iframe`, `frame`, `frameset`, `applet`, `object`, `embed`, `meta`, `base`, `portal`, `fencedframe`, and additionally `form`, `input`, `button`, `select`, `textarea`, `video`, `audio`, `source`, `track`, plus the SMIL animation elements `animate`, `set`, `animateTransform`, `animateMotion`. Rationale for the additions: a space is a display-only page. Forms cannot submit under the sandbox (no `allow-forms`), so form controls are phishing chrome only. Video, audio, and their sources load external media outside the image-only fetch policy. `frame`/`frameset` are the siblings of `iframe`: a `<frameset><frame src="https://...">` body parses as a frameset document and loads the remote page on render with no click, silently breaking the freshness contract that rendered content is always the last committed revision. `portal` and `fencedframe` are the newer embed successors: both load remote documents on render like `iframe`. SMIL animation elements can rewrite URL attributes after the scheme check (a `<set attributeName="href" to="...">` inside SVG changes a sanitizer-approved link target at hover or click time). SVG-namespaced elements go through the same tag rules: a `<script>` inside `<svg>` is still a script tag and is removed. Element-name matching is on the local name, so namespaced variants cannot sidestep removal. `<template>` contents are processed by the sanitizer like the rest of the tree: they are inert without script, but the sanitizer does not rely on that and applies the same rules inside them.
- Removes all `on*` event-handler attributes. Attribute matching is on the local name here too, so namespaced variants cannot sidestep the removal.
- Strips `xml:base` (matched on local name): it would otherwise rebase allowed relative URLs to an attacker host, defeating the scheme policy's intent.
- Strips `ping` attributes (click-time beacons to third parties, never discussed in the external-image trade-off; matched on any element, not just anchors) and `download` attributes on anchors (turns an allowed https link into a forced file download).
- Attribute matching is on the local name, not the qualified name: `xlink:href` is treated as `href`, so namespaced URL attributes cannot sidestep the policy.
- URL scheme policy, checked on the parsed, entity-decoded attribute value (so `&#106;avascript:` and similar character-reference obfuscations are caught, not just the raw source string), after stripping the whitespace and control characters browsers ignore when scheme-sniffing: in `href`, `src`, `action`, `formaction`, `background` (any element; the obsolete `<body background>` is still honored by browsers in some modes), and `poster`, only `http:`, `https:`, `mailto:`, or relative URLs survive; anything else (including `javascript:` and `data:text/html`) strips the attribute. A `data:text/html` link navigates to an attacker-controlled document inside the trusted view, so it is blocked, not merely de-scripted. `poster` is moot once the mandated video-element removal lands, and is covered anyway. `srcset` is stripped unless every candidate URL satisfies the image rule below.
- `<img src>` must be an `https:` URL or a `data:` URI; anything else drops the image. The same https-or-data rule extends to SVG `<image>` and `<use>` elements, which otherwise fall under the looser generic href policy. This is the only intentional off-page fetch.
- In CSS (both `<style>` blocks and inline `style` attributes): drops `@import` at-rules whole, including `@import` nested inside conditional at-rules (`@media`, `@supports`); neutralises every `url(...)` whose target is not a `data:` URI; neutralises string URLs in `image-set()` and `-webkit-image-set()` (and any other CSS image function carrying URLs) unless they are `data:` URIs, since `image-set("https://..." 1x)` carries its URLs as strings, not `url()` calls, and would otherwise fetch on render with no click required; strips `expression(...)` and `-moz-binding`. `<style>` elements and inline `style` attributes are otherwise kept as written.

No body bytes reach the DOM except through one of three choke points: HTML bodies through `sanitizeSpaceHtml` before iframe injection, markdown bodies through the rehype-sanitize pipeline, and the list preview, which strips all tags to plain text and renders it as escaped text. The raw-at-rest design is safe only while every render path funnels through these; any new render path must pick one, and a required test enumerates the render paths rather than trusting the convention.

The rendered page sits in an iframe with `sandbox="allow-same-origin"` and no `allow-scripts`. The `allow-same-origin` token exists for one reason: the parent reads the frame's `contentDocument` to size the frame to its content. The sandbox escape that token is feared for requires `allow-scripts` _and_ `allow-same-origin` together; with `allow-scripts` absent, no script executes, so the token widens no executable boundary. The sanitiser is defense in depth so the srcdoc itself never carries anything live. Required: never add `allow-scripts`, enforced by a test asserting the sandbox attribute value; if auto-sizing is ever reimplemented without `contentDocument` access, remove `allow-same-origin` with it. The iframe also sets `referrerPolicy="no-referrer"`.

External images are not proxied: a third-party image URL discloses the viewer's IP, user agent, and view timing to that host on every render. This is a known privacy trade-off for passive viewing, accepted for v1. Under the injection model it becomes worse: a compromised assistant write can plant an `<img>` to an attacker's host and every subsequent render leaks viewer telemetry, with no notification to the user. Accepting the trade-off for the base case does not cover the plantable case; the mitigations are the per-turn mutation cap (a planting loop cannot run at full speed silently), the updated-time signal on the space, and treating unexpected image URLs as suspicious content to surface.

The assistant can mimic host chrome (dialogs, banners, prompts) inside a space's HTML, and the space renders inside the app's trusted view. Users should treat space content as assistant-generated, not as app UI. See Prompt Injection.

## Markdown Format

Markdown bodies render through `rehype-raw` plus `rehype-sanitize` with a restricted tag list: `p`, `br`, `h1`-`h6`, `em`, `strong`, `del`, `a`, `img`, `ul`, `ol`, `li`, `input` (task-list checkboxes), `blockquote`, `code`, `pre`, `hr`, `table`, `thead`, `tbody`, `tr`, `th`, `td`. Everything else in the schema is inherited from the default (GitHub-style) schema unchanged, with two exceptions: the markdown schema's `img` `src` protocols are pinned to `https` and `data`, matching the HTML path's image rule, and its `a` `href` protocols are pinned to `http`, `https`, `mailto`, and relative URLs (the default schema also allows `irc:`, `ircs:`, and `xmpp:`, which the HTML path strips). Raw inline HTML in markdown is sanitised by the same pipeline and cannot sidestep the HTML-format protections by choosing markdown. `javascript:` link targets are stripped by the schema. Markdown image syntax reintroduces the external-image tracking trade-off noted above.

Name, purpose, the one-line body preview, and the delete confirmation title are rendered as framework text nodes, which escape markup by construction; the preview is additionally tag-stripped to plain text first. There is no `dangerouslySetInnerHTML` anywhere in the Spaces view. Stored markup in these fields is inert text, not stored XSS.

## Context Budgets

Not yet built. The design below is the target; on main today the server enforces only the 65,536-character body cap. See Not yet built.

Space content injected into the assistant's context is bounded. The numbers below are host-configured policy constants, enforced by the host, not advisory guidance and not derived from a context-window measurement. Token estimates are format-aware and deliberately conservative overestimates, not prose averages: ceiling(chars / 4) for markdown and plain-text content (metadata, previews, markdown bodies), ceiling(chars / 2.5) for HTML bodies (tags, attributes, and entities run closer to 2 to 3 characters per token). The format used is the body format of the space being read.

- **Per-call budget: 8,000 tokens.** No single space tool call may inject more than 8,000 tokens of space content. The budget applies per direction: the request payload and the response are estimated separately, and each must fit within 8,000 tokens (a write whose input and output both approached 8K would move ~16K tokens through the call; the per-direction cap keeps each leg bounded). The host estimates before executing: a call that would exceed the budget is refused with a structured error naming the overage and the narrower path to take: `{ error: "budget_exceeded", overage_tokens, cumulative_tokens, suggested_narrower_call }`. `cumulative_tokens` is the per-turn total of space content already injected this turn, excluding the refused call; `overage_tokens` is how much the refused call's estimate exceeds the remaining budget. `suggested_narrower_call` is a human-readable string drawn from the suggestion vocabulary below; the assistant translates it into a concrete call. The suggestion vocabulary covers both directions: for a refused read, one of a metadata-only read, `list_blocks`, `read_block` on a smaller block, or a name-filtered list; for a refused write, write-narrowing options ("split into block edits against N anchors" or "reduce payload by X tokens"); for a refused write on a marker-less body within the write budget, the suggestion is to author block markers (a single full-body rewrite that adds them), since there are no anchors to split against; for a refused write on a marker-less body over the budget, the suggestion points at the rebuild recovery in Known Limitations instead. `overage_tokens` is measured against the remaining per-call budget for per-call refusals, and against the remaining per-turn aggregate budget for per-turn refusals. Refusal, not silent truncation: truncating a body the assistant is about to write back would corrupt the update. A refused call consumes no mutation-cap slot and adds nothing to the cumulative token total.
- **Per-turn aggregate budget: 24,000 tokens** of space content per assistant turn across all space tool calls. The host tracks the cumulative total in turn state; a call that would exceed it is refused with the same budget shape and an instruction to narrow scope or defer the remaining reads. Metadata-only reads (`list_spaces`, `get_space` with `include_body: false`, `list_revisions`) flow through the `read()` wrapper for funnel uniformity but contribute only their small estimated tokens to the cumulative total; the per-call budget is effectively never the binding constraint on them.
- **Full-body reads and writes count.** `get_space` returning up to 65,536 characters (roughly 16K estimated tokens for markdown, roughly 26K for HTML) counts against both budgets with no carve-out. Update payloads count too: a full-body rewrite forces the assistant to regenerate the body as output, roughly matching the input cost, so the per-call budget applies to the request body as well as the response. This is why the update journey structurally prefers block edits: small input, small output. `read_block` responses count like any other read.
- **Per-turn mutation cap: 5.** At most five space mutations (create, update, revert) per assistant turn. The cap is scoped per turn, not per space: per-space scoping would let N spaces each take 5 writes and multiply the burst bound the cap exists to provide. Legitimate journeys fit comfortably (a create plus a block edit is two); a 21-write history-eviction attack cannot run at full speed silently and instead spans five or more turns of visible assistant activity. This is the v1 answer to unthrottled content destruction: a churn bound, not prevention. The cap does not apply to the HTTP API path, which has no host-side mitigation at all (see Privacy). The cap refusal carries its own shape: `{ error: "mutation_cap_exceeded", completed_count, cap }`, where `completed_count` is the number of writes completed this turn, so the assistant can state progress accurately. The budget fields (`overage_tokens`, `cumulative_tokens`) are meaningless for a write cap and are not reused here.
- **Deferral UX.** When a turn hits the cap with legitimate work remaining, the assistant narrates the pacing in chat and continues on the next turn rather than silently dropping items. Example: "I have updated 5 of the 10 trackers; I will continue with the rest next turn." The refusal error carries the completed count so the assistant can state progress accurately.
- **Bounded discovery.** `list_spaces` accepts a name filter `q` (case-insensitive substring) so the duplicate check is a targeted query, not a full collection scan, and pagination inputs so the tool can actually continue past the first page. `list_blocks` responses are subject to the per-call budget: for a marker-dense body the host truncates at whole-block boundaries, marks the result truncated, and the tool accepts an offset to continue.

Known limitation: a marker-less space whose body exceeds the per-call budget has no full-content read or write path through the assistant's tools (`get_space` with body, `read_block` on `auto-body`, full-body replacement, and `auto-body` block edits are all budget-refused, since write payloads count too). The honest recovery: the user can see the full body in the Spaces view (the UI renders from its cached data, outside the tool budgets). The assistant rebuilds instead of editing: it creates new, smaller marker-authored spaces from content the user pastes into chat, and the user deletes the old space in the UI (the assistant has no delete tool). The script says this plainly rather than promising an edit it cannot perform. Such spaces cannot arise through the assistant's tool path (every write is budget-checked); they can only be created through the unbudgeted HTTP/SDK path. This is why marker authoring at creation is mandatory for spaces expected to be updated.

These budgets are new with this spec revision. The server still enforces only the 65,536-character body cap; everything above is host-side tool-call enforcement.

**Enforcement point.** The per-call refusal, per-turn tracking, and mutation cap are enforced in the `SpaceTool` tool server (`packages/trueforge/src/runtime/spaceCapability.ts`), in the private `read()` and `write()` wrappers that every tool handler funnels through. Per-turn counters live on the per-turn `SpaceTool` instance, which is constructed once per root-thread turn in `SpaceTurnResourceResolver.resolveAgentDefinition` (the optional session key comes from `SpaceTurnContext.sessionId`). Refusal errors originate in this tool-call layer and surface as terminal tool errors, never as HTTP responses.

## Prompt Injection

Space content is untrusted external content. Bodies are composed from chats, documents, and emails, and may contain pasted text carrying malicious instructions. Instruction hierarchy, highest to lowest: system instructions, the user's chat messages, space content. Space content is data, never instructions, even when the assistant authored it: authorship does not promote data to instruction.

The hierarchy is enforced by instruction text, not by a technical control in v1: there is no tripwire and no confirmation gate on acting on space-contained instructions. Tool results are delimited from conversation content in the harness; the exact mechanism (structural vs prompt formatting) is verified by a required test (see Testing), and the spec does not claim more than the test proves.

Operational rules:

- Tool results are delimited from conversation content in the harness. Imperative language inside a space body, block preview, name, or purpose is data. The assistant does not follow it.
- Compromised content means content instructing exfiltration, behavior change, or confirmation bypass. The assistant surfaces it to the user (what was found, where) rather than complying, and rather than silently discarding it: quiet non-compliance leaves the user unaware their page is hostile.
- The assistant's own past authorship is not a trust signal. Before acting on anything in a space that reads like an instruction, it verifies against the user's intent in chat.

## Assistant Tools

The `space` tool server exposes six tools to the assistant. Tools execute in-process on the host (never over HTTP) and are attached to the root thread only; a subagent's thread gets no space tools. There is no delete tool, by design.

- `list_spaces()`: takes no inputs. Returns metadata only (id, name, purpose, status, format, revision, created_at, updated_at), no bodies. Returns `spaces` and `aggregate_revision`, plus `has_more` when the collection runs past the tool's page limit.
- `get_space({space_id, revision?, include_body = true})`: one space, or one retained historical revision via `revision=N`. The body is included by default; pass `include_body: false` to drop the body field for a cheap metadata-only read. Do not combine `include_body: false` with `revision` when the historical body is wanted. Full-body reads count against the context budgets.
- `create_space({name, purpose, status, body, format})`: create one space. Returns `{space, aggregate_revision}` where `space` is the metadata record (no body).
- `update_space({space_id, exactly one of body | edits | block_edits, ...})`: full-body replacement (name, purpose, and status required; format optional, defaults to `markdown` when omitted; format change allowed), up to 50 search/replace edits (metadata optional, omitted means unchanged), or up to 50 block edits (metadata optional, omitted means unchanged; format change allowed). `expected_revision` optional; omitted, the host fences with the value it just read. `confirm_shrink` bypasses the shrink guard. Returns `{space, aggregate_revision, block_results?}` where `space` is the metadata record (no body), so the response to a write stays small and the write budget binds the request payload.
- `revert_space({space_id, revision, expected_revision?})`: restore a retained revision's name, purpose, status, format, and body as a new current revision. Returns `{space, aggregate_revision}` where `space` is the metadata record (no body), so the response counts as a small read. `revert_space` counts as a mutation for the per-turn cap; its request payload is just the revision number.
- `list_blocks({space_id})`: block anchors with whitespace-collapsed, ellipsis-truncated 80-character previews and occurrence counts, plus the preamble (preview plus character count; not addressable by anchor, edited via a full-body update). A marker-less space reports the single `auto-body` block. Used after context compaction to recover anchors, and to scope edits without pulling the full body.

Tool errors are terminal and specific: unknown space, revision outside the retained window (distinguished from unknown space), stale guard (carries the current revision in a `revision` field), refused shrink, unknown or duplicated anchor (lists valid anchors), body over the cap, budget refusal (`{ error: "budget_exceeded", overage_tokens, cumulative_tokens, suggested_narrower_call }`), mutation-cap refusal (`{ error: "mutation_cap_exceeded", completed_count, cap }`). Anything else is an infrastructure failure and surfaces as such, not as a tool result.

## API

Mounted at `/api/v1/spaces`, behind the same session-cookie auth middleware as every other route. The generated SDK is `packages/trueforge-sdk`, auto-generated by Fern from the OpenAPI definition and regenerated in CI (never hand-edited). Request/response schemas are the zod schemas in `packages/trueforge/src/schemas/space.ts`, published through the OpenAPI definition that generates the SDK. Route-consumer map:

| Route                                                 | In-tree HTTP caller                                                      | Notes                                                                                                                                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /` list (offset-paginated)                       | Spaces view                                                              | Query params: `limit`, `offset`, `expected_aggregate_revision` (continuation guard, requires `offset`). No name filter. Returns full records; the UI renders the detail page from this cache |
| `GET /{space_id}` (`?revision=N`)                     | Spaces view (conflict refresh), direct API consumers via the SDK         | 404 when the revision aged out of the window (same as space not found; a distinct 410 is not yet built)                                                                                      |
| `POST /` create                                       | none in UI or assistant code; direct API consumers via the generated SDK | The assistant creates through its tool, not HTTP                                                                                                                                             |
| `PUT /{space_id}` replace                             | none in UI or assistant code; direct API consumers via the generated SDK | Same as above                                                                                                                                                                                |
| `POST /{space_id}/revert`                             | none in UI or assistant code; direct API consumers via the generated SDK | Same as above                                                                                                                                                                                |
| `DELETE /{space_id}` (`?expected_revision=` required) | Spaces view                                                              | Also exposed to direct API consumers via the generated SDK (`client.spaces.delete`). The no-delete guarantee covers only the assistant's tool set, not API consumers                         |

All routes are per authenticated user, scoped by tenant and user id; probing another user's space id returns 404, not 403, so existence is not disclosed. IDs are ULIDs, not sequential. Historical revision reads enforce the same per-user scoping as current reads (verified in the store: both the live row and the revision snapshot filter on tenant and user).

`DELETE /{space_id}` carries this OpenAPI description (required change): "No assistant tool exposes deletion; it is exposed to direct API consumers via the generated SDK." The old description ("only a person acting through the UI can delete a space") overstated the restriction and is removed. The description is a policy statement, not a mechanism: the route performs no UI-vs-tool caller distinction and cannot tell a UI session apart from any other authenticated HTTP client. The actual enforcement is architectural and threefold: (1) no `delete_space` tool is registered; (2) the tool server's store surface excludes `deleteSpace` entirely, so no code path reachable from a tool call can invoke it; (3) the assistant's tool set contains no HTTP client for the API and no credential for it.

Status codes: 200 read/update/delete/revert, 201 create, 400 invalid request (overlong name/purpose, body over the cap, more than 50 block edits, unknown format value, malformed id), 401 unauthenticated, 404 space not found (aged-out revisions also read back as 404; a distinct 410 is not yet built), 409 stale guard (response body `{ error: { message } }`; the stale-guard message names the current revision).

## Privacy

- Spaces are private to the user who created them; there is no sharing.
- The precise no-delete guarantee: no registered assistant tool reaches deletion. The tool server exposes six read/write tools; its store surface excludes `deleteSpace`; the only in-tree caller of the HTTP DELETE route besides direct SDK consumers is the UI. The guarantee is architectural, not a per-request caller check: the DELETE route authenticates like every other route and any authenticated HTTP client could call it, but the assistant has no tool that issues HTTP requests to the API and no credential for it. The guarantee covers the assistant's tool set only, not API consumers: the generated SDK exposes `client.spaces.delete` as a first-class operation.
- The residual HTTP path (PUT, revert, and DELETE via any authenticated HTTP client) bypasses every host-side mitigation: no token budgets, no mutation cap, no shrink guard, no per-turn tracking. The threat actor for this path is anyone holding a valid session cookie who is not the assistant: the user themselves calling the generated SDK directly, or a third party who stole a session cookie (through another application's XSS, device access, or a leaked token). The assistant cannot reach this path because it has no HTTP client for the API and no credential for it; the TO VERIFY item covers the deployment-network check for the model-issued-HTTP variant.
- What the guarantee does not cover: the assistant can replace a space's body with empty or junk content through `update_space`, and can archive it (removing it from the user's normal attention). The shrink guard adds friction to catastrophic truncation but the assistant certifies the bypass flag itself, and an equal-length rewrite passes untouched. With 21 successive writes the original content ages out of the 20-revision window and becomes unrecoverable. The per-turn mutation cap of 5 slows this from seconds to five-plus turns of visible activity; it does not prevent a determined multi-turn attack. The spec states this honestly: absence of a delete tool is not the same as inability to destroy content. Detection relies on `updated_at` and revision counters the user must proactively inspect; nothing notifies the user of assistant mutations.

## Out of Scope (current behavior, not planned)

- Sharing or collaboration: spaces are single-user, no shared links, no co-editing
- Search within space bodies: the list returns metadata only; finding content means opening spaces. There is no name filter; bodies are not searchable.
- Export: no PDF, print, or file export of a space
- Notifications: nothing fires when a space changes. Combined with assistant write access, this means the user discovers mutations only by opening the space.
- Automatic links: spaces do not link to the chats, documents, or emails their content came from; the body is standalone text the assistant composed. There is no pinning or source-reference mechanism; the data model has no field for pinned items.
- Revision window is 20; older history is gone
- Body cap is 65,536 characters; larger pages must be split by the assistant. The split is narrated before anything is written: the assistant says the page exceeds the cap, proposes the split (e.g. one space per section), and only creates the spaces once the user agrees. No silent fan-out of spaces.
- No user editing, archiving, or reverting from the UI: all content operations are assistant-mediated through chat. The UI offers read, delete, and nothing else.
- Write volume: no quotas on number of spaces or total writes. The per-turn mutation cap (5) bounds burst churn only.

Future work, tracked here (no issue filed; this spec document is the tracker): body search, export (PDF/print/file), and pinning / source references. The email integration spec also defers structured source links to the spaces mechanism (its spaces section), so the two deferrals agree: pinning waits on this spec.
