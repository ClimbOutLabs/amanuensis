# Spec: Aman on Windows

**Status:** draft

## Problem

The friends release (v0.2.0) waits on Windows. Today's installer is about 8,500 lines of shell (`installer/install.sh`, `installer/lib/*.sh`, `installer/doctor/aman`) plus two Node modules (`pki.mjs`, `qr.mjs`). It runs on Mac and Linux, and on Windows only inside WSL, which means a Linux terminal, a Linux user account, backups that stop when WSL idles out, and a Linux `~/.amanuensis` the person cannot see. The friends have never opened a terminal and will give up at the first confusing step.

The installer also builds every image from a git checkout. That needs git, a 6 GB Docker memory floor, about 700 MB of npm downloads and a 20 to 40 minute build on a laptop. The owner keeps the build on every PC (nothing runs that the person's own PC did not build), so the Windows design has to make that wait safe and plain for someone who has never watched a build, and has to drop the git requirement.

## Solution

One cross-platform installer written in TypeScript, shipped as a single executable per platform, that does on Windows what the shell version does on Mac and Linux, reads and writes the same state directory layout, and replaces the shell version one command at a time. Windows gets it first, as a thin end-to-end slice. Mac and Linux move to it afterwards without reinstalling: the shell `aman upgrade` already overwrites `bin/aman` from the checkout on every upgrade, so the day the checkout's `installer/doctor/aman` becomes a launcher for the new executable, existing installs pick it up at their next upgrade.

The person on Windows: downloads `Aman-Setup.exe`, double-clicks it, answers four questions in a plain window, waits, and gets a desktop icon called Aman. Docker Desktop is the only prerequisite, and the installer installs it for them.

### Scope of this spec

In: the Windows installer end to end, the host-side adapters, delivery, the migration of Mac and Linux onto the same code, the test strategy, the build plan. Out: a graphical installer (the window is a plain text window with one question at a time; a GUI can follow once the flow is right), signing in with outside accounts (Aman uses only its own sign-in), reach beyond this computer and the home network, and any change to the app itself except where named below.

## What stays Linux-only

The app, the sign-in service, the speech service and the sandbox slots run in Linux containers. On Windows, Docker Desktop runs them inside a Linux virtual machine (WSL2 by default, Hyper-V where WSL2 is unavailable). The person never sees that machine. They see Docker Desktop once, as the one program the installer puts on their PC first, and afterwards as the whale icon in the tray.

The gVisor sandbox needs no host support. Each slot container's agent starts every call in a fresh `runsc` guest with `--platform=systrap`, which needs neither KVM nor ptrace from the host, and the slot setup already detects a Docker Desktop host, skips the AppArmor profile (the agent records its absence, as on Mac) and skips the per-slot disks (the VM's disk bounds the workspaces). The owner has confirmed this works on Docker Desktop for Mac, which is the same model: a Linux VM with a LinuxKit kernel. On Windows the WSL2 backend runs Microsoft's WSL2 kernel instead, which supports seccomp and the system calls systrap uses, so the sandbox is expected to run unchanged. This is the first thing the owner proves on a real PC (owner test W1 below); if it fails, `--no-sandbox` is the fallback and run code shows as off in the app, as it does today.

Nothing else on Windows needs administrator rights except installing Docker Desktop and adding one firewall rule. Everything else is per-user.

### The long wait

The friends bring their own model key, so the one long wait the person cannot avoid is the build. It is designed for someone who has never seen one:

- The window shows one line per part in plain words ("Building the Aman app", "Building the sandbox", "Downloading the speech model") with elapsed time and a rough time left, taken from the sizes in the printed plan. No build output is shown; it goes to a log file the message names only if something fails.
- Before the first question the window says: "The next part takes 20 to 40 minutes and needs nothing from you. You can keep using this PC. Leave the window open, and do not close the laptop lid."
- The installer asks Windows not to sleep while it builds, the same request a video player makes, so a quiet PC does not stop the build. The screen may still lock; that is fine.
- If the PC sleeps anyway (the lid is closed, the battery runs out), Docker Desktop pauses with it. On wake the build continues where it was. If the window was closed, the person opens Aman Setup again: every image that finished is kept, and the window says "Continuing where it left off."
- If the build fails, the message is one sentence about what happened and one about what to do, with the log file named for the owner: "Building the Aman app ran out of memory. Open Docker Desktop, Settings, Resources, and give it at least 6 GB, then open Aman Setup again."

The memory check runs before the first question, not after the wait: a laptop whose Docker Desktop has under 6 GB is told so at the start, with the same Settings, Resources sentence, before anything is downloaded.

The same bar applies to Mac and Linux once they move onto this installer: a `.pkg` on Mac (double-click, admin password once for Docker Desktop, the same questions), and on Linux a downloaded executable that offers the Docker Engine install steps it already prints today. Those two are later PRs and are listed in the build plan, not designed further here.

The installer is one TypeScript program. Everything that touches the operating system goes through one `Host` interface with three implementations (`windows`, `darwin`, `linux`) and one fake for tests. ### Installing Docker Desktop

The installer downloads `Docker Desktop Installer.exe` from `desktop.docker.com` over https, checks its Authenticode signature (the signer must be Docker Inc, the chain must be valid) before anything runs elevated, then runs it with `install --quiet --accept-license --backend=wsl-2`. It states what that means in one sentence first: "Docker Desktop is made by Docker Inc. Its terms apply to it; Aman only runs inside it." Docker Desktop's installer turns on the WSL feature and asks for one restart when WSL was missing. If the PC has virtualization turned off in its firmware, nothing can be done from software; the message is: "This PC has virtualization turned off, which Docker Desktop needs. It is a setting in the PC's startup menu. Ask the person who helps you with this computer, then run Aman Setup again." Windows 10 22H2 and Windows 11 are supported; Home editions are fine because WSL2 does not need Hyper-V.

### Where the source comes from

The installer no longer needs git or a checkout. It downloads the release's source archive from GitHub (`codeload.github.com/.../zip/refs/tags/v0.2.0`), checks it against a SHA-256 pinned into the executable at build time, and unpacks it under `%LOCALAPPDATA%\Amanuensis\source\<tag>`. Image tags come from the release tag instead of the git tree hash, so a reinstall builds nothing and an upgrade sees the change. On Mac and Linux a checkout keeps working for developers: the installer uses the checkout when started from one and the archive otherwise.

No prebuilt images are published. The owner's decision is that every PC builds the app, the speech service and the sandbox from the source it downloaded, and pulls only what it pulls today: the sign-in service and the https front end by pinned digest, and the base images the Dockerfiles name. The cost is the 20 to 40 minute wait and the 6 GB Docker memory floor, both handled above; the gain is that nothing runs on the friend's PC that their own PC did not build from the released source, which the install docs state in one sentence.

The model key: the friends bring their own Token Factory key. The Windows flow keeps one plain step, "Paste your model key:", preceded by the address where a key is made and one sentence on what it is for. The key is read hidden, never echoed, never put in a command line, and written only to the instance `.env` with a user-only ACL, as today. A person who leaves it empty is told, in one sentence, that Aman will open but cannot answer until a key is added under Settings, Model, and the closing summary repeats that line.

## Delivery

GitHub Releases carries, per tag: `Aman-Setup.exe` (Windows x64), `Aman-Setup.pkg` (Mac, universal, later PR), `aman-linux-x64` and `aman-linux-arm64` (later PR), and a `manifest.json` with the SHA-256 of each and of the source archive. The Windows executable is built on Linux, because there is no Windows machine in the build path: one esbuild bundle of the installer package becomes a Node single executable application blob, injected with `postject` into a pinned Windows `node.exe` downloaded from nodejs.org and checked against a SHA-256 in `release.json` (a `node_sha256_win_x64` pin beside the four that exist today), then given its icon and version resource with the pure JavaScript `resedit`. Nothing in that chain needs Windows. How the result is checked is in Testing.

Unsigned, the person sees two warnings: the browser's "isn't commonly downloaded" (Edge: Keep, Show more, Keep anyway) and SmartScreen's "Windows protected your PC" (More info, Run anyway). The release page shows both screens with the two buttons circled, in that order, and nothing else. Signing with a standard code-signing certificate does not remove SmartScreen until the file earns reputation; Azure Trusted Signing (about ten dollars a month, needs a registered business or a verified individual) or an EV certificate removes it at once.

The owner's decision: v0.2.0 ships unsigned, with the two-screenshot guide on the download page. Signing is a later PR, after v0.2.0, once a signing service is set up.

## Migration: retiring the shell without breaking Mac and Linux

The contract between old and new is the state directory, not the code. Its layout is already fixed by the shell version: `state/instances/<name>/*` registry files, `release/release.json` and `previous.release.json`, `instances/<name>/compose.yaml`, `.env`, `dex.env`, `tls/ca`, `tls/leaf/<name>`, `tls/trust/<name>`, `backups/<timestamp>/`, `state/backups`, `state/source`. PR 2 writes that layout down as `installer/STATE.md` and adds a contract test that both implementations pass against the same fixture directory; from then on neither may change a file format without the other.

Order of retirement:

1. The TypeScript installer handles Windows only. Mac and Linux keep the shell. No shell file changes except the contract test.
2. The TypeScript installer gains Mac and Linux, reading existing state directories as they are. `installer/doctor/aman` becomes a 40-line launcher: it finds `~/.amanuensis/runtime/aman` (the new executable, downloaded and SHA-256 checked the same way the pinned Node is today) and runs it with the same arguments. Because the shell `aman upgrade` already copies `installer/doctor/aman` into `bin/aman` on every upgrade, every existing install switches to the new code at its next `aman upgrade`, with no action from the person, and `aman upgrade` keeps working before, during and after.
3. `install.sh` becomes the same kind of launcher for people who run it from a checkout. Each shell library is deleted in the PR whose TypeScript module replaces it, together with its tests and its stub, so no dead code waits around. The `lint:installer`, `test:installer*` scripts and the CI filters move with them (the `AGENTS.md` sync rule).
4. When `installer/lib` is empty, the two launchers are the only shell left. Rollback at any step is a revert, because the state layout never changed.

Mac and Linux installs made by the shell never need a reinstall. A Windows install made by this spec never has a shell to migrate from.

## Privacy

The installer reads no chats, memories, mail or audio. It handles the owner email, the password (hashed once inside the app image, never stored), the optional Token Factory key (written only to the instance `.env` with a user-only ACL), generated secrets, the certificate authority and its key, and install state and logs. On Windows this all lives under `%LOCALAPPDATA%\Amanuensis` with inheritance removed from secret files, and backups stay on the PC, unencrypted, as today. The installer contacts only the hosts the plan prints: GitHub for the source archive and the executable, Docker Hub, ghcr.io, npm, PyPI, Hugging Face and nodejs.org for the builds, `desktop.docker.com` for Docker Desktop, and Token Factory only when a key is given. No telemetry, no network scanning, no crash reports. Reach is this computer plus the home network: the firewall rule is for the Private profile only, the app is published only on `127.0.0.1` and this PC's own private addresses, and a public address is never offered.

## Testing

The cloud sessions that build and review this have no Windows machine, and GitHub Actions does not run on this repository (its runs fail within seconds of starting, so there is neither a Linux nor a Windows runner to lean on). The owner has a Windows PC and tests on it nightly. The split:

**On Linux, every PR, before it is pushed.** All installer logic is platform-neutral TypeScript tested with `node --test` under `packages/aman-installer/tests` (mirroring `src`), against the `Host` fake and a recording process runner. The recording runner captures every command line the installer would run and compares it to golden files, so a reviewer can read exactly which `schtasks`, `certutil`, `icacls`, `netsh` and `reg` invocations a flow produces, and a full `aman install --yes` runs against a fake Docker that answers from fixtures. The contract test runs both implementations against one state-directory fixture. All test data is synthetic: fake emails, generated secrets, never a real person's data. The building session runs `pnpm test:aman-installer` and `pnpm typecheck` before every push (the pre-push hook selects them), and each of the six reviewers runs them again; that, not a CI badge, is the proof a PR carries. PowerShell Core on Linux parse-checks the two one-line PowerShell calls (shortcut creation through the Shell COM object, and the Authenticode check), since both can only run on Windows.

**The `.exe`, built and checked on Linux.** The build script (`pnpm installer:exe`) is proven three ways without Windows: the same bundle that goes into the executable is run on Linux Node through the whole fake-host install, so the code inside the `.exe` is the code the tests passed; the finished file is parsed as a PE image (valid headers, the SEA resource present, the version resource reading back the release tag) and its SHA-256 is written to `manifest.json`; and `aman.exe --version` and `aman.exe --help` run under Wine as a smoke test that the injected blob starts. Anything deeper than that on Windows is the owner's.

**On the owner's Windows PC, nightly.** Each night a scheduled cloud session builds everything merged that day and publishes one downloadable build as a GitHub pre-release named `nightly-<date>` (the Releases API needs no Actions; `RELEASING.md` already cuts releases that way), replacing the previous night's and keeping the last seven. The pre-release carries `Aman-Setup.exe`, `manifest.json` with its SHA-256, and `TEST-SHEET.md`. The sheet is short and in plain steps: first the checks added by that day's merged PRs, then the standing checks W1 to W9 below marked as optional unless a release is near. Each Windows PR adds its checks as a file under `packages/aman-installer/owner-tests/`, one check per heading, each with the steps, what the person should see, and a "Screenshot:" line naming the one screen to capture; the nightly script concatenates the files that changed since the previous nightly tag. The owner runs the sheet, and anything that fails becomes an issue with the screenshots attached and a next-day fix PR. An empty merge day publishes no nightly.

**Merging.** A Windows PR merges once the six reviewers approve and the Linux proof above is in the PR. There is no CI gate to wait for, and it is safe because Mac and Linux keep the shell installer until PR 7 (Mac and Linux on the new installer), so nothing a Windows PR ships can reach an existing install before the owner has run it from a nightly.

**The standing checks.** Before v0.2.0, all of these on one PC that starts with no Docker Desktop and no WSL, with a stopwatch and a click counter; on an ordinary night, only the ones the sheet lists:

- W1. Sandbox proof: with Docker Desktop installed, `aman doctor sandbox` passes every slot's safety check and a real call, and a chat runs a Python snippet.
- W2. The full first install from the release page, counting clicks and waits against the table above, and reading every message aloud for jargon.
- W3. Restart the PC: Aman comes back without touching anything, and the desktop icon opens it.
- W4. Open Aman from a phone on the same Wi-Fi via the printed address, do the trust page, sign in.
- W5. Set the clock to 03:31 and confirm a backup folder appears; then `aman backup` by hand.
- W6. `aman upgrade` to a second build; then break the second build on purpose and confirm the rollback message and a working app.
- W7. Settings, Apps, Amanuensis, Uninstall, with and without the data. Confirm nothing is left in `%LOCALAPPDATA%`, Task Scheduler, the certificate store, the firewall and the Start menu.
- W8. The failure paths: Docker Desktop closed when the icon is clicked; virtualization off (a VM with it disabled); the laptop on a public Wi-Fi profile (Aman stays reachable on this PC only).
- W9. Open the app in Edge, Chrome and Firefox on the PC: no certificate warning in the first two, the Firefox steps from the trust page in the third.

## Decisions taken by the owner

1. No prebuilt images. Each PC builds from source; the build wait stays 20 to 40 minutes and is made safe to leave running (The long wait above).
2. v0.2.0 ships unsigned, with the two-screenshot download page guide.
3. Friends bring their own model key. The Windows flow keeps a plain "Paste your model key:" step with a link to get one.

4. There is no Windows CI, and GitHub Actions does not run on this repository. Every PR is proven on Linux with the fake host and the recorded-command tests, the `.exe` is built on Linux, the owner tests a nightly build on a real PC, and Windows PRs merge after the six reviewers.

v0.2.0 waits for Windows. The build plan marks which PRs are its gate.

## Build plan

Each PR is small, gets the six standing reviewers (SCOPE/USER, SECURITY, EFFICIENCY/CODE QUALITY, INTEGRATION, PM, QA/TEST) before merge, is proven on Linux as described in Testing, adds its owner checks under `owner-tests/` so they appear on that night's sheet, and names what the owner tests on a real Windows PC. The owner's nightly failures come back as next-day fix PRs, outside this numbering. Sonnet sessions build from this list after approval. PRs 1 to 3 are the first stage: a Windows person gets from download to a working Aman. The target for that stage is one week of sessions plus one owner test day. PRs 1 to 6 are the v0.2.0 gate: the release is cut when all six are merged and the owner's tests W1 to W9 pass on a clean PC. PRs 7 to 9 follow the release.

1. **Package and skeleton (v0.2.0 gate).** New workspace package `packages/aman-installer` (TypeScript, Node 24, esbuild bundle, no runtime dependencies beyond what the repo already pins), the `Host` interface with `windows`, `darwin`, `linux` and `fake` implementations, the recording process runner, the plain-window UI (one question at a time, prompts end with a colon, messages from one shared `messages.ts` so reviewers see every sentence a person can read). Commands: `--version`, `doctor docker` (is Docker Desktop installed, running, with enough memory). Scripts: `test:aman-installer`, `installer:exe` (the Linux build of the `.exe` with the pinned `node.exe`, the PE check, the Wine smoke test and `manifest.json`), and `installer:nightly` (build, then publish the `nightly-<date>` pre-release with the sheet through the Releases API); the `ci.yml` filters and matrix ids stay synchronized as `AGENTS.md` requires, even though the workflow does not run.
