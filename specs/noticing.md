# Spec: Noticing

**Status:** implemented

**Scope note:** This spec covers what the assistant watches for (mail from people the person marked always important, calendar clashes and travel, bills and deadlines, approvals that wait), how it decides how loudly to say so, and the Reach me settings page. It builds on the delivery feed in [Reaching You](notifications-delivery.md). Text messages are covered in [Text Messages](text-messages.md). Phone calls are separate work: this spec leaves the place for them.

## Problem

The assistant only spoke when the person opened a chat. A clash on the calendar, a bill due in two days or an approval left waiting went unnoticed, and a person had no say in what could interrupt them.

## Solution

Watchers look for a few kinds of event. Each new event is judged once by the model a new chat starts on, then the person's own rules decide what happens. Everything lands in the bell with the reason it was sent. The person chooses, in Settings, Reach me, what may reach them and how.

## Levels

- **Note**: a quiet item in the bell. No push. This is where most things end up.
- **Nudge**: a delivery with a push notice to the person's devices, and a text when the person has texts on and a confirmed number.
- **Call**: a phone call. Until phone calls are set up, a call that survives every rule is delivered as a nudge, and the reason says so. The level rules for calls stay in code and are tested, so a phone channel only has to report itself available.

## Watchers

- **Mail** every 10 minutes, only mail that reached the inbox since the last check, by the mail server's own arrival time, never more than a day back. A pass reads at most 100 messages. On Gmail, when a window holds more, it is halved until the mail in it fits, so every message before the point a pass stops at was read, and the next pass starts exactly there. On IMAP mail is listed by the server's message number instead (see below). A pass that reached the present starts the next one ten minutes earlier, for mail the server lists late (an index that lags, or a clock that runs ahead, or mail moved into the inbox with an older date). On IMAP the next pass goes on from the cursor, and that time is used only after a renumbering, where mail is named by its Message-ID so the ten minutes listed again raise nothing new. Gmail is listed by message, not by thread, so a reply cannot hide the mail before it. When Gmail is too slow to read a window, the next pass starts after the newest message read, or at the same place when none was. The shortest Gmail window is four seconds. A flood that holds more than a pass can read even then (500 messages) is passed over with a warning in the log and a fixed note, except mail from always-important senders, which is still listed and read, so a flood cannot hide it. On IMAP a flood is simply read over as many passes as it takes, since each pass goes on from the last message number it reached. A message the source can never read (gone, too large, a reply that does not parse, or a body that cannot be taken apart) is skipped with a warning, and the rest of the pass goes on. One later reply in a thread that cannot be read or fetched is left out of the paid-check, on Gmail and IMAP alike, so a stranger joining a thread cannot hide a payment.

  A failed read is one of three kinds. A message the source can never read, or an IMAP body over the connector's limit, is passed over at once. A **busy** failure says nothing about the message: a rate limit (HTTP 429, or a Gmail 403 that says the user is going too fast), a server error, a dropped connection, a login that could not be refreshed mid-read, a connector reply that names a timeout, a lost or missing connection or a failed login, and the session ending. Any other failure is **unclear**. The first failure of either kind does not stop the pass: the pass goes on, and once a later message's read worked, the failing message is tried once more. A failure that survives the retry counts as a failed pass for the message if it is unclear, and never counts if it was busy. A message that fails 3 counted passes in a row is passed over with a warning, and the next failing message counts from one. A second failure with no working read between stops the pass at the first of them, without counting either. The checkpoint remembers the message a pass stopped at, busy stops included, and when it first did. A message that has held up passes for 3 hours from then is passed over too, but only through the retry that followed a read that worked in the same pass. So a server that fails on everything, or a rate limit that lasts for hours, never makes a pass skip a message, and a message passed over never moves the checkpoint past the messages after it. A passed-over message that looked like a bill, or came from an always-important sender, raises a fixed note with when it arrived and who sent it.

  **Mail trouble follows how far behind the checkpoint is.** Reach me shows trouble whenever the mail read so far is more than an hour behind the clock, whatever the last pass reported. The kind is slow when the last pass ran out of time or calls, otherwise what the pass recorded: sign in to Google again, make a new app password for the Email connector, or something else. A busy or failing server shows as slow. A pass that leaves mail unread records the kind and when it first did so, and only a pass that reads to the end of its window clears it. The findings of the messages before a stop are written down, and the checkpoint moves to the arrival of the earliest message not read. On IMAP the checkpoint also keeps a cursor, the mailbox's UIDVALIDITY and the number (UID) of the last message handled, as runtime state. While some of the mail listed by time is still ahead of it, it also keeps the highest UID being dated and the time those messages are held to. The next pass lists the mail after it, so a pass that ran out of time or stopped at a flaky message keeps its progress exactly, however many messages arrived in the same second. A failure before any message is read leaves the checkpoint where it was.

  **Mail left behind raises one fixed note.** Mail a pass leaves unread for good raises one note for the whole stretch of trouble, "Aman could not read some mail that arrived from X on" while the trouble goes on, and "between X and Y" (or "around X" when both times print the same) once it has ended, with the assistant's own name ("Your assistant" when none is set) and the times in the person's time zone. Its id is the time the trouble began (or the hour of the first gap when there was none), so every pass of a stretch makes the same event and a delivered note is never repeated or widened. It is a fixed note, whose reason says some mail could not be read. It covers mail older than a day after a long outage (told when a pass reads past it), a stretch of Gmail that cannot be listed and is passed over, IMAP messages whose headers cannot be read, a Gmail flood passed over, and mail left unread when the last mail source goes away. A single message passed over has its own note only when it looked like a bill or came from an always-important sender, whether it was passed over after failing or because the source says it can never be read. Other single messages are not told about.

  A thread check that fails for any reason never stops the pass and never counts against the message: the bill is kept to be checked again with the tracked bills, and is raised once it falls due within 24 hours. A bill due later than the window is tracked without a thread check. The tracked bills are looked at first, and the ones due within 24 hours are raised without a call when the budget is gone, or when mail cannot be reached at all. A bill whose thread can never be read, including one that was permanently deleted, is raised at once, since nothing can say it was paid. A person who paid and then emptied the trash may be nudged for that bill, which is the price of never missing one.

  The look at tracked bills and the scan share one budget of 60 seconds and 80 calls to the mail server, which leaves room in the 4-minute session for opening it and one last slow call. A Gmail list also counts each message it fetches, and the look at tracked bills may use only the first 20 seconds and 20 calls. Each checks the budget before every call. A call can take up to its own limit (75 seconds for mail), and the session a connector stays open for lasts 4 minutes, so a slow pass can still be cut off. That ends as a busy failure, which never counts. The pass stops without counting anything. The next pass starts at the message it did not reach: on Gmail by its arrival, on IMAP by its number.

  On Gmail, a list that fails in a way that is not a busy server is looked into only when some list in the pass worked. A short list at the start tells a failing account (a wrong password, an account that is not found) from a failing stretch of mail, and when it fails a short list at the end does too. With neither working the pass stops, records the trouble and counts nothing. Otherwise the window is searched in one pass for the few seconds that fail alone. The mail before them is read, a flood in the way is passed over, and the pass goes on after them. The few seconds are counted under where they start, and passed over after 3 passes with a warning and a fixed note. On IMAP a list that fails that way stops the pass and records the trouble, since a bad message cannot fail a list there (see below).

  On the shared Email (IMAP) connector, new mail is listed by a small read-only helper in the connector's own container, the account agent the Email card already uses. It signs in with the same saved account (address, app password, server and port), so nothing new is set up. It opens the inbox read-only and fetches only each message's arrival time, From, Subject, Date and Message-ID, so nothing is marked read. With a cursor from the same UIDVALIDITY it searches by UID for the messages after the cursor's UID, at most 500 per call and 2,000 per pass, in UID order. With no cursor, or after the mailbox was renumbered (a new UIDVALIDITY), it starts again from the checkpoint's time, which is never more than a day back, and mail older than that is told about once as usual. Every message already in the mailbox then counts only if it arrived at or after that time, and one that comes in later is new. The cursor keeps the highest of those dated UIDs and the time they are held to. Every call goes on with both, and so does the next pass, while any dated UID is still ahead of the cursor: when the helper runs out of time before it has dated them all, and when a pass stops at an earlier message and moves the cursor back below them. So old mail is never listed as new. A restart, an early stop and a failed pass all keep them; a renumbering, a switch of mail source and the day limit drop the whole cursor and date the mailbox again. A message whose headers cannot be read, or that the server will not give, costs only itself: the cursor moves past it, it is counted, and the stretch is told about in the fixed note. A message deleted between the search and the fetch is simply gone, so it is not counted. When the server refuses a batch, the helper keeps the messages it did give and asks for each missing one alone. The helper stops starting new server calls after 35 seconds and answers with what it read so far, so a slow server usually only makes a call smaller and the next call goes on from there. Signing in, opening the inbox, the searches, the first dating call, the first header fetch and the first message asked alone are made whatever the time, and each may take up to 20 seconds, so a server slow at every step can still pass the app's 75-second limit. That pass then stops as too slow, and the next one tries again. Each call makes at least one round trip, so every call moves forward. Message ids are `imap:<UIDVALIDITY>:<UID>`, so a renumbered mailbox never gives a new message the id of an old one, and the connector's tools still get the bare UID. Events about IMAP mail are named by a hash of the Message-ID header together with the sender, the subject and the Date header, the two headers as sent (falling back to the message id when there is no Message-ID). None of these change when the mailbox is renumbered, so the same mail listed again raises nothing new. A message that copies another's Message-ID, or a sender that reuses one, still makes its own event unless its sender, Date header and subject all match too. A failed sign-in, an unreachable server and a slow answer are told apart with fixed words, so the server's own text never reaches the app. Bodies and later replies are still read through the connector's tools, which read each message on its own and report the ones they could not fetch as success with their ids missing. A tracked bill keeps the UIDVALIDITY it was numbered under in its id. Before its thread is checked, the helper is asked for the inbox's UIDVALIDITY now, once per pass, and taken from each list. When the two differ, the mailbox was renumbered and the bill's UID may name another message, so its thread is never checked against the mail now there. Whether it was paid is unknown, and the bill is raised as usual. A missing message is an unclear failure. An error from the connector, such as an account that was not found, is never read as a message that is gone. The saved account only ever holds a password sign-in, which the helper always handles, so no account falls back to another path. Without the helper's address (`MAIL_EMAIL_ACCOUNT_URL`) the shared mailbox is not watched.

- **Trouble with mail is shown.** The checkpoint also keeps when passes first left mail unread and why, until a pass reads to the end of its window. Settings, Reach me says in plain words that mail has not been checked since then, with the one thing to do, once the checkpoint is an hour behind. A mail source that is set up but cannot be opened counts as trouble too: the shared Email connector out of reach, or a Google login that has to be redone. While it cannot be reached, bills already tracked still come due. Which source is watched is written in the checkpoint and shown on Reach me. The person's own Google mail wins. The shared connector is read for the instance owner only when Google gives no mail at all, never in place of a login that must be redone. When the source changes, the place mail was read to and the start of the trouble carry over, up to a day back, so a switch never hides mail left unread; the counts and the IMAP cursor of the old source are dropped. A pass that finds the mail source out of reach keeps the checkpoint as it was, whatever source it was written for. A pass that finds no source at all, after trouble or an hour behind, raises the note for the unread stretch once. A person is looked at while they have a checkpoint, even with no source or saved settings. Bills tracked from the old source stay, and are raised without a paid-check once their thread cannot be found. Only someone with no mail set up at all has no trouble shown. The calendar is modelled the same way (ready, none, or out of reach with a kind) and keeps the same record of when its checks first failed. Reach me says so after an hour, and says to sign in to Google again when a Google calendar needs it. What the calendar answered is never written to the logs.
- Mail from an always-important sender counts only when the mail server confirms the sender. The topmost Authentication-Results header (RFC 8601) of a server the source trusts must say DMARC passed for the From domain. DMARC passes only when DKIM or SPF passed for an aligned domain, so mail sent through a mail service whose own signature comes first still counts. A sender can get some of its own text into that header: its envelope address, its HELO name, and comments that repeat them. So the header is read as RFC 8601 lays it out, with quoted strings and nested comments kept whole, and a value running to the next space or `;`. Mail services quote bounce addresses that hold `=`, so quotes are read, not refused. The header is not read at all when it holds a part that cannot be read, more than one DMARC result, a HELO check, an address in brackets, a backslash outside a quote or comment, `header.from=` more than once, or a value that holds `dmarc=` or `header.from=`. Each of these is a way echoed text could pass for a result. Gmail writes the envelope address in the SPF comment and again in `smtp.mailfrom`, so any echo of it brings a second `header.from=`, which refuses the header even when a raw quote inside a comment hides the echo from the reader. A raw quote inside a comment is read as a quoted string, so a `)` in a quoted address cannot close the comment early. Only `dmarc=` and `header.from=` are looked for inside values, since a real tracking address can end in `.arc` or `-auth`. A header that cannot be read verifies nothing. A source with no trusted servers verifies nothing. A sender whose domain publishes no DMARC policy is never confirmed. Otherwise it is ordinary mail.
- **Bills and deadlines** in new mail: a due date within 3 days with nothing later in the thread saying it was paid. A bill due later is tracked and checked again as it comes near.
- **Calendar** every 30 minutes: two events overlapping in the next 24 hours, and an event with a place starting within the person's travel lead time (default 90 minutes). On Google, an event is the person's own when they made and organised it, accepted someone else's invite, or no one else is on it. An invite from outside can name the person as organizer and accepted, so organizing counts only when Google also says the person made the event. Calendar does not say whether an accept came from the person or from the invite file, so an accept is believed, unless the person is named as organizer. An event with the person as organizer that someone else made, such as a delegate or an outside invite file, is not the person's own, even with no guests and whatever id it carries, since a sender writes that id. A clash with it is only a note. On CalDAV the stored invite says who organised and who accepted in words its sender wrote, so an event is own only when no one else is on it. A clash is own only when both events are. An invite the person never accepted can only become a note.
- **Approvals** for everyone on the instance that have waited longer than the person's chosen time (5 to 20 minutes, default 15), checked every 5 minutes. A request for the person's ok closes itself after 30 minutes when they open the chat, so an approval is only raised while it can still be answered, and the setting cannot go past 20 minutes. A waiting approval is delivered with kind `approval_waiting` and the approval's id, so the bell links to it. One that was answered before it went out is dropped. Approvals in an incognito chat are never raised, so nothing from that chat reaches the bell, Activity or a device.

Each finding has a stable id, so the same thing is never raised twice. When nothing new is found, no model is called.

## From finding to delivery

- Findings are written in one insert as pending (or, for a bill due later, tracking) before anything is decided, and the watcher's checkpoint moves only after that. A pass that stops halfway leaves pending events for the next pass, never lost ones.
- A pass claims a pending event with one atomic update that stores its claim id and time, and counts the try. A claim older than 10 minutes counts as left behind, and another pass may take it. A pass that stopped without handing the event back used up a try too, so after five tries the event is marked failed and not tried again. A pass that only waited for another one hands the try back.
- The model's answer is kept with the event, so a retry never asks the model again.
- Right before delivering, still inside the person's lease, the pass marks the event as being delivered, but only if its claim is still its own. A pass that stalled while another took the event over delivers nothing.
- The delivery's id is drawn at random when the event is first written and kept with it, so every try makes the same delivery and no one else can know the id. A delivery with that id is made at most once. If another person's delivery somehow holds the id, making it fails on every try, so the event ends as failed. A pass that takes over an event left halfway through delivery, and finds its delivery made with its sends written down, sends nothing and only marks the event done, whether or not a try is left. A delivery made but with no sends written down (the pass stopped between the two) is sent again, so a notice can rarely arrive twice but is never lost. A failure to mark an event done after its delivery went out is not a failed try.
- An event that is no longer worth saying when its turn comes (an event that has started, a bill past its due date, an approval past its 30 minutes, an approval answered meanwhile) is dropped, or marked raised when a pass that stopped halfway had already made its delivery. A tracked bill whose thread fails to read for a reason that may pass waits for the next pass and does not hold up the others. One whose thread can never be read, because it was deleted for good, is raised, since nothing can say it was paid.
- Pending approvals recorded more than 30 minutes ago are dropped for everyone, including people no pass looks at any more. One left halfway through delivery is closed by the next pass that looks at that person instead.
- How loudly to reach a person is decided under a per-person lease of two minutes, well past the longest a delivery's sends take, and taken again on a later try when busy. A holder that hangs past it only lets the next pass decide. That pass makes the same delivery, and sends it again only when no send of it was written down. So two passes never both read "no nudges yet" and both nudge, or both call inside the gap.
- How much has already reached the person is read from the delivery feed itself. Only what the assistant noticed counts toward the daily nudges. Reminders and Try it never do. Any delivery that went out as a call counts toward the time between calls.

## Deciding how loudly

One model call per new event asks only for a level, a reason and a one-sentence message. The model can ask, never decide. These rules run in code on its answer:

- Each kind has a highest level. Bills and waiting approvals can nudge but never call.
- A call needs the kind to be ticked for calls, calls to be switched on, no quiet hours, and at least 6 hours since the last call.
- Text that only claimed something (for example "urgent" in a bill) can raise a note and nothing more. The model's message shows only in the feed in the app. A push notice names only the kind of thing, never the model's words. In the feed, a message that carries any phone number, site or address is replaced by the finding's own summary, and a reason that does is replaced by "The model asked for a (level)." The check is a best effort over many spellings: digits kept apart by any marks or spaces, math minus signs, digits of other scripts, keycap digits, letters that pass for digits next to digits (O, l, I, S, Z), spoken separators between digits (dash, hyphen, space, ext, extension), digits read out as words next to written ones, a number read out in words, bare, bracketed, spaced or IP-address sites, other dots and Cyrillic lookalike letters, and a full-width or spelled-out at sign. Times, dates and amounts written the usual ways do not count. A long order number counts as a phone number, so the summary is used. Only a confirmed sender or the person's own event can be louder than a note. When a kind can only be a note, no model is called.
- At most 5 nudges a day (the person can change this). Past it, events become notes.
- When the daily token cap is reached, or no model can answer, events become plain notes and no model is called.

Quiet hours (default 21:00 to 08:00 in the person's time zone) hold back calls only. A person who never saved Reach me uses the time zone of their schedules, else the one their own Google Calendar is kept in, and UTC only when neither says. The Reach me page offers the browser's time zone the first time it is opened.

The model call uses the model a new chat starts on, with no tools. It is metered under the `noticing` usage role and counts toward the daily Token Factory cap.

## Reminders

Reminders follow the same channels. A reminder is never quieter than a nudge. A person can mark a reminder urgent, and with "Call me for reminders I mark urgent" ticked it may call, under the same call rules. A reminder that goes out as a call counts toward the time between calls, read from the feed. Reminders never count toward the daily nudges. A reminder that could call waits for the person's lease, and if another pass holds it every time, it arrives as a nudge.

## Reach me settings

- **The switch for the background checks** (`noticing_on`), first on the page as "Let the assistant watch for things", with one line on what it checks and how often, and that reminders work either way. It saves on its own, at once, from the last saved settings, so other changes on the page still wait for Save. It is off for everyone, existing installs included, until the person turns it on; the default lives in one constant (`NOTICING_ON_BY_DEFAULT`). It is a field of the stored Reach me document with a default, so older rows read as the default with no migration. An import brings it in switched off, like texts and calls.
  - Off: the service skips the person before anything is opened. No mail or calendar source is opened or listed, no approvals are looked at, no model is called and nothing is delivered. Tracked bills and checkpoints are kept untouched. Reach me shows no mail or calendar trouble and no watched mailbox, since nothing is checked. Reminders are not affected.
  - Turned off mid-way: the next pass for that person does nothing.
  - First turned on: with no checkpoint the first mail check looks back only the usual 10 minutes from the moment of that pass, with the date bound as now, so old mail never floods in.
  - Turned on again after a gap: the checkpoint is where it was. Within a day the next pass reads on from it, so mail that came in while off is read then. After more than a day the usual one-day limit applies: older mail is not read, and the one fixed note about mail left unread is raised once.
- Channels: in the app (always on), push for each device, texts and phone calls. Texts have their own number and code flow when the server has a text provider (see [Text Messages](text-messages.md)); until then, and for calls, they show "not set up" with the one thing to do, and cannot be switched on.
- Always-important senders, with suggestions found in memories. Nothing is added until the person accepts it.
- Time zone, daily nudge limit, travel lead time and approval wait.
- Settings that only matter for calls (which kinds may call, quiet hours, hours between calls, call me for urgent reminders) are hidden until a phone channel is set up, with one line saying they appear then. Saved values are kept.
- A Try it button for each channel.

## Design Decisions

- Notes appear in the bell as quiet items. They never push.
- Every note and nudge is written to Activity with its reason.
- The assistant's name in any text comes from the person's own choice, never a fixed name.
- The channel list, levels and rules live in one place, so a phone channel plugs in by reporting itself available and acting on a `call` decision, with no change to the watchers. Texts did exactly that: `reachChannelsFor` reports them available when Twilio is set up, and a text sender joins the delivery layer.
- Settings, events, claims, leases and checkpoints are stored in SQLite and Postgres behind one store interface, and Reach me settings are in data export and import. An import brings texts and calls in switched off, and the number for texts in unconfirmed.
- The controller runs the passes by calling an internal route on the server with the service key, so the server alone holds mail, calendar and model access.

## Scope

- `reach_settings`, `noticing_event` (with its status, the model's answer, the delivery made, the claim and the tries), `noticing_checkpoint` and `reach_lease` tables, in one migration on SQLite and Postgres, with shared store contract tests
- Routes under `/api/v1/user/reach` (get, save, suggestions, test) and the internal `/api/internal/noticing/run`
- Mail and calendar sources: Google mail and Google Calendar for a person who connected them, and, for the instance owner only, the instance's own Email (IMAP) and Calendar (CalDAV) connectors, read with their read-only tools. Those connectors hold one mailbox and one calendar for the whole instance, so they belong to the owner. The owner is the default person when sign-in is off, and otherwise the single address the owner signs in with when people are told apart by email (the same rule the installer's name for the owner follows). With several addresses or another sign-in claim the instance names no owner and no one gets the shared connectors. Everyone else gets mail and calendar noticing only from their own Google connection.
- The Email (IMAP) connector does not pass on the receiving server's Authentication-Results, so no sender can be confirmed there. An always-important sender on IMAP mail is read as ordinary mail: it can still raise a bill note, never a nudge or call for the sender. The connector gives no thread, so "paid" is looked for in later mail with the same subject.
- Settings, Reach me page

## Privacy

- Events are read with read-only calls to the person's own mail, calendar and chats.
- When an event is judged, the model a new chat starts on sees a short, trimmed description of that one event (for example a sender, a subject and the start of the message). Nothing is sent when there is no event.
- Nothing is sent to anyone else. Push notices carry no event text, as before.
- Memory suggestions come from the person's own memories and are only questions.

## Testing

All tests use synthetic data, never a person's real data.

- Each watcher raises one event and no duplicates
- No event means no model call
- A model answer of call is lowered by each rule, including a kind not ticked for calls
- An email claiming urgency does not raise the level
- An always-important sender that fails the sender checks is treated as ordinary mail
- At the token cap, only notes are produced
- Reminders: urgent, tick and call gap
- The switch for the background checks: while off, no source, model or delivery is reached; turned off, the next pass stops; first turned on, mail is read from that moment; on again within a day, mail goes on from the checkpoint
- Shared store contract tests, route tests, and an export and import round trip with an older-format file

## Known limits

- Event ids come from the mail or calendar source. Switching the same mailbox between Google and the Email (IMAP) connector changes the ids, so one mail can be raised a second time. This is rare and the second item is the same note or nudge, so it is not worth a cross-source match.
- Gmail mail that carries no Authentication-Results of Google's own lets a forged header claiming to be Google's sit on top. Gmail adds its own header to mail it receives, so this needs mail that skipped Gmail's checks.
- On Gmail, more than 500 messages forged to look like an always-important sender, all inside four seconds, make that sender's own read too big, so the real message in the flood is passed over too. Gmail puts mail that fails DMARC under a reject policy in spam, and only the inbox is read, so this is unlikely.
- Calendar does not say whether an accept came from the person or from the invite file an outside sender wrote, so an accepted invite from outside counts as the person's own.

## Out of Scope

- Phone calls
- A summary of notes in the morning brief. Notes stay in the bell.
